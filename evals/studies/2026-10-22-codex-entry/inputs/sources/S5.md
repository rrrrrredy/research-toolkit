L5: In September 2025, OpenAI introduced GPT-5-Codex as the first version of GPT-5 optimized for agentic coding. In December 2025, we launched 5.2 which was the moment that people began to believe that using autonomous coding agents could be reliable. In particular, we saw a huge jump in how long the model could reliably follow instructions.
L6: 
L7: I wanted to stress-test that threshold. So I gave Codex a blank repo, full access, and one job: build a design tool from scratch. Then I let it run with GPT-5.3-Codex at "Extra High" reasoning. Codex ran for about 25 hours uninterrupted, used about 13M tokens, and generated about 30k lines of code.
L8: 
L9: This was an experiment, not a production rollout. But it performed well on the parts that matter for long-horizon work: following the spec, staying on task, running verification, and repairing failures as it went.

L25: ## The real shift is time horizon
L26: 
L27: This is not only "models got smarter." The practical change is that agents can stay coherent for longer, complete larger chunks of work end-to-end, and recover from errors without losing the thread.
L28: 
L29: METR's work on time-horizon benchmarks is a helpful framing for this trend: the length of software tasks frontier agents can complete with ~50% and 80% reliability has been climbing fast, with a rough ~7 month doubling time. Refer to [Measuring AI Ability to Complete Long Tasks (METR)](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/).

L33: Our recent GPT-5.3-Codex [launch announcement](https://openai.com/index/introducing-gpt-5-3-codex/) pushes this further for agent work in two practical ways:
L34: 
L35: 1. It’s better at multi-step execution (plan → implement → validate → repair).
L36: 2. It’s easier to steer mid-flight without resetting the whole run (course corrections don’t wipe progress).

L42: ## Why Codex can stay coherent on long tasks
L43: 
L44: Long-running work is less about one giant prompt and more about the agent loop the model operates inside.
L45: 
L46: In Codex, the loop is roughly:
L47: 
L48: 1. Plan
L49: 2. Edit code
L50: 3. Run tools (tests/build/lint)
L51: 4. Observe results
L52: 5. Repair failures
L53: 6. Update docs/status
L54: 7. Repeat
L55: 
L56: That loop matters because it gives the agent:
L57: 
L58: - Real feedback (errors, diffs, logs)
L59: - Externalized state (repo, files, docs, worktrees, outputs)
L60: - Steerability over time (you can course-correct based on outcomes)
L61: 
L62: This is also why Codex models feel better on Codex surfaces than a generic chat window: the harness supplies structured context (repo metadata, file tree, diffs, command outputs) and enforces a disciplined “done when” routine.
L63: 
L64: We recently published an [article](https://openai.com/index/unrolling-the-codex-agent-loop/) about the Codex agent loop that has more details.
L65: 
L66: To top this off, we also launched the Codex app that makes that loop usable day-to-day:
L67: 
L68: - [Parallel threads across projects](https://developers.openai.com/codex/projects) (long work doesn’t block your day job)
L69: - [Skills](https://developers.openai.com/codex/build-skills) (standardize plan/implement/test/report)
L70: - [Automations](https://developers.openai.com/codex/automations/) (routine work in the background)

L76: 
L77: I picked a design tool for this “experiment” because it’s an unforgiving test: UI + data model + editing operations + lots of edge cases. You can’t bluff it. If the architecture is wrong, it breaks quickly.
L78: 
L79: I gave GPT-5.3-Codex a meaty spec, ran it at “Extra High” reasoning, and it ended up running uninterrupted for ~25 hours and was able to stay coherent and ship quality code. The model also ran verification steps (tests, lint, typecheck) for every milestone it completed.

L177: ## Takeaways for long-horizon Codex tasks
L178: 
L179: What made this run work was not a single clever prompt. It was the combination of:
L180: 
L181: - A clear target and constraints (spec file)
L182: - Checkpointed milestones with acceptance criteria (`plans.md`)
L183: - A runbook for how the agent should operate (`implement.md`)
L184: - Continuous verification (tests/lint/typecheck/build)
L185: - A live status/audit log (`documentation.md`) so the run stayed inspectable
L186: 
L187: This is the direction long-horizon coding work is moving toward: less babysitting, more delegation with guardrails.
L188: 
L189: ## Try Codex on your own long-running task
L190: 
L191: This 25-hour Codex run is a preview of where building with code is going. We’re moving beyond single-shot prompts and tight pair-programming loops toward long-running teammates that can take a real slice of work end to end, with you steering at milestones instead of micromanaging every line.
L192: 
L193: Our direction with Codex is simple: stronger teammate behavior, tighter integration with your real context, and guardrails that keep work reliable, reviewable, and easy to ship. We’re already seeing developers move faster when the agent absorbs routine implementation and verification, freeing humans up for the parts that matter most: design, architecture, product decisions, and the novel problems that don’t have a template.
L194: 
L195: And this won’t stop with developers. As Codex gets even better at capturing intent and providing safe scaffolding (plans, validations, previews, rollbacks), more non-developers will be able to build and iterate without living in an IDE. There’s more coming across Codex surfaces and models, but the north star stays the same: make the agent feel less like a tool you babysit and more like a teammate you can trust on long-horizon work.
