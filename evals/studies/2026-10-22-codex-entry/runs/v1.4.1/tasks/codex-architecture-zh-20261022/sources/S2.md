L4: 
L5: Codex app-server is the interface Codex uses to power rich clients (for example, the Codex VS Code extension). Use it when you want a deep integration inside your own product: authentication, conversation history, approvals, and streamed agent events. The app-server implementation is open source in the Codex GitHub repository ([openai/codex/codex-rs/app-server](https://github.com/openai/codex/tree/main/codex-rs/app-server)). See the [Open Source](https://learn.chatgpt.com/docs/open-source) page for the full list of open-source Codex components.
L6: 
L7: If you are automating jobs or running Codex in CI, use the
L8:   [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk) instead.
L57: ## Protocol
L58: 
L59: Like [MCP](https://modelcontextprotocol.io/), `codex app-server` supports bidirectional communication using JSON-RPC 2.0 messages (with the `"jsonrpc":"2.0"` header omitted on the wire).
L60: 
L61: Supported transports:
L62: 
L63: - `stdio` (`--listen stdio://`, default): newline-delimited JSON (JSONL).
L64: - `websocket` (`--listen ws://IP:PORT`, experimental and unsupported): one
L65:   JSON-RPC message per WebSocket text frame.
L66: - Unix socket (`--listen unix://` or `--listen unix://PATH`): WebSocket
L67:   connections over Codex's default app-server control socket or a custom Unix
L68:   socket path, using the standard HTTP Upgrade handshake.
L69: - `off` (`--listen off`): don't expose a local transport.
L70: 
L71: When you run with `--listen ws://IP:PORT`, the same listener also serves basic
L72: HTTP health probes:
L73: 
L74: - `GET /readyz` returns `200 OK` once the listener accepts new connections.
L75: - `GET /healthz` returns `200 OK` when the request doesn't include an `Origin`
L76:   header.
L77: - Requests with an `Origin` header are rejected with `403 Forbidden`.
L78: 
L79: WebSocket transport is experimental and unsupported. Local listeners such as
L80: `ws://127.0.0.1:PORT` are appropriate for localhost and SSH port-forwarding
L81: workflows. Non-loopback WebSocket listeners currently allow unauthenticated
L82: connections by default during rollout, so configure WebSocket auth before
L83: exposing one remotely.
L84: 
L85: Supported WebSocket auth flags:
L86: 
L87: - `--ws-auth capability-token --ws-token-file /absolute/path`
L88: - `--ws-auth capability-token --ws-token-sha256 HEX`
L89: - `--ws-auth signed-bearer-token --ws-shared-secret-file /absolute/path`
L90: 
L91: For signed bearer tokens, you can also set `--ws-issuer`, `--ws-audience`, and
L92: `--ws-max-clock-skew-seconds`. Clients present the credential as
L93: `Authorization: Bearer <token>` during the WebSocket handshake, and app-server
L94: enforces auth before JSON-RPC `initialize`.
L95: 
L96: Prefer `--ws-token-file` over passing raw bearer tokens on the command line. Use
L97: `--ws-token-sha256` only when the client keeps the raw high-entropy token in a
L98: separate local secret store; the hash is only a verifier, and clients still need
L99: the original token.
L100: 
L101: In WebSocket mode, app-server uses bounded queues. When request ingress is full,
L102: the server rejects new requests with JSON-RPC error code `-32001` and message
L103: `"Server overloaded; retry later."` Clients should retry with an exponentially
L104: increasing delay and jitter.

L194: ## Core primitives
L195: 
L196: - **Thread**: A conversation between a user and the Codex agent. Threads contain turns.
L197: - **Turn**: A single user request and the agent work that follows. Turns contain items and stream incremental updates.
L198: - **Item**: A unit of input or output (user message, agent message, command runs, file change, tool call, and more).
L199: 
L200: Use the thread APIs to create, list, or archive conversations. Drive a conversation with turn APIs and stream progress via turn notifications.
L201: 
L202: ## Lifecycle overview
L203: 
L204: - **Initialize once per connection**: Immediately after opening a transport connection, send an `initialize` request with your client metadata, then emit `initialized`. The server rejects any request on that connection before this handshake.
L205: - **Start (or resume) a thread**: Call `thread/start` for a new conversation, `thread/resume` to continue an existing one, or `thread/fork` to branch history into a new thread id.
L206: - **Begin a turn**: Call `turn/start` with the target `threadId` and user input. Optional fields override model, personality, `cwd`, sandbox policy, and more.
L207: - **Steer an active turn**: Call `turn/steer` to append user input to the currently in-flight turn without creating a new turn.
L208: - **Stream events**: After `turn/start`, keep reading notifications on stdout: `thread/archived`, `thread/unarchived`, `item/started`, `item/completed`, `item/agentMessage/delta`, tool progress, and other updates.
L209: - **Finish the turn**: The server emits `turn/completed` with final status when the model finishes or after a `turn/interrupt` cancellation.
L210: 
L472: ## Threads
L473: 
L474: - `thread/read` reads stored thread metadata without subscribing to it.
L475: - `thread/turns/list` pages through a stored thread's turn history without
L476:   resuming it. Use `itemsView` to choose whether turn items are omitted,
L477:   summarized, or fully loaded.
L478: - `thread/items/list` pages through persisted thread items, optionally restricted to one turn.
L479: - `thread/list` supports cursor pagination plus `modelProviders`, `sourceKinds`, `archived`, `isPinned`, `cwd`, `useStateDbOnly`, `searchTerm`, and experimental `parentThreadId` or `ancestorThreadId` filtering.
L480: - `thread/loaded/list` returns the thread IDs currently in memory.
L481: - `thread/archive` moves the thread's persisted JSONL log into the archived directory and attempts to archive spawned descendant thread logs that aren't already archived.
L482: - `thread/delete` permanently deletes a persisted active or archived thread and its spawned descendant threads.
L483: - `thread/metadata/update` patches stored thread metadata, including persisted `gitInfo` and `isPinned`.
L484: - `thread/unsubscribe` unsubscribes the current connection from a loaded thread and can trigger `thread/closed` after an inactivity grace period.
L485: - `thread/unarchive` restores an archived thread rollout back into the active sessions directory.
L486: - `thread/compact/start` triggers compaction and returns `{}` immediately.
L487: - `thread/revert` removes a specified turn and every later turn from a persistent paginated thread's history. It doesn't change local files.
L488: - `thread/inject_items` appends raw Responses API items to a loaded thread's model-visible history without starting a user turn.
L489: 
L874: ### Trigger thread compaction
L875: 
L876: Use `thread/compact/start` to trigger manual history compaction for a thread. The request returns immediately with `{}`.
L877: 
L878: App-server emits progress as standard `turn/*` and `item/*` notifications on the same `threadId`, including a `contextCompaction` item lifecycle (`item/started` then `item/completed`).
L879: 
L880: ```json
L881: { "method": "thread/compact/start", "id": 25, "params": { "threadId": "thr_b" } }
L882: { "id": 25, "result": {} }
L883: ```

L964: ## Turns
L965: 
L966: The `input` field accepts a list of items:
L967: 
L968: - `{ "type": "text", "text": "Explain this diff" }`
L969: - `{ "type": "image", "url": "https://.../design.png" }`
L970: - `{ "type": "localImage", "path": "/tmp/screenshot.png" }`
L971: 
L972: You can override configuration settings per turn (model, effort, `cwd`, sandbox policy, summary). When specified, these settings become the defaults for later turns on the same thread. `outputSchema` applies only to the current turn. For `sandboxPolicy.type = "externalSandbox"`, set `networkAccess` to `restricted` or `enabled`; for `workspaceWrite`, `networkAccess` remains a boolean.
L973: 
L974: For `turn/start.collaborationMode`, `settings.developer_instructions: null` means "use built-in instructions for the selected mode" rather than clearing mode instructions.
L975:

L1019:   "input": [ { "type": "text", "text": "Run tests" } ],
L1020:   "cwd": "/Users/me/project",
L1021:   "approvalPolicy": "unlessTrusted",
L1022:   "sandboxPolicy": {

L1024:     "writableRoots": ["/Users/me/project"],
L1025:     "networkAccess": true
L1026:   },
L1027:   "model": "gpt-6.1-sol",
L1028:   "effort": "medium",
L1029:   "summary": "concise",
L1030:   "personality": "friendly",
L1031:   "outputSchema": {
L1032:     "type": "object",
L1033:     "properties": { "answer": { "type": "string" } },
L1034:     "required": ["answer"],
L1035:     "additionalProperties": false
L1036:   }

L1043: with a nonempty `name`, an optional `namespace`, and an `output` string or
L1044: array of content items. Set `input` to an empty array; you can't combine
L1045: `toolOutput` with nonempty user input.
L1046: 
L1047: ```json
L1048: {
L1049:   "method": "turn/start",
L1050:   "id": 31,
L1051:   "params": {
L1052:     "threadId": "thr_123",
L1053:     "input": [],
L1054:     "toolOutput": {
L1055:       "name": "run_tests",
L1056:       "namespace": null,
L1057:       "output": "All 42 tests passed."
L1058:     }
L1059:   }
L1060: }
L1061: ```
L1062: 
L1063: The output remains tool output in the conversation and appears as a
L1064: `functionCallOutput` item in notifications and persisted history. If a regular
L1065: turn is already active, Codex queues the output for that turn.

L1085: ### Steer an active turn
L1086: 
L1087: Use `turn/steer` to append more user input to the active in-flight turn.
L1088: 
L1089: - Include `expectedTurnId`; it must match the active turn id.
L1090: - The request fails if there is no active turn on the thread.
L1091: - `turn/steer` doesn't emit a new `turn/started` notification.
L1092: - `turn/steer` doesn't accept turn-level overrides (`model`, `cwd`, `sandboxPolicy`, or `outputSchema`).
L1093: 
L1094: ```json
L1095: { "method": "turn/steer", "id": 32, "params": {
L1096:   "threadId": "thr_123",
L1097:   "input": [ { "type": "text", "text": "Actually focus on failing tests first." } ],
L1098:   "expectedTurnId": "turn_456"
L1099: } }
L1100: { "id": 32, "result": { "turnId": "turn_456" } }
L1101: ```

L1119:

L1328: ## Events
L1329: 
L1330: Event notifications are the server-initiated stream for thread lifecycles, turn lifecycles, and the items within them. After you start or resume a thread, keep reading the active transport stream for `thread/started`, `thread/archived`, `thread/unarchived`, `thread/closed`, `thread/status/changed`, `turn/*`, `item/*`, and `serverRequest/resolved` notifications.
L1331: 
L1332: ### Notification opt-out
L1333: 
L1334: Clients can suppress specific notifications per connection by sending exact method names in `initialize.params.capabilities.optOutNotificationMethods`.
L1335: 
L1336: - Exact-match only: `item/agentMessage/delta` suppresses only that method.
L1337: - Unknown method names are ignored.
L1338: - Applies to the current `thread/*`, `turn/*`, `item/*`, and related v2 notifications.
L1339: - Doesn't apply to requests, responses, or errors.
L1340: 
L1341: ### Fuzzy file search events (experimental)
L1342: 
L1343: The fuzzy file search session API emits per-query notifications:
L1344: 
L1345: - `fuzzyFileSearch/sessionUpdated` - `{ sessionId, query, files }` with the current matches for the active query.
L1346: - `fuzzyFileSearch/sessionCompleted` - `{ sessionId }` once indexing and matching for that query completes.
L1347: 
L1348: ### Warning events
L1349: 
L1350: - `configWarning` - `{ summary, details?, path?, range? }` for recoverable
L1351:   configuration or initialization problems.
L1352: - `warning` - `{ threadId?, message }` for non-fatal runtime warnings.
L1353: 
L1354: ### Windows sandbox setup events
L1355: 
L1356: - `windowsSandbox/setupCompleted` - `{ mode, success, error }` emitted after a `windowsSandbox/setupStart` request finishes.
L1357: 
L1358: ### Turn events
L1359: 
L1360: - `turn/started` - `{ turn }` with the turn id, empty `items`, and `status: "inProgress"`.
L1361: - `turn/completed` - `{ turn }` where `turn.status` is `completed`, `interrupted`, or `failed`; failures carry `{ error: { message, codexErrorInfo?, additionalDetails? } }`.
L1362: - `turn/diff/updated` - `{ threadId, turnId, diff }` with the latest aggregated unified diff across every file change in the turn.
L1363: - `turn/plan/updated` - `{ turnId, explanation?, plan }` whenever the agent shares or changes its plan; each `plan` entry is `{ step, status }` with `status` in `pending`, `inProgress`, or `completed`.
L1364: - `hook/started` and `hook/completed` - `{ threadId, turnId?, run }` when a synchronous lifecycle hook starts and when its final run summary is available. These notifications aren't emitted for asynchronous hooks.
L1365: - `model/safetyBuffering/updated` - `{ threadId, turnId, model, useCases, reasons, showBufferingUi, fasterModel }` when a response enters transient safety buffering.
L1366: - `model/rerouted` - `{ threadId, turnId, fromModel, toModel, reason }` when the service routes a request to another model.
L1367: - `model/verification` - `{ threadId, turnId, verifications }` when the service requires additional account verification.
L1368: - `thread/tokenUsage/updated` - usage updates for the active thread.
L1369: 
L1370: `turn/diff/updated` and `turn/plan/updated` currently include empty `items` arrays even when item events stream. Use `item/*` notifications as the source of truth for turn items.
L1371: 
L1372: ### Items
L1373: 
L1374: `ThreadItem` is the tagged union carried in turn responses and `item/*` notifications. Common item types include:
L1375: 
L1376: - `userMessage` - `{id, content}` where `content` is a list of user inputs (`text`, `image`, or `localImage`).
L1377: - `functionCallOutput` - `{id, name, namespace, output}` for standalone tool output supplied through `turn/start.toolOutput`. `namespace` can be `null`.
L1378: - `agentMessage` - `{id, text, phase?}` containing the accumulated agent reply. When present, `phase` uses Responses API wire values (`commentary`, `partial_answer`, `final_answer`). A `partial_answer` is stable answer text that may be followed by more output or tools.
L1379: - `plan` - `{id, text}` containing proposed plan text in plan mode. Treat the final `plan` item from `item/completed` as authoritative.
L1380: - `reasoning` - `{id, summary, content}` where `summary` holds streamed reasoning summaries and `content` holds raw reasoning blocks.
L1381: - `commandExecution` - `{id, command, cwd, status, commandActions, aggregatedOutput?, exitCode?, durationMs?}`.
L1382: - `fileChange` - `{id, changes, status}` describing proposed edits; `changes` list `{path, kind, diff}`.
L1383: - `mcpToolCall` - `{id, server, tool, status, arguments, appContext?, pluginId?, result?, error?}`. For trusted MCP apps, `appContext` can include `connectorId`, `linkId`, `resourceUri`, `appName`, `templateId`, and the stable connector `actionName`. Older persisted items can omit newer metadata. Use `appContext.resourceUri` instead of the deprecated top-level `mcpAppResourceUri`.
L1384: - `dynamicToolCall` - `{id, tool, arguments, status, contentItems?, success?, durationMs?}` for client-executed dynamic tool invocations.
L1385: - `collabToolCall` - `{id, tool, status, senderThreadId, receiverThreadId?, newThreadId?, prompt?, agentStatus?}`.
L1386: - `webSearch` - `{id, query, action?}` for web search requests issued by the agent.
L1387: - `imageView` - `{id, path}` emitted when the agent invokes the image viewer tool.
L1388: - `enteredReviewMode` - `{id, review}` sent when the reviewer starts.
L1389: - `exitedReviewMode` - `{id, review}` emitted when the reviewer finishes.
L1390: - `contextCompaction` - `{id}` emitted when Codex compacts the conversation history.
L1391: 
L1392: For `webSearch.action`, the action `type` can be `search` (`query?`, `queries?`), `openPage` (`url?`), or `findInPage` (`url?`, `pattern?`).
L1393: 
L1394: The app server deprecates the legacy `thread/compacted` notification; use the `contextCompaction` item instead.
L1395: 
L1396: All items emit two shared lifecycle events:
L1397: 
L1398: - `item/started` - emits the full `item` when a new unit of work begins; the `item.id` matches the `itemId` used by deltas.
L1399: - `item/completed` - sends the final `item` once work finishes; treat this as the authoritative state.
L1400: 
L1401: ### Item deltas
L1402: 
L1403: - `item/agentMessage/delta` - appends streamed text for the agent message.
L1404: - `item/plan/delta` - streams proposed plan text. The final `plan` item may not exactly equal the concatenated deltas.
L1405: - `item/reasoning/summaryTextDelta` - streams readable reasoning summaries; `summaryIndex` increments when a new summary section opens.
L1406: - `item/reasoning/summaryPartAdded` - marks a boundary between reasoning summary sections.
L1407: - `item/reasoning/textDelta` - streams raw reasoning text (when supported by the model).
L1408: - `item/commandExecution/outputDelta` - streams stdout/stderr for a command; append deltas in order.
L1409: - `item/fileChange/outputDelta` - deprecated compatibility notification for legacy `apply_patch` text output. Current app-server versions no longer emit it; use `fileChange` items and `turn/diff/updated` instead.

L1411: ## Errors
L1412: 
L1413: If a turn fails, the server emits an `error` event with `{ error: { message, codexErrorInfo?, additionalDetails? } }` and then finishes the turn with `status: "failed"`. When an upstream HTTP status is available, it appears in `codexErrorInfo.httpStatusCode`.
L1414: 
L1415: Common `codexErrorInfo` values include:
L1416: 
L1417: - `ContextWindowExceeded`
L1418: - `UsageLimitExceeded`
L1419: - `HttpConnectionFailed` (4xx/5xx upstream errors)
L1420: - `ResponseStreamConnectionFailed`
L1421: - `ResponseStreamDisconnected`
L1422: - `ResponseTooManyFailedAttempts`
L1423: - `BadRequest`, `Unauthorized`, `SandboxError`, `InternalServerError`, `Other`
L1424: 
L1425: When an upstream HTTP status is available, the server forwards it in `httpStatusCode` on the relevant `codexErrorInfo` variant.
L1427: ## Approvals
L1428: 
L1429: Depending on a user's Codex settings, command execution and file changes may require approval. The app-server sends a server-initiated JSON-RPC request to the client, and the client responds with a decision payload.
L1430: 
L1431: - Command execution decisions: `accept`, `acceptForSession`, `decline`, `cancel`, or `{ "acceptWithExecpolicyAmendment": { "execpolicy_amendment": ["cmd", "..."] } }`.
L1432: - File change decisions: `accept`, `acceptForSession`, `decline`, `cancel`.
L1433: 
L1434: - Requests include `threadId` and `turnId` - use them to scope UI state to the active conversation.
L1435: - The server resumes or declines the work and ends the item with `item/completed`.
L1436: 
L1437: ### Command execution approvals
L1438: 
L1439: Order of messages:
L1440: 
L1441: 1. `item/started` shows the pending `commandExecution` item with `command`, `cwd`, and other fields.
L1442: 2. `item/commandExecution/requestApproval` includes `itemId`, `threadId`, `turnId`, optional `reason`, optional `command`, optional `cwd`, optional `commandActions`, optional `proposedExecpolicyAmendment`, optional `networkApprovalContext`, and optional `availableDecisions`. When `initialize.params.capabilities.experimentalApi = true`, the payload can also include experimental `additionalPermissions` describing requested per-command sandbox access. Any filesystem paths inside `additionalPermissions` are absolute on the wire.
L1443: 3. Client responds with one of the command execution approval decisions above.
L1444: 4. `serverRequest/resolved` confirms that the pending request has been answered or cleared.
L1445: 5. `item/completed` returns the final `commandExecution` item with `status: completed | failed | declined`.
L1446: 
L1447: When `networkApprovalContext` is present, the prompt is for managed network access (not a general shell-command approval). The current v2 schema exposes the target `host` and `protocol`; clients should render a network-specific prompt and not rely on `command` being a user-meaningful shell command preview.
L1448: 
L1449: Codex groups concurrent network approval prompts by destination (`host`, protocol, and port). The app-server may therefore send one prompt that unblocks multiple queued requests to the same destination, while different ports on the same host are treated separately.
L1450: 
L1451: ### File change approvals
L1452: 
L1453: Order of messages:
L1454: 
L1455: 1. `item/started` emits a `fileChange` item with proposed `changes` and `status: "inProgress"`.
L1456: 2. `item/fileChange/requestApproval` includes `itemId`, `threadId`, `turnId`, optional `reason`, and optional `grantRoot`.
L1457: 3. Client responds with one of the file change approval decisions above.
L1458: 4. `serverRequest/resolved` confirms that the pending request has been answered or cleared.
L1459: 5. `item/completed` returns the final `fileChange` item with `status: completed | failed | declined`.
