# Codex 如何把一次请求变成可持续的工作

截至2026年10月22日的给定材料，Codex的核心架构是模型与工具之间的执行系统，即Harness。模型根据上下文判断下一步，Harness维护会话、组织工具调用、执行权限策略并传递进度；客户端提供任务入口、业务上下文和审批界面，执行环境承载命令与文件。开源的是Harness及相关集成组件，模型访问和托管服务另有边界。理解这些分工，才能判断产品能力取决于哪里、故障该由谁处理。〔S1：L7–37〕

以“修复仓库中的一个缺陷”为例，本地app-server客户端先初始化连接，再创建或恢复thread，以`turn/start`提交任务。thread承载会话，turn承载一次请求后的工作，item记录消息、命令、文件修改或工具调用。模型结合输入与检索到的代码提出行动，工具在对应环境执行，结果回到上下文，支持下一步修改、验证或修复。这条反馈循环让任务能够随实际错误调整，而不只依靠最初描述。〔S2：L194–209；S5：L44–62〕

客户端也参与执行闭环：它接收文本增量、工具进度和文件差异，遇到适用的审批请求返回决策，最终接收轮次状态。`item/completed`给出该工作项的最终状态，`turn/completed`则可能是完成、中断或失败。因此，界面应区分“还在输出”“等待决策”和“执行结束”；协议的完成状态本身不能证明缺陷已修好，产品仍需验收条件。后者是依据事件语义作出的设计判断。〔S2：L1360–1399、L1427–1459〕

上下文还包括按需加载的方法。Skills把说明、资源和可选脚本封装成工作流；Codex先看到名称、描述和路径，选用时再读取完整`SKILL.md`。初始目录默认最多使用上下文窗口的2%，技能过多可能截短描述甚至省略条目；该预算不限制选中技能全文。我的判断是，这能控制常驻上下文开销，但将准确发现方法的责任部分交给描述和调用入口。显式指定技能及其输入项有助于明确选择，不能据此保证方法总被正确执行。〔S3：L33–48、L91–103；S2：L1512–1514〕

跨轮接续涉及三种状态：持久保存的会话记录、模型当下可用的上下文，以及仓库和状态文件。app-server允许恢复或分叉thread，也允许在运行中用`turn/steer`补充输入；历史压缩另有接口和事件。恢复记录不代表全部历史始终装入模型窗口，也没有材料证明压缩无损。尤其是`thread/revert`只撤回会话历史，不改变本地文件，产品需要分别处理会话恢复与成果回滚。〔S2：L474–488、L874–878、L1085–1092〕

长任务因而需要可重读的目标、约束、里程碑和验证结果。历史案例中，作者让GPT-5.3-Codex以Extra High推理、完全访问权限从空仓库开发设计工具，报告约25小时、1,300万tokens及3万行代码；规格、计划和状态写入文件，迭代中持续验证。作者同时承认产物未达生产就绪。这支持“持久状态与反馈有助于接续”的解释，不能作为当前各版本成功率、生产质量或费用的估计，也无法分离模型、Harness和任务设计各自的贡献。〔S5：L7–9、L79–83、L162、L177–185〕

部署选择还要把Harness位置与执行环境位置分开。Agents API由OpenAI运行Harness并维护会话；它可以没有计算环境，也可以连接托管或自备环境。自备执行环境并不意味着Harness也由用户托管。下表的责任来自文档，选型含义是本文分析。〔S6：L5–31、L50–81〕

| 使用方式 | 职责与能力边界 | 对产品设计的含义 |
| --- | --- | --- |
| CLI的`codex exec`／SDK | 前者运行有界非交互任务；后者提供启动、恢复、流式访问接口 | 脚本和CI可从较薄的集成开始；不能据此假定托管了计算 |
| 本地app-server | 本地进程提供会话、工具循环和审批协议；应用拥有界面、业务规则与工具 | 适合深度交互；团队需接好事件、审批及本地运行环境 |
| Agents API，无环境 | 托管Harness可调用远程MCP或应用处理的函数工具；无内建Bash、文件工作区 | 服务查询可减少环境管理；文件编辑能力需要另行提供 |
| Agents API，托管环境 | OpenAI创建和管理沙箱；应用配置依赖、文件及网络 | 适合需要计算和产物的任务；仍需处理业务工具和事件 |
| Agents API，自备环境 | 托管Harness通过executor执行；应用负责供给、重连、关闭和文件保留 | 可接私网及定制软件，同时承担环境生命周期工作 |

表据S1：L39–49、L67–78；S6：L15–31、L50–54、L75–109。托管服务支持流式事件或webhook，但函数工具处理器不可用时，Agent仍可能等待结果；“会话托管”没有消除应用端故障。〔S6：L102–109〕

权限设计直接影响自治程度和中断体验。沙箱规定技术上能做什么，审批规定何时需要放行；关闭审批提示仍可保留沙箱限制。本地CLI／IDE默认命令禁网和工作区写入限制，不能推广成所有形态的通则：命令网络代理也不覆盖模型请求、MCP、搜索等连接。自动审批把合资格请求交给审查Agent，能减少人工介入，却增加模型调用；超时或审查解析失败时动作仍不执行。其成本与可靠性须分别评估。〔S4：L59–74、L246–253、L300–357〕

对Agent产品团队，我的建议是先确定交互方式、所需数据与动作、文件计算和验收条件，再选择入口及责任分配。成本评估应同时计入模型调用、执行环境、应用运维、人工等待和失败修复；渐进加载、持久状态与审批自动化改变的是这些成本之间的分配，材料不足以证明哪种组合总体最便宜。长时间运行的价值，应由可验收成果衡量，而非运行时长或代码量。

本文仅据六份官方材料的所给摘录综合分析，未访问省略页面或进行性能实测；案例效果属于作者报告，缺少跨形态的可比成本与可靠性数据，也不足以揭示闭源内部实现。
