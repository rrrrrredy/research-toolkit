L5: Codex helps protect your code and data and reduces the risk of misuse.
L6: 
L7: This page covers how to operate Codex safely, including sandboxing, approvals,
L8:   and network access. If you are looking for Codex Security, the product for
L9:   scanning connected GitHub repositories, see [Codex Security](https://learn.chatgpt.com/docs/security).
L10: 
L11: By default, the agent runs with network access turned off. Locally, Codex uses an OS-enforced sandbox that limits what it can touch (typically to the current workspace), plus an approval policy that controls when it must stop and ask you before acting.
L12: 
L13: For a high-level explanation of how sandboxing works across the ChatGPT desktop app,
L14: Codex CLI, and IDE extension, see [sandboxing](https://learn.chatgpt.com/docs/sandboxing).
L15: For a broader enterprise security overview, see the [Codex security white paper](https://trust.openai.com/?itemUid=382f924d-54f3-43a8-a9df-c39e6c959958&source=click).
L48: ## Sandbox and approvals
L49: 
L50: Local computer access with Work Cloud has separate local and cloud execution policies:
L51: 
L52: - **Cloud execution:** Work cloud containers use existing Work Cloud policies.
L53: - **Local execution:** Local execution requirements govern the connected computer. MDM and legacy managed-device requirements take precedence over Agent Security, which takes precedence over the device's system requirements file.
L54: 
L55: For Work with local access and dots, supported Global policy applies to the shared cloud orchestrator when managed policy is enabled. Work cloud containers and dots cloud computers use their own execution configuration and requirements. Test local and cloud controls separately. Keep orchestrator controls, including approvals and web search, in Global. Use the dedicated Allowed approval policies and Allowed web search modes controls where available, and TOML for other supported fields. Check the [Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference) for the field list and execution scope before applying a Codex example to Local computer access with Work Cloud.
L56: 
L57: Moving between desktop, web, and mobile does not grant access to another computer. Before enabling sync or expanding access, review the Agent Security baseline and test an allowed and a blocked action in each execution environment. See [Managed configuration](https://learn.chatgpt.com/docs/enterprise/managed-configuration).
L58: 
L59: Codex security controls come from two layers that work together:
L60: 
L61: - **Sandbox mode**: What Codex can do technically (for example, where it can write and whether it can reach the network) when it executes model-generated commands.
L62: - **Approval policy**: When Codex must ask you before it executes an action (for example, leaving the sandbox, using the network, or running commands outside a trusted set).
L63: 
L64: Codex uses different sandbox modes depending on where you run it:
L65: 
L66: - **[Codex Cloud (Legacy)](https://learn.chatgpt.com/docs/environments/cloud-environment)**: Runs in isolated OpenAI-managed containers, preventing access to your host system or unrelated data. Uses a two-phase runtime model: setup runs before the agent phase and can access the network to install specified dependencies, then the agent phase runs offline by default unless you enable internet access for that environment. Secrets configured for cloud environments are available only during setup and are removed before the agent phase starts.
L67: - **Current Codex Cloud**: See [environment variables and network secrets](https://learn.chatgpt.com/docs/environments/cloud-environments#environment-variables-and-secrets) for how credentials are handled during setup and tasks.
L68: - **Codex CLI / IDE extension**: OS-level mechanisms enforce sandbox policies. Defaults include no network access and write permissions limited to the active workspace. You can configure the sandbox, approval policy, and network settings based on your risk tolerance.
L69: 
L70: In the `Auto` preset (for example, `--sandbox workspace-write --ask-for-approval on-request`), Codex can read files, make edits, and run commands in the working directory automatically.
L71: 
L72: Codex asks for approval to edit files outside the workspace or to run commands that require network access. If you want to chat or plan without making changes, switch to `read-only` mode with the `/permissions` command.
L73: 
L74: Codex can also elicit approval for app (connector) tool calls that advertise side effects, even when the action isn't a shell command or file change. Destructive app/MCP tool calls always require approval when the tool advertises a destructive annotation (unless the tool advertises a read annotation, which takes priority).

L246: ### Traffic outside the command network proxy
L247: 
L248: The network proxy filters scripts, programs, and child processes that run
L249: inside the local command sandbox. It does not filter web search, app or
L250: connector tool calls, MCP server connections, browser or Computer Use activity,
L251: Codex cloud tasks, or the client's model and authentication requests. These
L252: surfaces use separate service connections, feature settings, workspace
L253: policies, or environment controls.
L254: 
L255: Browser tools separately check managed network denies and exclusive allowlists
L256: before accessing an origin. Browser origin policies can further restrict site
L257: access, uploads, downloads, and developer tools. See
L258: [managed browser controls](https://learn.chatgpt.com/docs/enterprise/managed-configuration#control-browser-and-computer-use).
L259: 
L260: For managed users, combine command network policy with controls such as
L261: `allowed_web_search_modes`, approved `mcp_servers`, and feature requirements
L262: for apps, plugins, browsers, or Computer Use. See
L263: [Managed configuration](https://learn.chatgpt.com/docs/enterprise/managed-configuration).
L264: 
L265: You can also control the [web search tool](https://platform.openai.com/docs/guides/tools-web-search) without granting full network access to spawned commands. Codex defaults to using a web search cache to access results. The cache is an OpenAI-maintained index of web results, so cached mode returns pre-indexed results instead of fetching live pages. This reduces exposure to prompt injection from arbitrary live content. Treat web results as untrusted. If you are using `--yolo` or another [full access sandbox setting](#common-sandbox-and-approval-combinations), web search defaults to live results. Use `--search` or set `web_search = "live"` to allow live browsing, or set it to `"disabled"` to turn the tool off:
L266: 
L267: ```toml
L268: web_search = "cached"  # default
L269: # web_search = "disabled"
L270: # web_search = "live"  # same as --search
L271: ```
L272: 
L273: Set `web_search = "indexed"` when external web access should be gated by the
L274: search index. Use caution when enabling network access or web search in Codex.
L275: Prompt injection can cause the agent to fetch and follow untrusted instructions.

L277: ## Defaults and recommendations
L278: 
L279: - On launch, Codex detects whether the folder is version-controlled and recommends:
L280:   - Version-controlled folders: `Auto` (workspace write + on-request approvals)
L281:   - Non-version-controlled folders: `read-only`
L282: - Depending on your setup, Codex may also start in `read-only` until you explicitly trust the working directory (for example, via an onboarding prompt or `/permissions`).
L283: - The workspace includes the current directory and temporary directories like `/tmp`. Use the `/status` command to see which directories are in the workspace.
L284: - To accept the defaults, run `codex`.
L285: - You can set these explicitly:
L286:   - `codex --sandbox workspace-write --ask-for-approval on-request`
L287:   - `codex --sandbox read-only --ask-for-approval on-request`
L288: 
L289: ### Protected paths in writable roots
L290: 
L291: In the default `workspace-write` sandbox policy, writable roots still include protected paths:
L292: 
L293: - `<writable_root>/.git` is protected as read-only whether it appears as a directory or file.
L294: - If `<writable_root>/.git` is a pointer file (`gitdir: ...`), the resolved Git directory path is also protected as read-only.
L295: - `<writable_root>/.agents` is protected as read-only when it exists as a directory.
L296: - `<writable_root>/.codex` is protected as read-only when it exists as a directory.
L297: - `<writable_root>/.aws` is protected as read-only when it exists as a directory.
L298: - Protection is recursive, so everything under those paths is read-only.
L299: 
L300: ### Run without approval prompts
L301: 
L302: You can disable approval prompts with `--ask-for-approval never` or `-a never` (shorthand).
L303: 
L304: This option works with all `--sandbox` modes, so you still control Codex's level of autonomy. Codex makes a best effort within the constraints you set.
L305: 
L306: If you need Codex to read files, make edits, and run commands with network access without approval prompts, use `--sandbox danger-full-access` (or the `--dangerously-bypass-approvals-and-sandbox` flag). Use caution before doing so.
L307: 
L308: For a middle ground, `approval_policy = { granular = { ... } }` lets you keep specific approval prompt categories interactive while automatically rejecting others. The granular policy covers sandbox approvals, execpolicy-rule prompts, MCP prompts, `request_permissions` prompts, and skill-script approvals.
L309: 
L310: ### Automatic approval reviews
L311: 
L312: By default, approval requests route to you:
L313: 
L314: ```toml
L315: approvals_reviewer = "user"
L316: ```
L317: 
L318: Automatic approval reviews apply when approvals are interactive, such as
L319: `approval_policy = "on-request"` or a granular approval policy. Set
L320: `approvals_reviewer = "auto_review"` to route eligible approval requests
L321: through a reviewer agent before Codex runs the request:
L322: 
L323: ```toml
L324: approval_policy = "on-request"
L325: approvals_reviewer = "auto_review"
L326: ```
L327: 
L328: For the full reviewer lifecycle, trigger conditions, configuration precedence,
L329: and failure behavior, see
L330: [Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review).
L331: 
L332: The reviewer evaluates only actions that already need approval, such as sandbox
L333: escalations, blocked network requests, `request_permissions` prompts, or
L334: side-effecting app and MCP tool calls. Actions that stay inside the sandbox
L335: continue without an extra review step.
L336: 
L337: The reviewer policy checks for data exfiltration, credential probing, persistent
L338: security weakening, and destructive actions. Low-risk and medium-risk actions
L339: can proceed when policy allows them. The policy denies critical-risk actions.
L340: High-risk actions require enough user authorization and no matching deny rule.
L341: Prompt-build, review-session, and parse failures fail closed. Timeouts are
L342: surfaced separately, but the action still does not run.
L343: 
L344: The [default reviewer policy](https://github.com/openai/codex/blob/main/codex-rs/core/src/guardian/policy.md)
L345: is in the open-source Codex repository. Enterprises can replace its
L346: tenant-specific section with `guardian_policy_config` in managed requirements.
L347: Local `[auto_review].policy` text is also supported, but managed requirements
L348: take precedence. For setup details, see
L349: [Managed configuration](https://learn.chatgpt.com/docs/enterprise/managed-configuration#configure-automatic-review-policy).
L350: 
L351: In the ChatGPT desktop app, these reviews appear as automatic review items with a status
L352: such as Reviewing, Approved, Denied, Aborted, or Timed out. They can also
L353: include a risk level and user-authorization assessment for the reviewed
L354: request.
L355: 
L356: Automatic review uses extra model calls, so it can add to Codex usage. Admins
L357: can constrain it with `allowed_approvals_reviewers`.

L359: ### Common sandbox and approval combinations
L360: 
L361: | Intent                         | Flags / config                                                                                                                      | Effect                                                                                                                                           |
L362: | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
L363: | Auto (preset)                  | _no flags needed_ or `--sandbox workspace-write --ask-for-approval on-request`                                                      | Codex can read files, make edits, and run commands in the workspace. Codex requires approval to edit outside the workspace or to access network. |
L364: | Safe read-only browsing        | `--sandbox read-only --ask-for-approval on-request`                                                                                 | Codex can read files and run commands within the read-only sandbox. Actions outside the sandbox can require approval.                            |
L365: | Read-only non-interactive (CI) | `--sandbox read-only --ask-for-approval never`                                                                                      | Codex can read files and run commands within the read-only sandbox; it never asks for approval.                                                  |
L366: | Auto-review mode               | `--sandbox workspace-write --ask-for-approval on-request -c approvals_reviewer=auto_review` or `approvals_reviewer = "auto_review"` | Same sandbox boundary as standard on-request mode, but eligible approval requests are reviewed by Auto-review instead of surfacing to the user.  |
L367: | Dangerous full access          | `--dangerously-bypass-approvals-and-sandbox` (alias: `--yolo`)                                                                      | <ElevatedRiskBadge /> No sandbox; no approvals _(not recommended)_                                                                               |
L368: 
L369: For non-interactive runs, use `codex exec --sandbox workspace-write`.

L424: ## OS-level sandbox
L425: 
L426: Codex enforces the sandbox differently depending on your OS:
L427: 
L428: - **macOS** uses Seatbelt policies and runs commands using `sandbox-exec` with a profile (`-p`) that corresponds to the `--sandbox` mode you selected. When restricted read access enables platform defaults, Codex appends a curated macOS platform policy (instead of broadly allowing `/System`) to preserve common tool compatibility.
L429: - **Linux** uses `bwrap` plus `seccomp` by default.
L430: - **Windows** supports [MXC](https://learn.chatgpt.com/docs/windows/windows-sandbox#windows-sandbox), with `elevated` and `unelevated` as legacy fallbacks. In [Windows Subsystem for Linux 2 (WSL2)](https://learn.chatgpt.com/docs/windows/wsl), Codex uses the Linux sandbox implementation. WSL1 was supported through Codex `0.114`; starting in `0.115`, the Linux sandbox moved to `bwrap`, so WSL1 is no longer supported.
L431: 
L432: If you use the Codex IDE extension on Windows, it supports WSL2 directly. Set the following in your VS Code settings to keep the agent inside WSL2 whenever it's available:
L433: 
L434: ```json
L435: {
L436:   "chatgpt.runCodexInWindowsSubsystemForLinux": true
L437: }
L438: ```
L439: 
L440: This ensures the IDE extension inherits Linux sandbox semantics for commands, approvals, and filesystem access even when the host OS is Windows. Learn more in the [WSL guide](https://learn.chatgpt.com/docs/windows/wsl).
L441: 
L442: When running on Windows, prefer MXC when the device and policy support it by setting this in `config.toml`:
L443: 
L444: ```toml
L445: [features]
L446: prefer_mxc = true
L447: ```
L448: 
L449: Keep a permitted legacy implementation in `windows.sandbox` for fallback. See the [Windows setup guide](https://learn.chatgpt.com/docs/windows/windows-sandbox#enable-mxc) for configuration and compatibility limits.
L450: 
L451: When you run Linux in a containerized environment such as Docker, the sandbox may not work if the host or container configuration blocks the namespace, setuid `bwrap`, or `seccomp` operations that Codex needs.
L452: 
L453: In that case, configure your Docker container to provide the isolation you need, then run `codex` with `--sandbox danger-full-access` (or the `--dangerously-bypass-approvals-and-sandbox` flag) inside the container.
