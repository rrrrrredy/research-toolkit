# 国内办公 Agent：从生成文件到接续工作

信息截止：2026 年 11 月 5 日。面向 AI 产品与企业办公负责人。

国内办公 Agent 的竞争，已经从首次生成延伸到同一对象上的持续工作。Kimi Work 增加选区修改、Office 历史版本与在线文档双写；灵犀将文字／表格双写、团队和项目云模式接入工作台；WorkBuddy 用资料库连接保存、修订与发布。扣子组织不同运行环境中的 Agent 参与项目，豆包工作借助飞书身份使用组织资料，悟空把电脑执行接到钉钉文档、日程和审批上。独立工作台、桌面执行与办公套件正在交叉，按互不重叠的产品阵营选型，已经难以解释这些差异。[Kimi 发布日志](https://www.kimi.com/help/kimi-work/release-notes)、[灵犀产品文档](https://www.lingxi.cn/docs)、[WorkBuddy 资料库](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Library)

**采用时，先确定材料在哪里、最终改变哪个对象、谁能确认工作结束。** 本机目录中的文件处理，重点是访问与编辑；组织资料上的协作，重点是身份和对象权限的延续；无人值守任务，重点是执行环境、触发与中断后的接续。产品负责人则应关注另一条连续链路：用户能否指出改动位置，修改能否保存，Agent 能否读回新版本，下一位同事能否接着使用成果。

### 共同证据范围

本文沿用截至截止日已取得的官方帮助、更新、权限和计费文档，以及具有输入与过程描述的公开使用记录。官方文档用于说明产品提供的功能、运行机制与商业条件，安全机制也按厂商说明引用；公开记录用于讨论对应账号、版本和材料上的操作。本文没有安装产品实测，未下载重算花叔的配套文件，也未取得光子星球体验的原测试文件；相关文件修改结果继续按作者的操作叙述引用。

现有资料没有同输入、同权限、同完成标准的跨产品对照，因此不作成功率、稳定性或净人效排名。模型基准、历史修复条目和厂商采用人数，分别保留其原有含义，不换算成办公任务完成率、当前故障率或生产率。恢复功能按能恢复的对象与条件比较，节省多少返工仍缺少相应测量。日期明确的材料按对应版本使用；持续维护的页面按截止日可见内容使用，不将全部内容倒推为页面首发时的能力。

## 二、按工作对象定义“完成”

以销售月报为例，Agent 可以先读取销售表，生成分析与演示文稿，再把修正写回团队台账，最后把汇报发到群里。一条自然语言任务由此跨越三种结果，各自需要不同的完成依据。

| 工作对象 | 具体结果 | 完成依据 | 修改或失败后怎样处理 |
| --- | --- | --- | --- |
| **新文件** | 新建报告、表格、PPT、页面 | 实际文件可以打开；数字、公式、图表和内容符合输入与用途 | 可以另存或重做，检查重点在交付文件本身 |
| **既有对象** | 修改原销售表、现有文档、共享知识条目 | 指定位置已改变，未指定的内容与必要属性保留；保存后能继续编辑与协作 | 确认写入的是原对象还是副本，核对保留了谁的修改，并找到需要恢复的版本 |
| **业务状态** | 发送通知、提交审批、更新记录、公开发布 | 接收方或业务系统显示目标状态，动作由适当身份完成；审批提交与审批通过分别定义结束状态 | 重跑前查清哪些动作已经生效，再决定补做哪一步或交由负责人处理 |

这是一种任务划分，而非产品等级。浏览器操作也可能改变业务状态，套件内的 Agent 也可能只生成新文件。具体入口、工具与权限，共同决定任务能走到哪一个结束位置。

对于持续使用的文件，“可编辑”包含比外观更多的要求。如果表格公式被静态数值替代，当次数字可以正确，下次修改输入却不再自动重算；如果图表成为图片，接手的同事就无法继续编辑图表数据。既有文件的验收因此需要覆盖改动之外的结构：原有公式、图表、链接、格式，以及工作所需的权限和协作关系。对这类对象，保留下一轮工作的起点，往往比缩短首次生成时间更重要。

## 三、六组产品分别接住了哪一段工作

### Kimi Work：围绕本地文件和在线文档持续修改

Kimi Work 的基本路径是在电脑客户端读取本地目录、运行代码、使用浏览器并产出办公文件。9 月的连续更新把修改与保存进一步纳入工作台：9 月 22 日允许选中 PPT、Excel、Word 或 Markdown 内容后提出修改；9 月 24 日增加 Office 文件历史版本；9 月 30 日加入飞书、Notion 文档双写、产物卡片，以及相关页面的评论编辑和问答。[产品介绍](https://www.kimi.com/help/kimi-work/overview)、[发布日志](https://www.kimi.com/help/kimi-work/release-notes)

这些功能分别处理持续编辑中的三个问题。选区向 Agent 传递修改位置，减少用户重新描述整份文件的需要；历史版本保留前后状态，方便回看改动；在线文档双写则把这一交互延伸到已连接的协作对象。对需要反复打磨报告、表格和演示文稿的用户，Kimi Work 的考察重点可以从初稿生成转向局部修改、保存和下一轮读取。涉及在线对象时，仍要按目标文档和插件授权确定实际操作范围。

运行条件对周期任务尤其重要。手机远程发指令或查看结果时，本地任务仍依赖桌面环境。官方 FAQ 明确，Work 桌面定时任务需要电脑与应用运行，休眠、关机或关闭应用期间错过的触发不会在下次启动时补跑。夜间整理本机文件，需要把设备在线纳入工作安排；Kimi 中另行创建的云端定时任务则采用另一条运行路径。[常见问题](https://www.kimi.com/help/kimi-work/kimi-work-faq)

### 扣子：让多人调度 Agent，同时保留执行环境的差别

扣子的特点是把不同 Agent 放进同一项目与对话入口。原生 Agent 内置日程、邮箱、云电脑等工作台能力，三方精选 Agent 与本地接入则使用不同的框架和资源。官方能力表列的是扣子工作台功能；本地接入文档另行明确，本地 Agent 可以处理本机文件、软件与代码，实际任务仍由用户电脑执行。[Agent 类型](https://docs.coze.cn/cozespace_agent_overview)、[本地 Agent](https://docs.coze.cn/cozespace_local_agent)

本地 Agent 加入项目后，项目成员可以共同下达指令。对于已经由技术人员维护的本地工具链，这提供了一条让其他同事参与使用的路径：团队不必每人各建一套执行环境，就能围绕同一个 Agent 提问和交办工作。相应地，那台机器、coze-bridge 连接程序、本地账号与工具权限也成为共同依赖，设备和连接维护仍需有人负责。

三方精选 Agent 运行在扣子云电脑中，不依赖本地电脑在线。其 Claude Code、Codex CLI 使用相应框架并搭配扣子提供的模型，未绑定原厂账号或模型。选择这条路径，得到的是扣子管理的云端执行资源和模型配置；本地接入则继续受本地服务方的账号、计费与运行规则约束。[三方精选 Agent](https://docs.coze.cn/cozespace_cloud_agent)

因此，两条路径的取舍主要在于是否需要延续已有环境。资料、工具和私有配置已在本机时，本地接入更便于复用；需要离开个人设备持续运行时，云端路径更相关，但输入资料、登录状态和目标系统必须在云端可达。统一协作入口解决了调度分散，执行资源的选择仍由任务决定。

### 飞书／豆包工作：让组织身份贯穿资料与成果

豆包工作同时提供办公文件创作、局部编辑、浏览器／电脑操作和飞书原生技能。审批、日历、文档、多维表格等属于平台内置技能；飞书生态之外的服务主要通过连接器接入，读写范围由连接账号和资源权限共同决定。这使同一任务既可以生成文件，也可以进入组织对象上的后续操作。[产品与工具说明](https://www.feishu.cn/content/article/7677519271848610746)

其更有区别的机制是输入与成果沿用同一条企业身份主线。按照飞书官方说明，用户原有权限内的组织架构、文档、群聊和会议等可以成为工作上下文；成果回到飞书后，团队继续按原有权限查看、分享、评论和编辑。对本来就依赖这些资料与协作关系的任务，这提供了减少重复导出、整理材料和重新映射分享对象的机会。[权限与数据说明](https://www.feishu.cn/content/article/7680042598047763739)

要利用这条路径，登录身份必须与工作资料对应。独立 PC 端使用豆包账号时主要进入个人空间，使用飞书账号时才对应企业身份，两套身份的数据、权限和权益不自动合并。飞书内入口与 PC 入口的功能也不完全相同，企业开放范围还受管理员配置和分批放量影响。已有大量飞书资料的团队，可以优先考察这条身份连续的路径，同时确认发起人能读取目标版本，成果能够回到预期的协作位置。

### 悟空：把会员资源、组织授权和执行设备分别配置

悟空把文件处理、日程、文档、审批等动作放进钉钉工作平台。其采用条件分属三个环节：会员提供算粒与模型权益，组织授权决定能否通过悟空访问钉钉数据，执行设备决定任务在哪里运行。企业购买会员后须由管理员分配席位；组织操作须由主管理员开启；敏感动作再由员工确认。[企业会员 FAQ](https://wukong.dingtalk.com/docs/enterprise-membership/faq/)、[权限说明](https://wukong.dingtalk.com/docs/quick-start/privacy-and-security/)

云电脑主要改变设备依赖。官方说明其可承担长时任务，减少对个人电脑持续在线的依赖，但须另购，目前只支持个人购买与使用，而且只能在购买组织中选择该设备。对跨分子公司或多组织身份的工作，云设备与组织授权需要一起核对；这不是可以由企业统一采购、跨组织调度的一池资源。[云电脑说明](https://wukong.dingtalk.com/docs/cloud-computer/)

企业技能管理的开放状态仍有文档差异。4 月历史更新写有企业专属技能中心，而当前企业 FAQ 对员工上传技能后集中沉淀、可见性管理和预安装等能力仍保留“开发中、申请体验”的表述。需要统一管理技能的团队，应以所需管理动作是否已在本组织开放为采用条件，不能仅凭历史更新标题安排全面部署。[更新日志](https://wukong.dingtalk.com/docs/changelog/)、[企业 FAQ](https://wukong.dingtalk.com/docs/enterprise-membership/faq/)

### WPS／灵犀：文档结构、执行环境与入口资格共同决定用途

灵犀独立端处理 Word、Excel、PPT、PDF，并提供代码执行和网页操作。10 月 22 日的文字／表格双写、团队功能和项目云模式，把持续编辑与跨设备使用纳入了更明确的产品路径。它的文档取向值得放到后续使用中考察：报告要继续修订，表格要继续计算，演示文稿要交给同事调整，交付物的内部结构会影响这些动作能否接续。[灵犀产品文档](https://www.lingxi.cn/docs)

6 月 11 日的 WPS 文字 Agent 内测帖提供了具体的原生对象说明：可更新的目录域、可二次编辑数据的图表、可修改公式，以及可接受或拒绝的修订与批注。这些设计让用户能够检查改动、保留文档结构并继续编辑，适用入口则是专用安装包与内测资格。当前灵犀文档仍将 Office 插件列为即将上线，因而历史侧栏内测、独立端双写和当前 Office 插件应分别看待。[文字 Agent 内测帖](https://bbs.wps.cn/topic/90044)

执行环境进一步决定资料范围。本地环境可访问授权目录与本地服务，适合直接处理散落在电脑中的文件；云端环境可访问 WPS 云盘，但不能直接读取本机文件，也不支持本机系统操作。选择云端处理云盘文档时，可以减少本地资源占用；若任务需要本机目录或本地服务，就要保留本地路径或另行准备云端可取得的输入。

研究与分析任务还要看已开放的数据源。专业数据源专节列明已接入秘塔学术搜索，而金融数据、政府公开数据及其他垂直数据仍有计划接入项。简介对多类数据源的概括不能替代这些具体状态；所需数据尚未接入时，任务仍需要用户提供材料或采用其他已可用的检索路径。[灵犀执行环境、项目与数据源说明](https://www.lingxi.cn/docs)

### WorkBuddy：让内容维护、修订确认与发布各有位置

WorkBuddy 的资料库把产物接入后续工作：MD 承担文字叙事，CSV 保存数据，HTML 负责展示，任务可以读取资料后继续加工并保存回去。其中，Agent 对 MD 的修改以待确认状态呈现，接受后才写入正文。用户由此可以先审阅建议，再决定哪些改动成为正式内容。[资料库说明](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Library)

这套安排把长期维护拆成了不同对象：内容调整落在 MD，数据更新落在 CSV，呈现变化落在 HTML。对需要持续更新的方案、台账或页面，采用时可以先确定哪一份内容是后续维护的依据，以及谁负责接受修订。

成果可见范围也由不同操作决定。“我的文档”仅本人可见，团队空间按空间权限向成员开放；“发布为网站”默认关闭，开启后任何获得链接的人都可以访问。保存、团队共享和公开发布因此是三种交付选择。准备让同事接着改的资料，与准备对外提供链接的页面，应分别设置范围。

企业旗舰版的两种套件提供了另一项实质选择。Buddy One 套件包含 CodeBuddy，以及腾讯文档、知识库、网盘等办公协同产品；企业微信联合套件使用企业微信登录、通讯录与授权上下文，不含 CodeBuddy 和前述办公协同产品。两种套件同价，选择后不能切换。已有企业微信资产的团队与需要补齐协同工具的团队，面对的是不同权益组合，应在下单前明确登录、资料与协作方式。[企业版版本说明](https://cloud.tencent.com/document/product/1831/134332)

## 四、模型、上下文、权限和人的工作怎样配合

### 模型配置影响理解与执行，产品决定可调用的工作路径

公司提供产品、服务和商业安排，产品提供工具、执行环境、状态与交互，模型负责在可见资料和允许动作内理解目标、选择步骤。以“更新报价”为例，模型需要理解报价口径，产品需要接通目标系统，发起人需要具备相应权限，任务还必须读到正确版本的成本表。这些环节分别决定该补充资料、调整工具、取得授权，还是改进推理与计算。

六组产品并非单一模型路线。Kimi Work 将自研模型与工作台结合：介绍页仍有 K3 表述，K3.1 Pro 发布说明已列明支持 Work 3.1.0+；企业组织还需管理员启用，发布时默认关闭。豆包工作将 Seed、Seedream、Seedance 等能力纳入产品体系。扣子的云端框架与所配模型可以分离，灵犀和 WorkBuddy 支持自定义模型，悟空高级会员的自定义模型则另有资格与组织控制条件。[K3.1 Pro 发布说明](https://www.kimi.com/en/blog/kimi-k3-1-pro)、[豆包工作说明](https://www.feishu.cn/content/article/7677519271848610746)、[灵犀模型说明](https://www.lingxi.cn/docs)、[WorkBuddy 模型配置](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Model)、[悟空会员 FAQ](https://wukong.dingtalk.com/docs/enterprise-membership/faq/)

选择产品时，因此要保留实际配置：用了哪个模型、什么工具、在哪个环境运行。需要改善复杂约束理解或计算时，模型选择是相关变量；需要读取内网文件或写入业务系统时，连接与权限则先决定任务有没有可执行路径。

### 保存了背景，还要确认它怎样进入当前任务

上下文的作用取决于生效范围和进入任务的时点。灵犀项目之间隔离，项目配置更新只影响此后新发起的任务；扣子本地终端会话与平台会话不同步；WorkBuddy 资料库中的空间或文档需要添加到任务，才能沿这条路径成为输入。[灵犀项目说明](https://www.lingxi.cn/docs)、[扣子本地 Agent](https://docs.coze.cn/cozespace_local_agent)、[WorkBuddy 资料库](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Library)

这三种机制处理的是不同问题：项目固化后续任务的共同背景，平台会话组织协作过程，资料库保存可再次选用的成果。持续保存资料可以减少重复准备，却也需要明确当前采用哪一版。旧预算与新预算同时存在时，任务可能计算正确但选错版本；资料缺失源于权限时，增加上下文窗口也解决不了访问问题。版本、字段含义和结果接收人，仍应作为任务输入明确下来。

### 人工参与既有业务责任，也有错误造成的返工

管理员决定成员能使用哪些产品、模型与对象；业务人员补充数据口径、版本与缺失材料；使用者定位修改、接受修订并核对结果；有批准权的人决定对外动作。这些工作中，一部分本来就是正常的业务责任，另一部分才是错误或工具中断造成的重复劳动。

区分两者，会改变采用判断。例如，保留报价审批并不表示 Agent 没有价值；反过来，减少了文件编写时间，却增加大量查错和重新录入，也未必改善整项工作。评价时应分别记录正常确认与额外纠错，才能判断产品究竟接走了什么、又把什么留给了人。

## 五、失败后恢复的是什么

连接恢复、重新运行任务、恢复文件版本和撤销业务动作，处理的是不同状态。任务中断时，部分记录或通知可能已经生效；文件回滚也不会自然撤回外部消息或审批。恢复的起点应是查清已有结果，再选择合适的接续方式。

## 六、公开使用记录中的具体工作路径

### 豆包工作：保存人的修改，再让 Agent 接着使用

花叔《豆包工作从入门到精通》的 9 月记录，展示了一条围绕同一文件接续的路径。按作者叙述，9 月 7 日，Agent 先为虚构的四个月销量表填入公式；作者在内置编辑器中修改 B2，保存并重新打开，再要求 Agent 重读。后续 PPT 使用了修改后的数据。这个过程的关键是保存与重读：人的修改先成为文件状态，再进入下一轮生成。[《豆包工作从入门到精通》§05–06](https://www.huasheng.ai/orange-books/doubao-work/read/)

9 月 17 日的另一条记录使用表格原生选区指定 H4。作者报告，另存结果只有该格的字体加粗属性改变，公式、数值与其他样式保留。HTML 报告案例则使用标题和文字定位卡片；书中还保留了网页排序出错后，按具体预期顺序反馈并修复的过程。表格选区、HTML 文字定位和排序纠错，是三种不同的交互，不应合并为同一种网页框选能力。

该记录区分虚构销量、模拟缺数表、真实历史视频数据与教学模板，模板未逐条重测；案例来自作者对应账号与版本，未覆盖真实同事参与的多人协作。它对选型的具体启发是：需要人机交替编辑时，应检查用户保存的新状态怎样进入下一轮任务，以及反馈能否准确指向要改的位置。

### WorkBuddy：在自生成半成品上交替编辑

光子星球 7 月 30 日的体验，采用“先让产品生成半成品，再修改自己的作品”的方法，涉及 PPT、Word、Excel、Markdown 和跨格式汇报，表格包含 50 行模拟销售数据。作者描述了选区编辑、在同一窗口交替手动与 AI 修改，以及把表格分析继续整理成 PPT 的过程。[光子星球体验，新浪转载](https://finance.sina.com.cn/stock/t/2026-07-30/doc-inikrfcu9525292.shtml)

记录同时指出 Word 编辑框位置异常、PPT 文字偏多。这些问题让返工位置变得具体：内容生成之外，编辑器定位和呈现调整也会影响连续使用。它展示的是 7 月版本在自生成、受控素材上的操作，未覆盖企业多年积累的复杂文件、共享权限或长期重复任务；本文据此讨论交互路径，不将文章所称的标注准确推广到真实脏数据，也不把它当作 11 月版本测量。

### WPS 生态教程：Agent 给出步骤，人完成权限变更

5 月 5 日的一篇 WPS 教程中，作者自报金山 KVP，使用当时的灵犀 Claw 读取订单系统多维表格的结构，取得高级权限设置步骤，再由人手动配置角色和协作者权限。作者称，当时接入的云文档技能包没有直接设置的权限。[订单表权限教程](https://forum.wps.cn/topic/86990)

这条记录中的人机分工很明确：Agent 理解表结构并提供针对性指导，真正改变权限状态的是随后的人工作业。原文没有给出工具定义、授权配置或失败响应，限制究竟来自功能实现、接口开放还是账号授权，仍无法确定。因此，它说明的是 5 月该技能路径上的接手位置，而不是当前灵犀全部入口的能力上限；作者的生态身份也应与无关联独立测评分开理解。

### 厂商内部采用披露：说明使用规模，不提供任务表现分母

WorkBuddy 产品介绍称，其已成为超过 12,000 名腾讯员工常态使用的工作台。这是厂商披露的内部使用规模；页面没有提供足够的活跃定义、任务分母、人工耗时与对照，本文保留人数及其归属，不据此估算效果。[WorkBuddy 产品介绍](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Product-Guide)

上述操作叙述为选择采用任务提供了三个具体方向：保存后接续生成、在同一编辑环境中反复修改，以及由人接手尚未执行的业务步骤。它们共同把“协作”拆成了可观察的动作；真正的多人协作，还需要覆盖同事加入、对象权限和交接后的继续使用。

## 七、怎样据此确定采用范围

### 企业办公负责人：按资料位置与结束动作缩小选择

| 当前工作条件 | 值得优先考察的路径与理由 | 会改变采用判断的观察 |
| --- | --- | --- |
| **资料散在本机目录，最终交付可检查的文件** | Kimi Work、灵犀本地环境、WorkBuddy 等具有授权目录与文件工具的桌面路径。重点检查输出结构是否支持下一轮编辑。 | 若目录准备、设备维护、连接修复和结果核对占去更多人工，本地读取便利就不足以支撑扩大采用。 |
| **已有本地 Agent 和工具链，需要更多同事参与调度** | 扣子本地接入可复用已有环境，并通过项目让成员共同下达指令。 | 若共同使用带来账号、权限或机器资源维护负担，或旧会话背景无法方便转入，统一入口的收益会缩小。 |
| **资料与协作者主要在既有办公套件中** | 飞书资料可考察豆包工作的企业身份路径；钉钉对象可考察悟空；WPS 云文档可考察灵犀；腾讯协作资产则需按 WorkBuddy 两类企业套件分别选择。 | 若独立工作台在同输入、权限与质量要求下，需要的整理、核对和返工更少，套件上下文优势就会缩小。 |
| **同一文档或表格需要反复修订、交接** | 对照 Kimi 的选区与历史版本、灵犀对应入口的文档编辑、豆包工作的编辑与飞书协作、WorkBuddy 的资料库修订，考察哪条路径最贴近现有对象。 | 若改动不能保留原有公式、可编辑图表或协作关系，采用范围应退回新文件生成、受控副本或较简单对象。 |
| **需要无人值守的周期任务** | 输入在云端可达时，可考察豆包云端定时、扣子云端 Agent、悟空云电脑或灵犀云环境；Kimi Work 桌面定时则须保持电脑与应用运行。 | 若错过触发、等待确认或中断后的人工接续无法满足工作节奏，单次完成也不足以支撑周期采用。 |
| **规则固定，已有公式、脚本或自动化** | 先保留现有路径，辨别 Agent 是否解决了新增的理解、材料处理或交互需求。 | 若既有确定性流程更稳定、更易维护，就没有必要只为统一 Agent 入口迁移。 |

一个可落地的起点，是下一次已有的例行月报或资料整理任务。由现有业务负责人确定输入版本、目标对象和必须保留的内容，管理员确认所需入口与权限，使用者检查保存后的文件或业务状态。先让 Agent 承担边界清楚、结果可检查的部分；对外发送、提交或发布是否纳入，应随责任安排和实际工具能力确定。

随后比较整项工作的变化：准备材料、确认动作、核对输出、修正错误和交接分别花了多少人工，运行等待是否影响交付。正常审批与重复纠错应分开记录。在质量与交付要求不变的条件下，如果同类任务可以持续接续、后续同事能够使用成果，且额外检查与恢复没有抵消节省的劳动，就有理由扩大到相近工作；否则应缩小对象范围、调整执行环境，或保留原流程。这里不预设节时比例，也不以减少必要审批作为采用目标。

### AI 产品负责人：把下一轮工作所需的状态做清楚

已有产品变化指向几项具体机会。选区和对象身份能让修改目标明确；版本差异与修订确认能让人看见并决定改动；保存后的重读能让用户修改成为下一轮输入；资料库与项目则为下一次任务保留材料。生成、接受修订、团队分享和公开发布需要清楚的状态区分，尤其是最后一步会改变成果的可见范围。

失败提示也应能帮助用户定位阻断点：缺的是输入、工具、权限，还是已经生成的结果有误。缺输入时补资料，缺连接时调整环境，缺权限时保留授权或人工接手，计算或内容出错时才进一步检查模型、公式与任务要求。这比把所有问题都归结为模型不够强，更有助于决定下一步产品改进。

六组产品已经形成不同的采用理由：本地工作台便于接触电脑中的材料，组织原生入口便于延续身份与对象关系，项目和资料库便于围绕成果继续修改。选择哪条路径，应由当前工作对象和组织现状决定。**先按对象与权限选择入口，再按完整任务中的准备、修改、恢复和交接情况，决定扩大采用、调整方案或保留原有自动化。**
