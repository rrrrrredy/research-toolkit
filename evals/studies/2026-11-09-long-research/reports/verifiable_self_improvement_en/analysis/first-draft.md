# Verifiable Self-Improvement: What Changes, Why It Helps, and What Survives the Search

Evidence through 9 November 2026. A research report for engineering and research leaders deciding where automated improvement can produce a reusable capability.

## The useful question is what the next task inherits

Automated improvement is already producing useful artifacts: a coding agent with better tools, a faster numerical kernel, a more effective task prompt, and a model that corrects its own mistakes more selectively. These advances have different causes and different deployment requirements. Treating them as one capability called “recursive self-improvement” obscures the engineering decisions that make them work.

The clearest dividing line is what remains after an optimization run ends. A better answer helps the current user. A better program, prompt or learned policy can help later users. The second outcome is valuable when the retained change improves the work it will actually encounter, with its required properties intact. Repeatedly obtaining a higher score on the examples used to choose the change is useful search feedback; the deployment decision concerns the future work that inherits the artifact.

Three findings organize this report. First, **the editable interface and evaluator form the central product design**. AlphaEvolve can search aggressively because many target programs have an executable objective and a controlled place to insert a change. Second, **reuse has to be measured on the relevant axis of change**. DGM's cross-benchmark results support transfer of some agent-code improvements; a controlled harness-evolution study finds little transfer under another protocol. Third, **correction needs a selective objective**. SCoRe improves the ability to repair wrong answers while preserving correct ones; a generic request to reconsider can worsen the result.

The practical opportunity is therefore broad but structured. Teams with a recurring, checkable task can expose a useful part of the system to automated search, retain the candidate's exact dependencies, and deploy the change that performs well on the work they expect next. Teams whose outcomes depend on unresolved judgments first need a more informative evaluation target. A larger improvement loop cannot supply a missing definition of success.

## Name the retained object before comparing systems

| System | What changes and persists | Candidate generator | Feedback and selection | What remains externally supplied |
|---|---|---|---|---|
| DGM | Coding-agent source patches and an archive of agent variants | An archived agent modifies its own code after a separate model diagnoses a failure | Empirical coding-task outcomes; fixed archive and parent-selection procedure | Foundation models, diagnostic model, task tests, initial agent and outer search code |
| AlphaEvolve | A target algorithm or program implementation | Gemini-based code proposals using a seed and program database | Executable evaluators, staged rejection and performance measurement | Objective, editable interface, workload, correctness checks and deployment integration |
| Promptbreeder | Task prompts, mutation prompts and selected worked examples | A frozen language model generates task and mutator variations | Training-example accuracy and population selection | Base model, examples and labels, genetic procedure and final test |
| SCoRe | Model weights implementing a two-attempt correction policy | On-policy responses during reinforcement learning | Training-time correctness rewards and a staged correction objective | Training oracle, task construction, initial checkpoint and learning algorithm |
| HarnessPro | Instructions, tool/runtime settings and selected harness packages | A development team diagnoses trajectories and proposes changes | Frozen generated tests, validation selection and final official grading | Models, development roles, task partitions, base runtime and final grader |

This is a classification of mechanisms, not a ranking. DGM edits parts of the agent that will perform later improvements; AlphaEvolve normally edits a target program used by another application. Promptbreeder can change the prompt that generates future prompts; SCoRe changes a policy through training. A temporary second attempt is a use of that policy, not another update to its weights. These distinctions identify what can compound and what must be supplied anew.

They also define the baseline. A proposed kernel should be compared with the implementation and compiler actually deployed. An agent-code change should be compared under the same downstream model and task conditions. A correction policy should be compared with the same model's first and second attempts. A search procedure should face a meaningful alternative use of the same search opportunity. The strongest claim in each comparison is the one that matches its changed object.

## How a retained improvement is produced

The common structure can be written as:

**Define the target and admissible changes → propose a candidate → execute a relevant evaluator → select or archive → evaluate the retained artifact on its intended future work → deploy, keep for further search, or revert.**

The steps have different meanings across the systems. Archiving a DGM descendant preserves a possible stepping stone; deploying it chooses what users will receive. AlphaEvolve's evaluator may protect feasibility outside the editable block. Promptbreeder's fitness labels tell the search which answers count as correct. SCoRe's training reward teaches when a second answer should differ. These are substantive decisions, not interchangeable boxes in a generic workflow.

The following comparisons reconstruct those decisions and show where the published results support useful reuse.

## DGM: a useful change survives the task that produced it

The Darwin Gödel Machine makes the coding agent itself the editable program. Its central attraction is reuse: a better editing tool or a better way to retain useful context can help on the next repository, whereas a patch that solves only today's issue is consumed by that issue. The optimization target is therefore the reusable agent, evaluated by the work it subsequently performs.

The actual loop has more than one source of intelligence. Evaluation logs identify an opportunity; a separate diagnostic model proposes an improvement; an archived coding agent implements that proposal in its own code; a fresh evaluation measures the changed agent. DGM's paper identifies the diagnostic model as OpenAI o1 in Appendix C.3. The inspected `self_improve_step.py` agrees, initializing `diagnose_model = 'o1-2024-12-17'`. Claude 3.5 Sonnet powers code modification in the reported experiments. During downstream evaluation, the SWE experiment uses Claude 3.5 Sonnet and Polyglot uses o3-mini. Foundation-model weights are frozen. The outer archive and parent-selection procedure remain fixed. [DGM v2, §§3–4, Appendix C.3](https://arxiv.org/html/2505.22954v2); [public self-improvement step](https://github.com/jennyzzt/dgm/blob/main/self_improve_step.py).

This division explains what compounds. A parent with a more useful editing interface can implement its next proposed change more effectively. The external diagnostic contribution does not disappear: better diagnosis may make a change feasible that the parent would not have proposed. Nor does the fixed selection rule improve merely because the descendants do. The retained artifact and the mechanism that selects it must be named separately if the system is to be compared with an ordinary external code optimizer.

| Part of the loop | Actual behavior | Why it matters to a reusable improvement |
|---|---|---|
| Candidate parent | Drawn from an archive; the default code combines score with an inverse child-count factor | A successful but underexplored branch can receive work; one lineage need not monopolize search |
| Diagnosis | Selected task failure or a class such as empty patches/context handling is turned into a proposed change | It directs search toward a concrete limitation, while supplying outside model work |
| Modification | Parent patches are applied in a container; the coding agent edits its own repository and exports a patch | The output is persistent executable state, not a temporary answer |
| Evaluation | Downstream tasks test whether the changed agent still edits code and solves problems | An attractive change description alone cannot improve the measured result |
| Retention | Compilable, functional descendants enter the archive; the default `keep_all` does not require beating the parent | A temporarily weaker descendant can contain a useful stepping stone |
| Later choice | New parents are sampled using the fixed outer procedure | Reuse depends on selection as well as invention; the entire optimizer is not self-editing |

The archive is valuable for a reason that ordinary “keep only the winner” optimization misses. Features can be complementary. A change that preserves more task context might initially make the agent slower or less decisive; a later tool change could make that retained context useful. Discarding every intermediate regression would prevent that path. Keeping a branch for exploration, however, is a different decision from deploying it to users. The former buys an option on future combinations; the latter requires current suitability. This distinction permits a broad research archive and a conservative production choice without confusing their purposes.

The observed gains support useful agent-code improvement. The paper reports SWE success rising from 20% to 50% on its 200-task evaluation pool and full Polyglot from 14.2% to 30.7%. Cross-benchmark transfer provides a separate result: the SWE-evolved agent reaches 28.9% on Polyglot versus the initial 14.2%; the Polyglot-evolved agent reaches 24.5% on SWE versus 20%. These results identify improvements that survive a changed task distribution, with transfer strength differing by direction. [DGM v2, §4.4 and Appendix A](https://arxiv.org/html/2505.22954v2).

The most useful interpretation is that some discovered infrastructure changes carry across tasks. It would be a mistake to infer that a feature generalizes simply because the program is reusable: reusable code can still encode benchmark-specific habits. Here the cross-benchmark comparison is informative precisely because it asks that further question. Model replacement adds another useful axis, but changing the model on the same selected tasks does not create a new task holdout. A team adopting the resulting code should ask which axis of change resembles its deployment: new repositories, a new language, a new model, or a new tool environment.

Selection exposure also explains the main SWE curve. Candidates are progressively evaluated on larger subsets; the same pool helps the process select promising variants. The score documents optimization progress on that pool. The transfer evaluations add evidence about the retained artifact beyond it. Neither type of result should erase the other: optimization progress is useful for finding candidates, and transfer determines how much of that progress can be reused.

The inspected public code is a source snapshot, not a reproduction of the reported run. Its defaults include 80 outer generations and two attempted modifications per generation; the paper describes 80 generated-agent iterations with parallel attempts. Those units cannot be silently equated. The paper's run definition and the code's command defaults describe different search budgets. This also prevents a generic “80 iterations” label from hiding a different search budget in a future replication.

## AlphaEvolve: the evaluator makes a broad search usable

AlphaEvolve changes a target program using a model-powered evolutionary search. The editable program need not be the agent running the search. Its engineering value comes from a convenient separation: the proposer can explore many implementations, while an evaluator rejects invalid ones and measures the property the application needs. The seed, allowed edit region, evaluation cascade and program database turn a vague wish for a better algorithm into a search over runnable candidates. [AlphaEvolve technical report, §§2–3](https://arxiv.org/html/2506.13131v1).

The shape of the evaluator determines how much freedom the proposer can use. If the system changes only the ranking of already-feasible placements, feasibility is protected by the surrounding application. If it writes low-level kernel code, the evaluator must also establish that the output still implements the required operation. If it proposes a mathematical construction, the relevant check may be exact verification of that construction. Calling each of these “evaluation” is convenient, but conceals different engineering obligations.

The Borg example makes the benefit of a narrow interface concrete. Ranking feasible hosts gives the optimizer a meaningful scheduling choice while leaving feasibility with the scheduler. This can be more productive than allowing arbitrary scheduler edits and trying to detect every failure afterwards. The useful generalization is about where to expose freedom: give search access to a consequential decision whose admissible outputs are already well defined. An application does not become less valuable because most of its implementation is fixed.

Kernel optimization has a different structure. Equivalent outputs are only the entry condition; speed depends on shape, dtype, compiler, hardware and surrounding work. A fast implementation on the search shapes may specialize too narrowly. AlphaEvolve's tiling work separates optimization shapes from held-out shapes, then reports both kernel and larger training effects. Its reported 23% average kernel speedup and 1% overall Gemini training-time reduction answer different questions. [AlphaEvolve technical report, §3.3](https://arxiv.org/html/2506.13131v1).

A simple application of Amdahl's law clarifies the mechanism. If a changed component represents fraction `f` of the original runtime and becomes `s` times as fast, the normalized new runtime is `(1-f)+f/s`, assuming the rest stays unchanged. A substantial local improvement can therefore produce a small but valuable end-to-end gain when the component is a small part of the total. Conversely, a favorable microbenchmark can be commercially irrelevant if it does not affect the actual bottleneck. This is an analytical illustration, not a reverse estimate of Google's component share: the paper's averages and workload mixture need not match the assumptions of this single-component formula.

The RTL case provides a second practical lesson. The authors report an automatically discovered bit-width reduction, while also stating that downstream synthesis independently found that change. The discovery is still evidence that the search can propose a valid simplification. Its incremental production benefit depends on the counterfactual toolchain: if the existing compiler already removes the redundancy, adding the proposed source change may improve readability or portability without creating an additional hardware saving. Automated discovery and additional realized gain are distinct business questions, and the source itself supplies the information needed to answer them. [AlphaEvolve technical report, §3.3](https://arxiv.org/html/2506.13131v1).

By the November 2026 cutoff, official documentation describes AlphaEvolve as a service requiring a functional seed and an evaluable optimization objective. The May 2026 impact update reports applications beyond the initial demonstrations, including Spanner write-amplification and scientific optimization. These are dated deployment reports. The research recommendation does not require adding every reported percentage to a leaderboard: the recurring product pattern is a high-value, repeatedly executed program with an objective that can be evaluated often enough to guide search. [Current product overview](https://cloud.google.com/vertex-ai/generative-ai/docs/alphaevolve/overview); [May 2026 impact update](https://deepmind.google/blog/alphaevolve-impact/).

This is an attractive deployment target because the development effort can be amortized across future executions. That economic argument does not mean the optimizer should prefer a cheap but incorrect candidate, nor that search is free. The engineering decision is whether the eventual improvement matters enough to justify candidate generation, evaluation infrastructure and integration. The evidence for correctness must cover the function actually deployed; the evidence for performance must cover the workload that will execute it.

## Promptbreeder: the reusable artifact can be language

Promptbreeder retains task prompts, mutation prompts and, in its few-shot setting, successful worked examples. A frozen language model generates variants; answer accuracy on training examples determines fitness; a population evolves under a human-designed selection procedure. Hypermutation changes the instruction used to generate future prompt variants. Thus some of the search behavior is editable, even though the base model, genetic procedure, fitness labels and task definition remain external. [Official ICML paper, §§3–4](https://proceedings.mlr.press/v235/fernando24a.html).

The useful mechanism is adaptation to a recurring domain. A prompt found for one problem is a one-off artifact; a prompt that improves performance on unseen problems from that domain is reusable. Promptbreeder's official Table 1 reports PaLM 2-L zero-shot GSM8K accuracy of 83.9%, versus 66.5% for its CoT baseline and 65.5% for a 2,000-prompt combinatorial-initialization baseline. The held-out evaluation and baseline identity are essential to interpreting that comparison. The official paper and Table 1 were read, including the footnote assigning half-splits to four datasets without supplied training/test partitions.

The mutation-prompt mechanism does not make human problem formulation irrelevant. A mutator can propose novel instructions only within the objective and examples available to the search. If the task description is wrong, the system can spend substantial effort becoming better at the wrong framing. If the labels reward an incomplete answer, fluent prompt variants may optimize that omission. The remedy is to improve the specification or evidence about the intended task, rather than make the evolutionary loop more elaborate.

The ablation clarifies the scale of the claim. Appendix B evaluates population mean fitness over 200 evaluations with a population of ten; it does not report the final held-out accuracy of a new deployment. Its heatmap mostly favors the removed mechanisms being present, but contains exceptions. Initial prompt diversity has a large effect in that setting. This supports a contribution to search behavior; it does not identify one universally superior mutation sentence. [Official paper, Appendix B, Figure 4, PDF pp.16–17](https://raw.githubusercontent.com/mlresearch/v235/main/assets/fernando24a/fernando24a.pdf).

For a product team, the main design choice is what should persist after the search. A prompt is easy to deploy and inspect, but its meaning is mediated by a particular model and formatting convention. Replacing the model can change the effect of the same words. Retain the discovered prompt with the model, output parser and evaluation conditions that made it useful. Reusing the search method on a new model is a different claim from transferring the exact prompt without searching again.

## SCoRe: improving a correction policy requires a training signal

SCoRe changes weights so that a model can improve its answer in a second attempt. It uses correctness feedback during training and then asks the trained model to revise without that oracle at inference. The retained object is a trained policy; a particular second answer is a temporary inference result. This separates learned self-improvement from repeatedly prompting an unchanged model to reconsider.

The method trains on the model's own evolving responses. A first stage discourages collapse into simply repeating the first answer; a second rewards useful correction while penalizing degradation of a correct answer. On MATH, Gemini 1.5 Flash's reported first/second-attempt accuracies move from 52.6/41.4 before training to 60.0/64.4 with SCoRe. The trained checkpoint's second attempt adds 4.4 percentage points; the change in that correction delta is 15.6 points. On HumanEval, the trained Gemini 1.0 Pro policy transfers from MBPP training. [SCoRe v1, §§3,5–6, Tables 3–5](https://arxiv.org/html/2409.12917v1).

The central failure mode is objective ambiguity. A training objective can reward a high final answer score without requiring the model to learn how to use its earlier attempt. Learning to answer immediately and then copy itself can satisfy that objective on training data. Alternatively, an offline collection of successful corrections can teach repair on another model's errors while failing on the learner's own error distribution. Useful correction requires both the right incentive and relevant states to correct.

This explains why a correction policy should be judged by two transitions: wrong-to-right and right-to-wrong. A system that finds more errors but damages even more correct answers does not improve the delivered result. A system that never changes an answer avoids damage but has no correction benefit. The desired policy selectively changes what is wrong and preserves what is right. That is a learned decision about content, not a preference for more rewriting.

The positive result is operationally valuable: training can make a second attempt worthwhile where naïve reconsideration is harmful. It also defines the next deployment question precisely. If a team wants three or ten successive revisions, it needs evidence about those later states; a policy trained and evaluated for one correction round does not determine their behavior. The appropriate retained capability is the demonstrated two-attempt policy, rather than an assumed indefinitely improving loop.

## A changed harness needs a better feedback signal than its own change proposal

HarnessPro targets the instructions, tool behavior and runtime settings around an existing coding model. Its optimization team reads execution trajectories, diagnoses failures and proposes executable changes. The resulting harness is subsequently used to perform tasks; the development team's roles are not automatically a collection of agents launched for every downstream task. The retained artifact is a configuration and runtime package around the model, rather than new model weights. [HarnessPro v2, §§3–4](https://arxiv.org/html/2610.26770v2).

The important design decision is candidate selection. A model can write an articulate justification for a change that does not actually fix a task. HarnessPro generates tests from a task and the initial execution trajectory, freezes those tests, and uses execution against them to evaluate later candidates. Freezing keeps the evaluator from changing to agree with each candidate. Generated tests supply a reproducible signal where official task tests are unavailable during optimization. Their errors still matter: a mistaken assertion can repeatedly reject a correct candidate or reward a defect. The mechanism improves the consistency of feedback; the test's relationship to the intended task determines whether that consistency is useful.

The authors' preliminary comparison reports failure recall increasing from 41.7% for direct model judgments to 83.3% using generated tests. This is a failure-detection metric from that experiment, not a task success rate. The final benchmark results use official grading. That separation is a productive design: inexpensive surrogate feedback helps search, while a different evaluator measures the resulting system. [HarnessPro v2, §4.3 and Figure 2](https://arxiv.org/html/2610.26770v2).

The experiment separates three uses of tasks. Ten training tasks per benchmark drive candidate generation and evaluation, using three rollouts per task per epoch. Other non-test tasks form the validation set used to retain candidates. The held-out test sets contain 59 Terminal-Bench 2 tasks, 100 SWE-Bench Pro tasks and 100 ProgramBench tasks. Search runs for three epochs on the first two benchmarks and four on ProgramBench, retaining up to three harnesses after each epoch. The held-out score therefore concerns an artifact selected before those tasks were used for final grading. Validation remains part of selection: it should not be counted as a second independent final test. [HarnessPro v2, §5.1](https://arxiv.org/html/2610.26770v2).

The strongest reported configuration reaches 80.8% on Terminal-Bench 2, compared with RHO's 76.3%, using GPT-5.5 with Codex 0.147.0. Its mean execution cost per task is $0.72 versus $1.09. These measurements concern execution of the resulting harness. They do not include all development trajectories, candidate generation, synthetic-test generation and validation in one amortized total. A team adopting an already published artifact faces a different economic question from a team rerunning the optimizer for its own workload.

The score definitions also differ across benchmarks. Terminal-Bench and SWE-Bench Pro count tasks whose official tests all pass. ProgramBench averages the fraction of tests passed within each task, then averages those task fractions. A ProgramBench percentage must retain that meaning in comparison tables. An optimizer that solves half the checks in every reconstructed program could obtain a substantial partial-credit score while completing no program fully. This can still measure progress, but a deployment requiring complete reconstructions needs the all-requirements result as well.

## What the ablations support

HarnessPro's ablations make one practical conclusion unusually clear: copying the most visible runtime rule is a poor substitute for the evaluated combination. On SWE-Bench Pro, adding dynamic reasoning routing to RHO lowers its reported score from 80% to 76%; adding budget hooks produces 75%; fixing reasoning effort at low produces 59%. The full strongest HarnessPro configuration reaches 80.7%. The result favors the particular evolved package over those isolated substitutions in that setup. It gives a concrete reason to inspect a proposed rule's effect on successful task completion before making it a general default. [HarnessPro v2, Table 3](https://arxiv.org/html/2610.26770v2).

Removing the test synthesizer reduces the strongest configuration's Terminal-Bench score from 80.8% to 74.6% and its SWE-Bench Pro score from 80.7% to 72.0%. Removing the planner has smaller effects in those configurations. This is evidence that candidate feedback and planned edits contributed to the optimization procedure. It does not specify that every new product needs identically named roles. A product whose failures already have executable checks can use those checks directly; inventing another test generator would add a component without supplying the missing information.

The released repository contains selected harness artifacts, task splits and evaluation runtime. The inspected README describes reproduction of those artifacts' evaluation. It does not expose the whole candidate-producing optimization process as a runnable public system. The inspected terminal-medium runtime hook illustrates that some resulting policies are executable constraints: it counts tool uses and can deny additional tools after the configured finalization threshold. That is a more consequential behavior than a reminder appended to a prompt. The appropriate deployment question is whether the threshold preserves the steps required by the target task. The research result does not remove the need to answer that task-specific question. [HarnessPro public release](https://github.com/pzs19/HarnessPro).

## A controlled negative result identifies the alternative use of extra computation

The July 2026 study *Rethinking the Effectiveness of Automatic Harness Evolution* compares harness changes with additional attempts at the task. It uses Terminal-Bench 2.1, a revised 89-task suite, a shared initial AHE harness, a five-attempt budget and three models in the no-test setting. The AHE comparison uses one rollout per task per harness and disables its explorer component. These choices define the tested system; this is not a reproduction of HarnessPro's later optimizer. [Rethinking v1, §§3–4](https://arxiv.org/html/2607.12227v1).

Without available unit tests, parallel sampling averages 72.3% versus the initial harness's 68.2%, using a model to select the final candidate. The reported harness-evolution average is 67.4%. With tests available, parallel sampling reaches 86.0% selected-answer success; sequential refinement reaches 84.3% selected-answer success and 91.8% pass@5, while harness evolution reaches 75.8% and 86.2%, respectively. The candidate-set metric and the selected final-answer metric answer different operational questions. A correct candidate somewhere among five attempts helps only if it can be found or consumed by the downstream workflow.

The transfer experiment is more directly relevant to a reusable harness. It uses 45 training tasks, 10 validation tasks and 34 disjoint test tasks. Harness evolution produces held-out scores of 64.5% versus 63.3% for Claude Opus 4.6, and 72.1% for GPT-5.4 both before and after evolution: an average increase of 0.6 percentage points. The useful finding is small observed transfer under this protocol, rather than a claim that no harness can ever generalize. The paper's discussion proposes a model-capability bottleneck and limited benchmark sensitivity as explanations. Those explanations fit the observed failures but are not separately isolated by the experiment. [Rethinking v1, Table 3 and §5](https://arxiv.org/html/2607.12227v1).

This result changes the decision about what to retain. An extra attempt can discover the answer to a hard instance without revealing a reusable strategy. Persisting the command sequence, task-specific file paths or one error workaround into a general prompt may then increase future reading burden without increasing future capability. Conversely, fixing an interface that systematically loses an argument can help every task that uses it. Both changes may arise from a trajectory; the causal link between the failure and the edited component distinguishes them.

## Why the two studies can both be informative

The papers ask related questions with different experiments. HarnessPro uses new models, different task versions and splits, a dedicated generated-test mechanism, validation-based candidate retention and specific runtime artifacts. Rethinking fixes a smaller five-attempt protocol around an AHE scaffold and directly compares alternative uses of those attempts. Their percentages cannot be subtracted to estimate the advantage of one research team over the other. Their combination instead identifies two decisions that must be made explicitly: whether to spend effort on solving the present instance, and whether to retain a change for future instances.

A deployment decision can follow the intended artifact. For a one-off task, extra sampling or correction can be worthwhile even if nothing reusable remains. For a service with recurring tasks, a harness change is valuable when it corrects a repeated causal failure and survives relevant new instances. For an optimizer, a better selection signal can be more valuable than a more elaborate candidate generator. The practical progression is to identify the failure, locate the component able to change it, and ask the appropriate future-work question. A loop becomes productive through those relationships, not through recursion alone.

Neither study supplies a universal agent architecture. Together they provide a stronger engineering lesson: examine the exact feedback that chose an artifact and the work on which that artifact was later useful. Keep genuine reusable repairs, use temporary search for instance-specific difficulty, and avoid turning every successful workaround into permanent instructions.

## The evaluator determines which improvements the search can find

### Correctness is a relationship to the intended task

An evaluator can execute perfectly and still reward the wrong behavior. A specification may omit a user requirement; a reference answer may contain an error; a performance benchmark may cover only convenient shapes; a simulator may omit a field constraint. Search then makes systematic progress on that surrogate. More evaluations make the wrong target more influential.

For program optimization, it helps to separate three levels. **Validity by construction** keeps an invariant outside the editable surface, as when a scheduler ranks only feasible hosts. **Testing** checks candidate outputs for selected inputs, including randomized and adversarial cases. **Complete verification of a defined finite or formal object** can establish a narrower proposition exactly, such as whether a particular mathematical construction satisfies specified equations. Their coverage differs. A passing numerical test suite is strong evidence for the inputs and tolerances it exercises; it is not automatically a proof of equivalence for every input supported by an API.

The engineering response follows the deployment obligation. A numerical kernel may need shape/dtype coverage, tolerance decisions, NaN behavior and hardware-specific checks. A scheduler needs the constraints and workload distribution of the actual fleet. A coding agent needs to preserve repository requirements beyond the hidden tests used for a benchmark. These concerns determine the evaluator and interface; they do not justify adding every possible check to every system.

Incorrect reference answers deserve special treatment because the system can be right for the wrong recorded score. When a selected candidate disagrees with a trusted implementation, the disagreement is an investigation target: inspect the intended specification, determine which result it implies, and preserve the original discrepancy. Quietly changing the oracle until the favorite candidate passes destroys the evidence for selection. Replacing an erroneous reference is legitimate when the underlying task supports the correction; the candidate must then be reconsidered against the corrected rule rather than awarded its former score unchanged.

### Adaptive reuse changes what a high score establishes

An evaluation set used repeatedly to choose candidates becomes part of the optimization process even if the model never sees its raw answers. Selection leaks information through which candidate survives. A large search can exploit a small systematic quirk or a lucky collection of examples. This is the practical meaning of adaptive overfitting: the best candidate on the reused set can be the one most fitted to that set's accidents.

DGM's adaptive coding pool and transfer results illustrate how to keep the questions separate. The optimization curve tells an engineer whether search is finding variants favored by its feedback. The cross-benchmark evaluation asks whether the selected agent retains useful behavior on another distribution. HarnessPro's validation set selects candidates and its held-out tasks evaluate the selected artifacts. Rethinking's45/10/34 split directly shows how apparent search progress can become only a small change on new tasks. These are different evidentiary roles, rather than stronger and weaker names for the same score.

The needed holdout should match the decision. A team changing an inference model needs evidence on that model; a team expanding to new repositories needs new repositories; a team entering a new task family needs that family. Merely reshuffling familiar prompts may test response variability while leaving the important distribution shift untouched. Conversely, an exact algorithm improvement need not outperform on unrelated natural-language tasks to be valuable. The future workload defines the relevant transfer claim.

Multiple candidate selection creates another asymmetry. A noisy high score is more likely to appear when many candidates are tried. The winning candidate should therefore be judged on evidence not used to make it the winner. This does not require hiding all useful feedback from the optimizer. Development feedback can be rich; the distinction is that final evidence for deployment must add information beyond the selection event. Three repeated measurements of a chosen artifact can characterize some rollout variation, while three independently optimized searches would address variability of the optimization procedure. Neither number should silently stand for the other.

### Reward exploitation can be local and ordinary

The most common failure need not look like a malicious system rewriting its reward. A prompt can teach answer-format tricks that a parser rewards. A test generator can overfit to the initial implementation's mistaken behavior. A runtime policy can make a tool-count metric look better by stopping before the required work is done. A kernel can exploit a benchmark's narrow shapes. In each case the artifact improves a measured quantity while losing something the user asked to retain.

SCoRe makes this problem concrete at the level of behavior. Rewarding final-answer correctness can encourage a strong first answer followed by copying, leaving no learned correction skill. Training against the distribution of the model's own errors and rewarding useful transitions changes the incentive. A similar principle applies to code and workflows: specify which properties must survive and which may improve. “More change” and “more confidence” are not substitutes for that transition.

The inspected HarnessPro hook also shows why a candidate's implementation matters. A budget reminder and a tool-denial threshold may have similar documentation but different consequences on a long task. Inspecting the executable path identifies whether the policy assists prioritization or removes the ability to perform a needed operation. The correct choice depends on the intended work. The ablations already show that copying a visible rule can reduce task success even while lowering its execution cost.

## Where candidate generation and evaluation each constrain progress

Improvement requires both finding a useful change and recognizing it. A stronger generator expands the candidate set; a better evaluator makes useful candidates more likely to survive. Increasing one does little when the other is the bottleneck. DGM's outside diagnostic model illustrates a contribution to finding changes. HarnessPro's generated tests illustrate an attempt to make candidate selection more informative. AlphaEvolve's application-specific evaluators make broad code generation manageable. SCoRe supplies the training feedback needed to make correction selective.

The balance differs by target. Generating a short prompt can be cheap relative to evaluating it across many tasks. Proposing a numerical kernel is quick relative to compiling, validating and profiling it on representative hardware. An agent change may require complete repository task executions to evaluate. Repeated evaluation can therefore dominate the work even when the model calls that generated the candidate are conspicuous. Public reports should keep those components separate rather than describe all of them as one inference cost.

For deployment, consider a symbolic break-even relation. Let development and integration effort expressed in an appropriate common unit be `D`; let the retained artifact save `s` per future valid execution; and let it add maintenance expenditure `M` over its service life. The savings case requires `N × s > D + M`, where `N` is the number of applicable future executions. This is not an estimate for any paper. It explains why a modest improvement in a frequently executed kernel can justify substantial search, while a highly specialized prompt for a one-off task may not need permanent deployment at all. If quality changes, that quality difference must be assessed explicitly; a lower bill for an incomplete answer is not the same outcome.

Amdahl's law supplies the companion engineering relation. A component improved by a factor of1.23 reduces total runtime by about0.94%,3.74% or14.96% when it originally occupied5%,20% or80% of runtime, assuming the rest is unchanged. These are illustrative calculations, not estimates of Google's workloads. They show why the full-system bottleneck matters more than a visually impressive local speedup. AlphaEvolve's kernel and overall-training percentages are useful precisely because they report both levels.

## Adoption decisions

**For kernels, heuristics and well-specified programs, begin with a consequential editable interface.** A working seed, an objective that distinguishes useful candidates and correctness conditions that reflect the deployment make automated search productive. Preserve representative workloads separately from the examples used to direct search. Use the existing compiler and production implementation as the actual baseline. If the proposed change is already produced downstream by the compiler, evaluate the additional benefit it delivers rather than counting the same optimization twice.

**For reusable agents, change the component responsible for a recurring failure.** A missing source argument, an inaccurate tool contract or an inability to preserve a needed artifact has a concrete relationship to future task execution. Repairing it may transfer broadly. An instance-specific shell sequence or a paragraph that worked on one benchmark deserves a narrower home. Use the original trajectory to explain the cause, then look for the effect in work that did not create the proposed rule. If the reusable change does not help, keep the solved instance and remove the unnecessary generalization.

**For learned correction, define what a successful revision preserves.** Evaluate wrong-to-right and right-to-wrong transitions together with final accuracy. Train on states resembling the errors the policy will encounter. SCoRe's result supports a trained two-attempt policy where naïve reconsideration performed poorly. Extending the number of rounds changes the encountered states and needs its own evidence; it is a new policy decision, not a free consequence of calling the mechanism recursive.

**For prompt or workflow search, preserve the artifact with its model and task assumptions.** A compact discovered prompt can be practical to deploy. Its effect depends on model behavior, formatting, tools and the examples used to select it. A new model may make the old prompt irrelevant or harmful. Retain the useful analysis of why the prompt helped so that maintenance can repair the relevant behavior instead of accumulating more instructions around an obsolete one.

**Keep exploration and production choices distinct.** An archive may retain a weaker candidate because it contains a promising idea. Production should use the candidate that meets current requirements. Preserve the previous artifact and its associated model/runtime/inputs so that a regression can be reversed. Rollback is meaningful only when the former dependencies remain known; a name such as “previous best” is insufficient if the model or workload changed underneath it.

The strongest current opportunities are systems with recurring, valuable work and feedback closely tied to that work. Published results show real improvement in agent code, algorithms, prompts and correction policies. They also show failed transfer and harmful isolated substitutions. The useful product direction is to connect the editable object, evaluation target and retained artifact tightly enough that later tasks inherit a demonstrated capability. Recursion can accelerate that process when the parts it changes are genuinely useful; the evidence for progress comes from what those later tasks receive.

### Measurement details that change interpretation

- **DGM run units:** The paper's80generated-agent iterations and the public code's80outer generations with two candidate attempts are retained as separate descriptions. The reported empirical scores follow the paper's protocol.
- **DGM model contributions:** A separate o1diagnostic model contributes proposed improvements; the agent's frozen foundation model and fixed outer selection remain external to the changed code.
- **AlphaEvolve performance:** Local kernel speedup and overall training-time reduction are reported separately. The RTL example explicitly acknowledges an existing downstream synthesis optimization.
- **Promptbreeder ablation:** Population mean fitness over200evaluations is not the final held-out score. The GSM8K comparison uses the same PaLM2-L block of Table1, avoiding cross-model mixing.
- **SCoRe correction:**15.6points is the change in the MATH correction delta; the trained policy's second attempt adds4.4points. The MATH and coding experiments use different named Gemini checkpoints.
- **HarnessPro metric and expense:** ProgramBench averages test fractions, unlike binary task success on the other two benchmarks. Mean final-task execution cost is distinct from developing and selecting the package.
- **Rethinking selected versus available answers:** Pass@1 for the delivered choice and pass@5 for availability in a candidate set remain distinct. The printed table averages and one-decimal model values are retained rather than reconstructed into false precision. The observed held-out+0.6points is not a statistical-equivalence result.

These details are concentrated here so that the main argument can focus on mechanisms and decisions. They should travel with the corresponding claims when the comparison is reused.
