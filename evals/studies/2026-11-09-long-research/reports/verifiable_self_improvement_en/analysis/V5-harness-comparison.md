# Harness improvement: selecting a reusable change

Preserved research contribution V5, produced by `/root` from VSI003 and VSI004 and the inspected HarnessPro release. The full report will incorporate this analysis with the earlier code, program, prompt and weight comparisons.

## A changed harness needs a better feedback signal than its own change proposal

HarnessPro targets the instructions, tool behavior and runtime settings around an existing coding model. Its optimization team reads execution trajectories, diagnoses failures and proposes executable changes. The resulting harness is subsequently used to perform tasks; the development team's roles are not automatically a collection of agents launched for every downstream task. The retained artifact is a configuration and runtime package around the model, rather than new model weights. [HarnessPro v2, §§3–4](https://arxiv.org/html/2610.26770v2).

The important design decision is candidate selection. A model can write an articulate justification for a change that does not actually fix a task. HarnessPro generates tests from a task and the initial execution trajectory, freezes those tests, and uses execution against them to evaluate later candidates. Freezing keeps the evaluator from changing to agree with each candidate. Generated tests supply a reproducible signal where official task tests are unavailable during optimization. Their errors still matter: a mistaken assertion can repeatedly reject a correct candidate or reward a defect. The mechanism improves the consistency of feedback; the test's relationship to the intended task determines whether that consistency is useful.

The authors' preliminary comparison reports failure recall increasing from 41.7% for direct model judgments to 83.3% using generated tests. This is a failure-detection metric from that experiment, not a task success rate. The final benchmark results use official grading. That separation is a productive design: inexpensive surrogate feedback helps search, while a different evaluator measures the resulting system. [HarnessPro v2, §4.3 and Figure 2](https://arxiv.org/html/2610.26770v2).

The experiment separates three uses of tasks. Ten training tasks per benchmark drive candidate generation and evaluation, using three rollouts per task per epoch. Other non-test tasks form the validation set used to retain candidates. The held-out test sets contain 59 Terminal-Bench 2 tasks, 100 SWE-Bench Pro tasks and 100 ProgramBench tasks. Search runs for three epochs on the first two benchmarks and four on ProgramBench, retaining up to three harnesses after each epoch. The held-out score therefore concerns an artifact selected before those tasks were used for final grading. Validation remains part of selection: it should not be counted as a second independent final test. [HarnessPro v2, §5.1](https://arxiv.org/html/2610.26770v2).

The strongest reported configuration reaches 80.8% on Terminal-Bench 2, compared with RHO's 76.3%, using GPT-5.5 with Codex 0.147.0. Its mean execution cost per task is $0.72 versus $1.09. These measurements concern execution of the resulting harness. They do not include all development trajectories, candidate generation, synthetic-test generation and validation in one amortized total. A team adopting an already published artifact faces a different economic question from a team rerunning the optimizer for its own workload.

The score definitions also differ across benchmarks. Terminal-Bench and SWE-Bench Pro count tasks whose official tests all pass. ProgramBench averages the fraction of tests passed within each task, then averages those task fractions. A ProgramBench percentage must retain that meaning in comparison tables. An optimizer that solves half the checks in every reconstructed program could obtain a substantial partial-credit score while completing no program fully. This can still measure progress, but a deployment requiring complete reconstructions needs the all-requirements result as well.

## What the ablations support

HarnessPro's ablations make one practical conclusion unusually clear: copying the most visible runtime rule is a poor substitute for the evaluated combination. On SWE-Bench Pro, adding dynamic reasoning routing to RHO lowers its reported score from 80% to 76%; adding budget hooks produces 75%; fixing reasoning effort at low produces 59%. The full strongest HarnessPro configuration reaches 80.7%. The result favors the particular evolved package over those isolated substitutions in that setup. It gives a concrete reason to inspect a proposed rule's effect on successful task completion before making it a general default. [HarnessPro v2, Table 3](https://arxiv.org/html/2610.26770v2).

Removing the test synthesizer reduces the strongest configuration's Terminal-Bench score from 80.8% to 74.6% and its SWE-Bench Pro score from 80.7% to 72.0%. Removing the planner has smaller effects in those configurations. This is evidence that candidate feedback and planned edits contributed to the optimization procedure. It does not specify that every new product needs identically named roles. A product whose failures already have executable checks can use those checks directly; inventing another test generator would add a component without supplying the missing information.

The released repository contains selected harness artifacts, task splits and evaluation runtime. The inspected README describes reproduction of those artifacts' evaluation. It does not expose the whole candidate-producing optimization process as a runnable public system. The inspected terminal-medium runtime hook illustrates that some resulting policies are executable constraints: it counts tool uses and can deny additional tools after the configured finalization threshold. That is a more consequential behavior than a reminder appended to a prompt. The appropriate deployment question is whether the threshold preserves the steps required by the target task. The research result does not remove the need to answer that task-specific question. [HarnessPro public release](https://github.com/pzs19/HarnessPro).

## A controlled negative result identifies the alternative use of extra computation

The July 2026 study *Rethinking the Effectiveness of Automatic Harness Evolution* compares harness changes with additional attempts at the task. It uses Terminal-Bench 2.1, a revised 89-task suite, a shared initial AHE harness, a five-attempt budget and three models in the no-test setting. The AHE comparison uses one rollout per task per harness and disables its explorer component. These choices define the tested system; this is not a reproduction of HarnessPro's later optimizer. [Rethinking v1, §§3–4](https://arxiv.org/html/2607.12227v1).

Without available unit tests, parallel sampling averages 72.3% versus the initial harness's 68.2%, using a model to select the final candidate. The reported harness-evolution average is 67.4%. With tests available, parallel sampling reaches 86.0% selected-answer success; sequential refinement reaches 84.3% selected-answer success and 91.8% pass@5, while harness evolution reaches 75.8% and 86.2%, respectively. The candidate-set metric and the selected final-answer metric answer different operational questions. A correct candidate somewhere among five attempts helps only if it can be found or consumed by the downstream workflow.

The transfer experiment is more directly relevant to a reusable harness. It uses 45 training tasks, 10 validation tasks and 34 disjoint test tasks. Harness evolution produces held-out scores of 64.5% versus 63.3% for Claude Opus 4.6, and 72.1% for GPT-5.4 both before and after evolution: an average increase of 0.6 percentage points. The useful finding is small observed transfer under this protocol, rather than a claim that no harness can ever generalize. The paper's discussion proposes a model-capability bottleneck and limited benchmark sensitivity as explanations. Those explanations fit the observed failures but are not separately isolated by the experiment. [Rethinking v1, Table 3 and §5](https://arxiv.org/html/2607.12227v1).

This result changes the decision about what to retain. An extra attempt can discover the answer to a hard instance without revealing a reusable strategy. Persisting the command sequence, task-specific file paths or one error workaround into a general prompt may then increase future reading burden without increasing future capability. Conversely, fixing an interface that systematically loses an argument can help every task that uses it. Both changes may arise from a trajectory; the causal link between the failure and the edited component distinguishes them.

## Why the two studies can both be informative

The papers ask related questions with different experiments. HarnessPro uses new models, different task versions and splits, a dedicated generated-test mechanism, validation-based candidate retention and specific runtime artifacts. Rethinking fixes a smaller five-attempt protocol around an AHE scaffold and directly compares alternative uses of those attempts. Their percentages cannot be subtracted to estimate the advantage of one research team over the other. Their combination instead identifies two decisions that must be made explicitly: whether to spend effort on solving the present instance, and whether to retain a change for future instances.

A deployment decision can follow the intended artifact. For a one-off task, extra sampling or correction can be worthwhile even if nothing reusable remains. For a service with recurring tasks, a harness change is valuable when it corrects a repeated causal failure and survives relevant new instances. For an optimizer, a better selection signal can be more valuable than a more elaborate candidate generator. The practical progression is to identify the failure, locate the component able to change it, and ask the appropriate future-work question. A loop becomes productive through those relationships, not through recursion alone.

Neither study supplies a universal agent architecture. Together they provide a stronger engineering lesson: examine the exact feedback that chose an artifact and the work on which that artifact was later useful. Keep genuine reusable repairs, use temporary search for instance-specific difficulty, and avoid turning every successful workaround into permanent instructions.
