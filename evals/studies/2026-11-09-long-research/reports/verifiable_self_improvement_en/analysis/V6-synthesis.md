## The evaluator determines which improvements the search can find

### Correctness is a relationship to the intended task

An evaluator can execute perfectly and still reward the wrong behavior. A specification may omit a user requirement; a reference answer may contain an error; a performance benchmark may cover only convenient shapes; a simulator may omit a field constraint. Search then makes systematic progress on that surrogate. More evaluations make the wrong target more influential.

For program optimization, it helps to separate three levels. **Validity by construction** keeps an invariant outside the editable surface, as when a scheduler ranks only feasible hosts. **Testing** checks candidate outputs for selected inputs, including randomized and adversarial cases. **Complete verification of a defined finite or formal object** can establish a narrower proposition exactly, such as whether a particular mathematical construction satisfies specified equations. Their coverage differs. A passing numerical test suite is strong evidence for the inputs and tolerances it exercises; it is not automatically a proof of equivalence for every input supported by an API.

The engineering response follows the deployment obligation. A numerical kernel may need shape/dtype coverage, tolerance decisions, NaN behavior and hardware-specific checks. A scheduler needs the constraints and workload distribution of the actual fleet. A coding agent needs to preserve repository requirements beyond the hidden tests used for a benchmark. These concerns determine the evaluator and interface; they do not justify adding every possible check to every system.

Incorrect reference answers deserve special treatment because the system can be right for the wrong recorded score. When a selected candidate disagrees with a trusted implementation, the disagreement is an investigation target: inspect the intended specification, determine which result it implies, and preserve the original discrepancy. Quietly changing the oracle until the favorite candidate passes destroys the evidence for selection. Replacing an erroneous reference is legitimate when the underlying task supports the correction; the candidate must then be reconsidered against the corrected rule rather than awarded its former score unchanged.

### Adaptive reuse changes what a high score establishes

An evaluation set used repeatedly to choose candidates becomes part of the optimization process even if the model never sees its raw answers. Selection leaks information through which candidate survives. A large search can exploit a small systematic quirk or a lucky collection of examples. This is the practical meaning of adaptive overfitting: the best candidate on the reused set can be the one most fitted to that set's accidents.

DGM's adaptive coding pool and transfer results illustrate how to keep the questions separate. The optimization curve tells an engineer whether search is finding variants favored by its feedback. The cross-benchmark evaluation asks whether the selected agent retains useful behavior on another distribution. HarnessPro's validation set selects candidates and its held-out tasks evaluate the selected artifacts. Rethinking's45/10/34 split directly shows how apparent search progress can become only a small change on new tasks. These are different evidentiary roles, rather than stronger and weaker names for the same score.

The needed holdout should match the decision. A team changing an inference model needs evidence on that model; a team expanding to new repositories needs new repositories; a team entering a new task family needs that family. Merely reshuffling familiar prompts may test response variability while leaving the important distribution shift untouched. Conversely, an exact algorithm improvement need not outperform on unrelated natural-language tasks to be valuable. The future workload defines the relevant transfer claim.

Multiple candidate selection creates another asymmetry. A noisy high score is more likely to appear when many candidates are tried. The winning candidate should therefore be judged on evidence not used to make it the winner. This does not require hiding all useful feedback from the optimizer. Development feedback can be rich; the distinction is that final evidence for deployment must add information beyond the selection event. Three repeated measurements of a chosen artifact can characterize some rollout variation, while three independently optimized searches would address variability of the optimization procedure. Neither number should silently stand for the other.

### Reward exploitation can be local and ordinary

The most common failure need not look like a malicious system rewriting its reward. A prompt can teach answer-format tricks that a parser rewards. A test generator can overfit to the initial implementation's mistaken behavior. A runtime policy can make a tool-count metric look better by stopping before the required work is done. A kernel can exploit a benchmark's narrow shapes. In each case the artifact improves a measured quantity while losing something the user asked to retain.

SCoRe makes this problem concrete at the level of behavior. Rewarding final-answer correctness can encourage a strong first answer followed by copying, leaving no learned correction skill. Training against the distribution of the model's own errors and rewarding useful transitions changes the incentive. A similar principle applies to code and workflows: specify which properties must survive and which may improve. “More change” and “more confidence” are not substitutes for that transition.

The inspected HarnessPro hook also shows why a candidate's implementation matters. A budget reminder and a tool-denial threshold may have similar documentation but different consequences on a long task. Inspecting the executable path identifies whether the policy assists prioritization or removes the ability to perform a needed operation. The correct choice depends on the intended work. The ablations already show that copying a visible rule can reduce task success even while lowering its execution cost.

## Where candidate generation and evaluation each constrain progress

Improvement requires both finding a useful change and recognizing it. A stronger generator expands the candidate set; a better evaluator makes useful candidates more likely to survive. Increasing one does little when the other is the bottleneck. DGM's outside diagnostic model illustrates a contribution to finding changes. HarnessPro's generated tests illustrate an attempt to make candidate selection more informative. AlphaEvolve's application-specific evaluators make broad code generation manageable. SCoRe supplies the training feedback needed to make correction selective.

The balance differs by target. Generating a short prompt can be cheap relative to evaluating it across many tasks. Proposing a numerical kernel is quick relative to compiling, validating and profiling it on representative hardware. An agent change may require complete repository task executions to evaluate. Repeated evaluation can therefore dominate the work even when the model calls that generated the candidate are conspicuous. Public reports should keep those components separate rather than describe all of them as one inference cost.

For deployment, consider a symbolic break-even relation. Let development and integration effort expressed in an appropriate common unit be `D`; let the retained artifact save `s` per future valid execution; and let it add maintenance expenditure `M` over its service life. The savings case requires `N × s > D + M`, where `N` is the number of applicable future executions. This is not an estimate for any paper. It explains why a modest improvement in a frequently executed kernel can justify substantial search, while a highly specialized prompt for a one-off task may not need permanent deployment at all. If quality changes, that quality difference must be assessed explicitly; a lower bill for an incomplete answer is not the same outcome.

Amdahl's law supplies the companion engineering relation. A component improved by a factor of1.23 reduces total runtime by about0.94%,3.74% or14.96% when it originally occupied5%,20% or80% of runtime, assuming the rest is unchanged. These are illustrative calculations, not estimates of Google's workloads. They show why the full-system bottleneck matters more than a visually impressive local speedup. AlphaEvolve's kernel and overall-training percentages are useful precisely because they report both levels.

## Adoption decisions

**For kernels, heuristics and well-specified programs, begin with a consequential editable interface.** A working seed, an objective that distinguishes useful candidates and correctness conditions that reflect the deployment make automated search productive. Preserve representative workloads separately from the examples used to direct search. Use the existing compiler and production implementation as the actual baseline. If the proposed change is already produced downstream by the compiler, evaluate the additional benefit it delivers rather than counting the same optimization twice.

**For reusable agents, change the component responsible for a recurring failure.** A missing source argument, an inaccurate tool contract or an inability to preserve a needed artifact has a concrete relationship to future task execution. Repairing it may transfer broadly. An instance-specific shell sequence or a paragraph that worked on one benchmark deserves a narrower home. Use the original trajectory to explain the cause, then look for the effect in work that did not create the proposed rule. If the reusable change does not help, keep the solved instance and remove the unnecessary generalization.

**For learned correction, define what a successful revision preserves.** Evaluate wrong-to-right and right-to-wrong transitions together with final accuracy. Train on states resembling the errors the policy will encounter. SCoRe's result supports a trained two-attempt policy where naïve reconsideration performed poorly. Extending the number of rounds changes the encountered states and needs its own evidence; it is a new policy decision, not a free consequence of calling the mechanism recursive.

**For prompt or workflow search, preserve the artifact with its model and task assumptions.** A compact discovered prompt can be practical to deploy. Its effect depends on model behavior, formatting, tools and the examples used to select it. A new model may make the old prompt irrelevant or harmful. Retain the useful analysis of why the prompt helped so that maintenance can repair the relevant behavior instead of accumulating more instructions around an obsolete one.

**Keep exploration and production choices distinct.** An archive may retain a weaker candidate because it contains a promising idea. Production should use the candidate that meets current requirements. Preserve the previous artifact and its associated model/runtime/inputs so that a regression can be reversed. Rollback is meaningful only when the former dependencies remain known; a name such as “previous best” is insufficient if the model or workload changed underneath it.

The strongest current opportunities are systems with recurring, valuable work and feedback closely tied to that work. Published results show real improvement in agent code, algorithms, prompts and correction policies. They also show failed transfer and harmful isolated substitutions. The useful product direction is to connect the editable object, evaluation target and retained artifact tightly enough that later tasks inherit a demonstrated capability. Recursion can accelerate that process when the parts it changes are genuinely useful; the evidence for progress comes from what those later tasks receive.
