# On-Device Models: Hardware Constraints, Task Fit, and Edge–Cloud Design

Evidence cutoff: 9 November 2026. Author: Codex research producer `/root/ttc_research`. This is substantive author analysis; independent review is separate.

## 1. Choose a task envelope before choosing an accelerator

On-device inference is appropriate when a useful task can be completed with the memory, response time, operating duration and data access that a supported device can reliably provide. Its strongest uses have a bounded input, a short or structured output and information already present on the device: rewriting a message, extracting fields from a document, finding a passage, or transcribing nearby speech. A cloud model remains attractive for difficult synthesis, uncertain knowledge and sporadic requests whose quality requirement exceeds a small local model. Hybrid execution works when the local stage can reduce the information or work sent remotely without losing what determines the answer.

This is a joint quality and systems decision. A fast answer with an omitted contractual exception fails document assistance. An accurate transcription that arrives after a long utterance ends fails live captions. A small model that runs while a developer keeps an app open may fail the intended background experience. The right unit of comparison is a completed, acceptable task under its actual operating conditions.

Four representative configurations anchor this report. Samsung's Galaxy S24 Ultra has a Snapdragon 8 Gen 3 for Galaxy and a 12 GB memory configuration. The PC throughput evidence uses an M4 Pro with 16 GPU cores, 24 GB unified memory and 273 GB/s specified bandwidth; the paper does not identify its enclosure or OS build. A Surface Laptop 7th Edition with Snapdragon X Elite, 32 GB LPDDR5x and a 45-TOPS Hexagon NPU illustrates Windows integration. An actively cooled Jetson Orin Nano 8 GB illustrates a dedicated endpoint with sustained speech work. These devices are not placed on a common speed leaderboard. Their evidence answers different deployment questions. [Samsung S24 specifications](https://news.samsung.com/us/enter-new-era-of-mobile-ai-samsung-galaxy-s24-series/), [BaseRT, version 1](https://arxiv.org/html/2607.00501v1), [Surface specifications](https://learn.microsoft.com/en-us/surface/tech-specs/surface-laptop-snapdragon-tech-specs), [Jetson Super announcement](https://developer.nvidia.com/blog/nvidia-jetson-orin-nano-developer-kit-gets-a-super-boost/).

The report distinguishes documented capability, author or vendor measurement, independent research measurement, and calculated scenario. Published rates retain their model, runtime, precision and phase. The memory reservations, duty cycles, network speeds and financial assumptions below are explicit design scenarios. No new model inference benchmark was run for this report.

## 2. Memory is a working set, not a download size

A deployment needs enough usable memory for weights, quantization metadata, activations and temporary buffers, attention state, retrieval assets, the application and simultaneous system work. Storage answers whether a package can be downloaded. Installed RAM answers how much physical memory exists. The app's available budget answers whether its next request can finish. GPU residency and OS memory pressure can impose a tighter limit than either headline number.

For a dense model with P parameters and an ideal b-bit representation, raw weight storage is P × b / 8 bytes. Real formats include scales, zero points, alignment and tensors retained at higher precision. A runtime may duplicate or transform weights during loading; memory-mapped files and accelerator allocations also complicate process-memory readings. An operating system can reclaim cached pages, but repeated page faults into a large weight set can make a technically successful load unusably slow. Unified memory removes some explicit CPU-to-GPU copies; it does not give the model exclusive use of that memory or bandwidth.

Qwen2.5-3B-Instruct supplies a concrete architecture for calculation. Its official model card specifies 3.09 billion parameters and a 32,768-token context for this model, despite a broader family-level description of longer contexts. Raw weights occupy 5.756 GiB at 16 bits, 2.878 GiB at 8 bits, or 1.439 GiB at 4 bits. These are ideal byte counts, not measured resident footprints or proof that a particular quantized artifact preserves quality. [Qwen model card](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct/blob/main/README.md).

For an ordinary full-attention decoder, an uncompressed KV cache requires:

`KV bytes = 2 × layers × KV heads × head dimension × bytes per element × cached tokens × batch size`.

The factor two represents keys and values. Qwen's configuration has 36 layers, 16 query heads, two KV heads and a hidden dimension of 2,048, giving a head dimension of 128. With two-byte KV elements and one sequence, each cached token needs 36,864 bytes, or 36 KiB. The cache therefore occupies 144 MiB at 4,096 tokens, 288 MiB at 8,192 and 1,152 MiB at 32,768. The configuration disables sliding-window attention, so the presence of a `sliding_window` field is not a reason to cap this calculation. Input, retained history, tool results and generated output all consume the context budget. [Official Qwen configuration](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct/blob/main/config.json).

Grouped-query attention reduces the number of stored KV heads relative to query heads. KV quantization reduces bytes per stored element, with metadata and kernel costs, and requires its own quality evaluation. A sliding window bounds attention state only when the architecture and runtime actually implement that policy. Shared caches can reduce the number of independently stored layers. Apple's 2025 architecture, for example, shares the second block's KV state with the last layer of the first block, reducing KV memory by 37.5% relative to its stated unshared design. None of these changes implies that every model with the same parameter count has the same cache size. [Apple 2025 technical report, §§2 and 6](https://arxiv.org/pdf/2507.13575v1).

The following worksheet deliberately separates a memory calculation from a device measurement. Assume the S24 application can safely allocate a **4 GiB task budget after other device usage**. This is a proposed admission limit, not a documented Android entitlement. Reserve 1.8 GiB for a 4-bit Qwen artifact and its weight overhead, 0.6 GiB for working buffers, 0.25 GiB for a resident embedding model, 0.35 GiB for application/text assets, and 0.5 GiB for headroom. Ten thousand 384-dimensional FP16 vectors need 7.68 MB; allowing another 50% for an illustrative index structure produces 11.52 MB, or 10.99 MiB. Actual text, document files and metadata must be budgeted separately within the app reservation or on disk.

| Total cached tokens | BF16 KV | Planned phone working set, including 0.5 GiB headroom | Margin under 4 GiB |
|---|---:|---:|---:|
| 4,096 | 144 MiB | 3.651 GiB | 0.349 GiB |
| 8,192 | 288 MiB | 3.792 GiB | 0.208 GiB |
| 32,768 | 1,152 MiB | 4.636 GiB | Exceeds by 0.636 GiB |

The practical choice is a bounded 4K–8K request, with output space reserved before generation. A full 32K context is outside this example's allocation even though the model accepts that length. If the embedding model can be unloaded before generation, it returns 0.25 GiB; if retrieval and generation must overlap, it cannot. Raising precision also changes the decision: using an assumed 3.6 GiB 8-bit weight reservation adds 1.8 GiB. That version fits a separately assumed 10 GiB PC task budget at 5.592 GiB for 8K tokens or 6.436 GiB for 32K, leaving room for the rest of the desktop workload. Those calculations do not transfer the S24's Gemma measurements to Qwen or predict Qwen throughput.

This is how memory affects product behavior. Admission should consider the current available budget and the complete request, not only whether a model is installed. Under pressure, reduce retrieved material, release an idle model, choose a smaller supported artifact or queue the work. A privacy-required offline task should retain a source browser and extraction path when generation cannot fit. A silent cloud upload is not a memory-management strategy.

## 3. What makes inference fast, and what quality is traded away

Prefill processes the prompt and builds attention state. It can exploit parallel work across input tokens, so matrix throughput and efficient kernels matter. Decode generates tokens sequentially. At small batch sizes, repeatedly reading weights and attention state can dominate; reducing their bytes can help more than a larger nominal arithmetic rating. Launch overhead and CPU coordination matter especially for small models. Long contexts increase attention work and state traffic, so decode speed can deteriorate as a session grows.

CPU, GPU and NPU are different execution paths. A CPU has broad operation support and convenient integration. A GPU offers parallel matrix and attention kernels, but shares resources with display and other applications. An NPU can execute supported low-precision graphs efficiently, while unsupported operations, shape restrictions and transfer boundaries may undermine the expected benefit. ONNX Runtime's QNN HTP documentation requires quantized models and fixed rather than dynamic shapes for the documented path; it also provides an option to reject CPU fallback. A model that loads through an NPU-enabled library is not evidence that its whole critical path executes on the NPU. [ONNX Runtime QNN documentation](https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html).

Weight quantization primarily reduces weight storage and traffic. Activation quantization changes intermediate representation and arithmetic. KV quantization targets the state that grows with context. Distillation changes the model's learned function and capacity; it may preserve a narrow task better than broad reasoning. Pruning or sparse activation reduces useful work only if the runtime avoids the removed work. In a mixture-of-experts model, few active parameters per token can reduce computation, while many experts still require storage or costly paging. Gemma 3n's effective-parameter design likewise distinguishes total parameters from the portion kept active through parameter skipping and cached per-layer embeddings. Its E2B designation should not be used as a two-billion-parameter full-package memory estimate. [Gemma 3n overview](https://ai.google.dev/gemma/docs/gemma-3n).

Quantization quality depends on how the representation is obtained. AWQ uses activation statistics to scale important weight channels before quantization and couples the representation to packing, dequantization and fused kernels. Its central lesson is that numerical compression and implementation must be designed together. The reduction in bytes is an opportunity for acceleration, not a guarantee across backends. [AWQ, version 5, §§3–4](https://arxiv.org/html/2306.00978v5).

Meta's Llama 3.2 release gives a useful within-family example. For the 3B instruction model, its model-card MMLU result falls from 63.4 in BF16 to 60.5 for vanilla PTQ, versus 62.0 with SpinQuant and 62.4 with its QAT/LoRA method. On the separate Open-rewrite metric, the BF16 score is 40.1 and the QLoRA score is 40.7. These results support task-specific evaluation: a compression path that slightly improves one rewrite score can still lose general knowledge accuracy. Meta's scheme also retains different tensors and LoRA components at different precisions, so its package cannot be represented as uniformly four-bit. [Llama 3.2 model card, quantization and instruction-tuned evaluation tables](https://github.com/meta-llama/llama-models/blob/main/models/llama3_2/MODEL_CARD.md).

Apple's July 2025 technical report illustrates a more aggressive system-level trade. It combines two-bit decoder weights, four-bit embeddings, eight-bit KV state and recovery adapters. Table 3 reports on-device MMLU moving from 67.8 to 64.4 and IFEval from 85.1 to 82.3 after the stated optimization bundle. The relevant judgment is that a compact, integrated model can be useful for supported text tasks while retaining a measurable quality cost. These July report values are not silently substituted for later Apple model revisions. [Apple technical report, §6 and Table 3](https://arxiv.org/pdf/2507.13575v1).

### Phase evidence from a phone and a PC

The fixed LiteRT-LM README commit of 21 July 2025 reports 1,024 prefill tokens and 256 decode tokens, with a 4,096-token configured context for the following S24 Ultra rows. The artifacts use four-bit per-channel weights. This is vendor runtime evidence; the table does not supply an OS build, thermal history, repeated-run confidence interval or task-quality result. Its phase comparison is nevertheless informative. [Pinned LiteRT-LM benchmark table](https://github.com/google-ai-edge/LiteRT-LM/blob/eaa380eee74b677f9f305eb2a92ae0fcc14ffc39/README.md).

| S24 Ultra model and backend | Prefill tokens/s | Decode tokens/s | Calculated 1,024-token prefill | Calculated phase sum with 256 output tokens |
|---|---:|---:|---:|---:|
| Gemma 3n E2B, CPU | 110.5 | 16.1 | 9.27 s | 25.17 s |
| Gemma 3n E2B, GPU | 816.4 | 15.6 | 1.25 s | 17.66 s |
| Gemma 3 1B, GPU | 1,876.5 | 44.57 | 0.55 s | 6.29 s |

Switching E2B to the GPU dramatically reduces prompt processing while decode remains similar and is slightly slower in the reported row. For a 128-token reply, the same rate calculation gives 9.46 seconds on the GPU; projecting to 512 output tokens gives 34.07 seconds. The latter extrapolates beyond the table's 256-token decode run. These phase sums omit loading, tokenization, queueing, first-token bookkeeping and rendering; they are planning calculations, not observed end-to-end latency. The smaller Gemma 3 1B may be the better choice for short transformations if it meets the task's quality bar. Increasing model capacity is worthwhile only when its improved answer quality compensates for longer waits and greater memory use.

BaseRT's 2026 paper offers a separate PC comparison. On its M4 Pro configuration, Llama 3.2 3B Q4 decodes 128 tokens at 117.3 tokens/s, versus 102.4 for llama.cpp b9630 and 112.1 for MLX 0.31.2. At a 2,048-token prompt, BaseRT prefill is 835 tokens/s and llama.cpp is 864. Summing the separate BaseRT rates gives a 2.45-second prefill and 1.09-second 128-token decode. This 3.54-second phase sum is not a measured combined request; the benchmark phases and cache lengths need not coincide. The evidence supports fast short local tasks on this PC class, and shows that a runtime can win decode while losing prefill. It does not establish universal runtime leadership: MLX is faster on the paper's Gemma 4 26B-A4B Q4 decode row, 69.3 versus 62.2 tokens/s. [BaseRT, §4 and Tables 1–3](https://arxiv.org/html/2607.00501v1).

### Sustained operation changes the feasible task

MELT provides independent evidence about the gap between a successful mobile run and a stable experience. With Zephyr 3B four-bit on an iPhone 14 Pro, its 50-prompt continuous experiment, repeated three times, shows degradation from the start and further changes around prompts 20 and 32. Its Jetson AGX comparison is smoother at a 50 W setting. The study also reports app termination, unresponsiveness and device restarts under some configurations. These older devices and runtimes establish mechanisms to account for, rather than a temperature or slowdown forecast for the S24. [MELT, version 4, §§5.2–5.3](https://arxiv.org/html/2403.12844v4).

A passively cooled phone should therefore favor short, cancelable bursts and explicit limits on concurrent models. A desktop or actively cooled edge box can serve longer duty cycles if measured at the intended ambient temperature and cooling configuration. A useful sustained criterion is that the latency distribution, memory use and queue depth remain acceptable for the duration of the workload, while the rest of the device remains responsive. Peak TOPS, a first warm response, and a fan's presence each describe only part of that criterion.

## 4. Private document assistance: keep retrieval close to the source

The most defensible local document assistant starts with retrieval and verifiable extraction. It does not ask a small model to read an entire personal archive in one prompt. A useful pipeline is:

```text
Local files → parsing / OCR → chunks with source locations → local embeddings / index
                                                            ↓
Question → retrieval → optional reranking → bounded evidence → answer + source spans
                                                            ↓
                                            citation and field validation → user
```

Each stage changes the quality envelope. OCR can lose a minus sign or a table heading before generation begins. Chunking can separate a clause from its exception. Retrieval can miss the decisive passage. A fluent response cannot recover evidence it never received. The system should retain page and span identifiers, present the supporting text, and distinguish extraction from synthesis. Exact identifiers and dates can be checked directly against source spans; a plausible summary requires a stronger semantic check.

The 10,000-vector worksheet in Section 2 is a modest local collection, not a claim that all its documents fit in model context. With a 4,096-token session, an example budget is 500 tokens for instructions and the question, 2,500 for selected passages, 300 for source labels and other framing, and up to 700 for the answer. That consumes 4,000 tokens and leaves a small margin. A phone can perform short, cited questions within this envelope if its model meets the domain's extraction quality target. The product should show the retrieved passages when it cannot produce a reliable answer. It should not replace missing evidence with the model's remembered facts.

A PC's larger usable working set makes a higher-precision small model, a reranker, or more context practical. It does not automatically make a 32K prompt the best design. Reading thousands of irrelevant tokens lengthens prefill, expands state and may make a small model less reliable. Use longer context when the task genuinely depends on it: reconciling a short series of related documents, checking several contractual conditions, or summarizing a complete technical note. Use retrieval and selective expansion for a large archive. The decision is governed by evidence coverage and answer quality rather than by filling the advertised context window.

For complex synthesis, a hybrid pipeline can keep parsing, indexing and selection local while sending approved excerpts to a stronger model. This is especially useful when a large file contains only a few passages relevant to the question. Suppose a 20 MB document would otherwise be uploaded over a 10 Mbit/s uplink. Payload transmission alone takes 16 seconds; at 1 Mbit/s it takes 160 seconds. Sending a selected 40 kB excerpt over the 10 Mbit/s link takes 0.032 seconds before transport overhead, round trips and inference. The calculation uses decimal bytes and assumes available throughput, not a promised network rate. If the document is already cached remotely, this first-upload advantage disappears; if offline operation or a strict local boundary is required, the remote route remains unavailable regardless of bandwidth.

The remote model still receives the excerpt's content. A summary can reveal a diagnosis, account balance or identifying event even when it omits the original document. Embeddings and extracted entities also remain data derived from the source. A useful hybrid design has a visible rule about which material may leave, applies that rule before constructing the outbound request, and keeps a local-only route with narrower capabilities. Calling an exchange “compressed” does not establish privacy.

### What collaborative document reasoning actually demonstrates

The final ICML 2025 Minions paper tests collaboration on FinanceBench, LongHealth and QASPER. Its stronger protocol decomposes work into simpler local jobs and coordinates them remotely, exploiting local parallelism rather than relying on one small model to solve the entire problem. This is a positive architectural result: carefully chosen local subtasks can reduce remote communication while preserving much of a stronger model's task performance. [Minions final paper, §§4–6](https://raw.githubusercontent.com/mlresearch/v267/main/assets/narayan25a/narayan25a.pdf).

Table 1 reports macro-average accuracy of 0.724 for remote-only GPT-4o and 0.709 for Minions with a Llama 8B local model. The corresponding average cloud charges are $0.233 and $0.042 per query. From the rounded table values, the collaborative system retains 97.9% of baseline accuracy at 18.0% of the cloud charge: an absolute accuracy loss of 1.5 percentage points and a 5.55-fold reduction in that charge. Local-only Llama 8B reaches 0.444. Thus the result supports coordinated assistance by the stronger model; it does not imply that an 8B local model alone provides remote-model quality. The paper uses January 2025 GPT-4o prices and treats local inference as free for this accounting. [Minions final paper, §3 and Table 1](https://raw.githubusercontent.com/mlresearch/v267/main/assets/narayan25a/narayan25a.pdf).

The latency result further clarifies where to apply this pattern. On ten LongHealth examples with an RTX 4090 local GPU, Table 2 reports 31.81 seconds for the 8B Minions system versus 11.00 seconds for remote-only. Those are workstation experiments, not phone measurements. A user willing to wait for a document analysis may accept the extra local work; a short interactive rewrite may not benefit. A phone with little parallel capacity cannot inherit the paper's batching advantage. The report also leaves formal privacy guarantees to future work. Its measured cost-quality frontier is evidence for a collaboration mechanism, while data disclosure, device energy and deployment cost still need their own accounting. [Minions final paper, §6.5, Table 2 and discussion](https://raw.githubusercontent.com/mlresearch/v267/main/assets/narayan25a/narayan25a.pdf).

For the selected hardware, the recommended progression is local retrieval and extraction on the phone, richer local evidence processing on the PC, and optional remote synthesis when quality requires it and the data policy allows it. The task contract should say what happens when extraction confidence is low or sources disagree: expand retrieval, show conflicting spans, request a human decision, or escalate within the permitted boundary. A model's uncalibrated confidence statement alone is insufficient to decide that escalation.

## 5. Interactive generation: optimize the useful response

Interactive text generation contains at least three different products. A rewrite transforms text that the user already supplied. A short dialogue uses a bounded application state. A general assistant must acquire facts, reason through unfamiliar tasks and sometimes invoke tools. Small local models are well aligned with the first two when the prompt is narrow. The third often benefits from a stronger cloud model, even if the network adds delay.

Apple's 2025 framework was explicitly designed around tasks such as extraction, summarization, refinement and short dialogue rather than general world-knowledge chat. Guided generation can make a response conform to a Swift data structure; it cannot establish that the fields contain true facts or that a proposed action is appropriate. This matters for local application design: a typed draft calendar event is useful if the user can inspect its date and location, while silently executing an uncertain action creates a different quality requirement. [Apple technical report, §7](https://arxiv.org/pdf/2507.13575v1).

The S24 results suggest a practical response design. A 128-token Gemma 3n E2B answer has a calculated warm phase sum of about 9.46 seconds with the cited 1,024-token GPU prefill; 512 tokens raises that extrapolated sum to about 34.07 seconds. Asking for a compact rewrite or a few extracted fields therefore improves responsiveness directly. Streaming makes progress visible but does not eliminate the total wait. A user may accept a first partial sentence quickly while still waiting for a final answer that can be validated or acted on. For structured actions, distinguish first visible output from the time when the complete validated object is usable.

The full timing model should be:

`time to usable result = queue + cold setup, if any + input preparation + prefill + generation + validation + presentation`.

Cold setup includes reading weights, allocating buffers, compiling kernels or building an accelerator engine. It may also include a first model download, which is a separate onboarding event rather than an inference latency. A 3 GB package takes at least four minutes over an otherwise available 100 Mbit/s connection, or forty minutes at 10 Mbit/s, before protocol overhead and verification. Keeping a model warm avoids some setup but occupies memory and may compete with the foreground app. A product should load deliberately, show readiness, cancel obsolete work, and release resources when the expected reuse no longer justifies residency.

Conversation history presents a second design choice. Appending every message preserves detail but increases prefill or cache occupancy. Reusing a valid prefix avoids repeating work, whereas changing earlier instructions or replacing history may invalidate it. Summarizing history can reduce state but may omit constraints or facts; the summary should retain structured commitments and link back to source messages when exact wording matters. Sliding attention and retrieval over prior messages are alternatives with different information-loss patterns. They should be evaluated on the kind of long conversation the product actually offers.

A practical router first checks policy and device readiness, then task difficulty and resource state. An offline-required rewrite goes to a ready local model or a simpler deterministic editing UI. A sensitive question can use local retrieval and return supporting passages when the local generator is inadequate. A difficult, nonsensitive analysis can go directly to the cloud when a local attempt would merely add delay. If the product uses a cheap local first attempt, escalation should depend on observable validation failures, missing evidence or a calibrated task classifier. Repeatedly asking the same small model to reconsider is not a reliable substitute for missing capacity.

The M4 Pro is a stronger candidate for a richer local assistant than the phone because it can accommodate larger working sets and the cited 3B runtime produces short outputs quickly. The Surface case is promising for tightly integrated NPU text transformations, but the available sources do not provide a matched throughput result against that Mac. Its 45 TOPS should guide neither a token-rate prediction nor a battery-life claim. A Windows product can choose the system model for supported tasks and an explicitly supported custom runtime for other models, retaining separate quality and performance qualifications for each path.

## 6. Frequent speech: make the entire pipeline continuous

Speech is a strong local candidate when the input is persistent, network availability is uncertain or raw audio should remain nearby. The relevant pipeline is broader than the recognizer:

```text
Microphone → capture / resampling → VAD → bounded chunks with overlap
                                         ↓
                                    speech recognizer
                                         ↓
                           overlap reconciliation / punctuation
                                         ↓
                         partial text → stabilized transcript → application
```

Capture and voice activity detection run even when no words are produced. Endpointing decides how long to wait before treating speech as complete. Overlapping chunks improve continuity but repeat computation. Punctuation, speaker attribution and application-level commands can require additional models. A product may need a small first-stage recognizer for immediate feedback and a later correction stage, or it may prefer an utterance-based result for voice commands. These are different latency targets.

WhisperTRT provides a concrete optimization result for an Orin Nano. At the fixed October 2024 repository commit, its README reports 0.86 seconds to transcribe a 20-second clip with `base.en`, compared with 2.55 seconds for the original Whisper backend. The corresponding reported memory figures are 439 and 666. Inspecting the code clarifies those figures: the profiling script runs a warmup, times one transcription by default, synchronizes the GPU around timing, and records the change in process RSS after execution. Its bit shift converts bytes to MiB, despite the README's MB label. Engine construction and model loading happen outside the timed call. The 439 MiB value is therefore a sampled RSS difference, not peak device memory. [Pinned WhisperTRT README](https://github.com/NVIDIA-AI-IOT/whisper_trt/blob/268eff10a1e38118a2734745b9db14f7419a08a5/README.md), [profiling code](https://github.com/NVIDIA-AI-IOT/whisper_trt/blob/268eff10a1e38118a2734745b9db14f7419a08a5/examples/profile_backend.py).

The rate result is encouraging: 0.86/20 gives a clip real-time factor of 0.043, leaving substantial compute headroom for a single stream under those benchmark conditions. The timed `transcribe` path includes its mel-spectrogram preparation and decoding; it does not include recording twenty seconds of future speech. A linear projection would require 154.8 seconds of recognition computation per hour of audio without overlap, or twice that with twofold repeated processing. This projection describes arithmetic capacity, not a measured continuous service, energy result or latency distribution.

The source code also identifies a concrete integration limit. This WhisperTRT path pads audio and truncates the mel representation to Whisper's 30-second window, then uses greedy argmax decoding. The example live program collects VAD-defined speech and sends a segment only after speech ends. It is consequently a useful utterance-transcription demonstration, but not a complete streaming-caption implementation. For uninterrupted long speech, the product needs bounded segmentation and overlap reconciliation before inference; otherwise material beyond the model window can be lost. Decoding options are not normalized across the compared backends, so the speed ratio is a result for the published paths, not proof of equal WER. [WhisperTRT model implementation](https://github.com/NVIDIA-AI-IOT/whisper_trt/blob/268eff10a1e38118a2734745b9db14f7419a08a5/whisper_trt/model.py), [live example](https://github.com/NVIDIA-AI-IOT/whisper_trt/blob/268eff10a1e38118a2734745b9db14f7419a08a5/examples/live_transcription.py), [Whisper audio constants](https://github.com/openai/whisper/blob/main/whisper/audio.py).

A useful deployment target for voice commands might permit utterance-end processing, while live captions require a bound on partial-text delay. In the latter design, use short rolling chunks, maintain an explicit maximum queue depth, and revise only an identified unstable suffix of the transcript. If recognition falls behind, preserving audio for later processing may suit a recorder; dropping old work to retain freshness may suit a live display. The choice follows the task. An always-on recorder must also specify whether audio is retained at all, for how long, and who can retrieve it.

### Precision, noise and energy change the speech choice

An independent 2024 study on an actively cooled Orin Nano 8 GB used JetPack 5.1, seventy LibriSpeech clips of roughly three to five seconds, and a separately corrupted version with added Gaussian noise. It measured incremental CPU-plus-GPU energy using `tegrastats`, after subtracting an idle baseline. Its noise procedure attenuated generated noise by 10 dB; this is not enough information to call the resulting speech a calibrated 10 dB SNR corpus. [ASR energy study, setup pp.4–7](https://arxiv.org/pdf/2405.01004).

Its Table 4 contains a useful counterexample to automatic gains from lower precision:

| WhisperX base, same study | Aggregate processing time | Reported memory | Incremental CPU+GPU energy | Clean WER | Noisy WER |
|---|---:|---:|---:|---:|---:|
| FP16 | 78.0 s | 4,029 MB | 155 J | 7.40% | 28.84% |
| INT8 | 80.1 s | 3,908 MB | 169 J | 7.83% | 30.69% |

Here INT8 saves about 3.0% of reported memory while taking 2.7% longer and consuming 9.0% more of the measured energy. Noisy WER rises by 1.85 percentage points. FP16 is the stronger choice for this model and experiment unless the memory saving is decisive. Other rows show different trade-offs, including lower energy for the medium INT8 model, so the result is not a universal rejection of INT8. The baseline-subtracted energy is not whole-box wall power, and these aggregate results are not commensurate with the WhisperTRT single-clip benchmark. [ASR energy study, Table 4, p.10](https://arxiv.org/pdf/2405.01004).

The selected edge device also has distinct operating versions. NVIDIA's later Super configuration advertises 102 GB/s bandwidth, 67 sparse TOPS and a 25 W module mode, with a supporting JetPack update. The earlier speech studies do not thereby become measurements of the Super mode. Higher clock and power options can enlarge the available throughput envelope, while cooling, power supply and the installed software remain part of the product configuration. [NVIDIA Super configuration and software requirements](https://developer.nvidia.com/blog/nvidia-jetson-orin-nano-developer-kit-gets-a-super-boost/).

For planning, assume an entire endpoint draws 4 W while idle and 15 W while actively computing. These are scenario inputs, not measured Orin power. Average power is `4 + duty × (15 − 4)` watts. At 10%, 50% and 100% compute duty, that gives 5.1, 9.5 and 15 W, or 0.1224, 0.228 and 0.360 kWh per day. The calculation concerns compute duty, not the fraction of time someone speaks: a recognizer faster than real time can process continuous audio with intermittent compute, while overlap, VAD, postprocessing and other workloads increase its occupancy. Keeping those quantities separate prevents an incorrect battery or cooling estimate.

| Assumed active whole-device power | 10% compute duty | 50% compute duty | Continuous computation |
|---|---:|---:|---:|
| 10 W, with 4 W idle | 4.6 W average | 7.0 W | 10.0 W |
| 15 W, with 4 W idle | 5.1 W | 9.5 W | 15.0 W |
| 25 W, with 4 W idle | 6.1 W | 14.5 W | 25.0 W |

A constrained edge box is thus attractive for frequent local speech when an appropriate recognizer passes the noise and vocabulary target, the pipeline bounds segment length, and sustained operation leaves queue and thermal headroom. Use the cloud for occasional difficult recordings, broad language coverage or stronger diarization when the data boundary permits it. A hybrid speech product can keep the raw stream local and send selected transcripts for reasoning, or upload only user-selected uncertain segments for re-recognition. The first reduces audio transfer but still discloses transcript content; the second requires consent to move the audio itself.

Vision follows the same whole-pipeline principle but cannot inherit speech throughput. Camera capture, exposure, resize, color conversion, frame selection, detection and tracking all consume resources. Raw 1,920×1,080 RGB frames at 30 frames/s represent about 186.6 MB/s before compression. That arithmetic supports local filtering or selecting relevant frames before transfer, not an inference-rate claim. For a continuous visual function, a compact detector or tracker at a reduced frame rate can be a better fit than repeatedly invoking a multimodal language model on every frame. A richer model can handle selected events locally or remotely after the time-critical stage has acted.

## 7. Architecture determines the privacy boundary and the operating contract

Local processing changes who must receive the input. In a genuinely local document or speech path, no inference provider needs the raw material. The remaining boundary includes the device, operating system, application, local model files and any tools the model invokes. The application can still transmit sensitive information through logs, analytics, crash reports, synchronization, backups or a remote tool. A local model does not make those separate paths disappear.

The useful comparison follows the data through the actual task:

| Architecture | Documents | Interactive text | Speech | Data boundary to state explicitly |
|---|---|---|---|---|
| Local-only inference | Parse, index, retrieve and answer locally | Prompt and history remain local | Capture and recognition remain local | Whether files, outputs, embeddings and logs are synchronized; which local accounts can access them |
| Cloud-only inference | Upload document or passages and query remotely | Send prompt, relevant history and tool results | Upload or stream audio for remote recognition | Provider, endpoint, region where configured, retention controls, application storage and deletion behavior |
| Hybrid | Local retrieval, remote synthesis of approved evidence | Local easy tasks, remote difficult tasks | Local recognition, optional remote reasoning or segment correction | Exactly which excerpts, transcripts, metadata or audio cross the boundary, and when fallback is allowed |

A privacy-preserving fallback must maintain the promise attached to the task. If a user selects “this material stays on this device,” a memory shortage or model failure should produce a local alternative, a queued task or an explicit inability to complete. For a user who permits remote processing, the app can show the scope of the outbound data and apply the chosen policy. A narrowly scoped transfer can reduce disclosure, but redaction requires care: removing names while preserving a rare combination of events may still identify someone.

Cloud privacy properties also differ. OpenAI's API documentation says API data is not used for training by default, while its standard abuse-monitoring logs can retain customer content for up to thirty days, subject to the stated exceptions. Application-state retention depends on the endpoint and feature; approved retention controls have their own eligibility and limitations. Therefore “not used for training” and “not retained” answer different questions. A product needs the policy of the endpoint and configuration it actually uses. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data).

Apple's Private Cloud Compute describes a different technical architecture: requests are encrypted to validated compute nodes, processed under restrictions on privileged access, and designed not to retain personal request data after completion. The public security design also describes software transparency and limits on logging. This extends the trusted processing boundary to a specific cloud architecture; it does not mean the task runs offline or that arbitrary third-party tools inherit those properties. Application logs and a tool that calls a separate service remain separate data paths. [Apple PCC security architecture](https://security.apple.com/blog/private-cloud-compute/).

### System APIs can reduce integration work, within their supported scope

System-managed models can share a download, use a tuned runtime and provide structured generation or application-specific capabilities. They also bring eligibility checks, version changes, quotas and platform rules. Custom runtimes offer greater control over model choice, distribution and offline behavior, while requiring the app owner to manage those concerns.

Apple's on-device Foundation Models API is documented from OS version 26 on its supported platforms. The app should check model availability, Apple Intelligence support, downloads and enabled state. Current documentation separately exposes PCC through a managed entitlement on the version-27 platforms it lists, with daily usage limits and a 32K context, compared with the on-device model's 4K context. A shared programming interface does not erase the difference in network dependence or data movement. The current API page is a stronger integration basis than treating a conference demonstration alone as a deployed entitlement for every app. [Foundation Models documentation](https://developer.apple.com/documentation/foundationmodels), [availability](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel/availability-swift.property), [PCC integration and eligibility](https://developer.apple.com/documentation/foundationmodels/adding-server-side-intelligence-with-private-cloud-compute).

For Android, ML Kit's November 2026 GenAI documentation lists device support by feature and model generation. The selected S24 Ultra's ability to run a custom LiteRT-LM artifact does not establish its eligibility for these system APIs. The same page permits GenAI inference only while the app is the top foreground application and explicitly blocks use from a foreground service when the app is not foreground. It also documents short-term busy responses and a per-app battery-use quota. A background speech product cannot assume the foreground GenAI API is its always-on engine; it needs a suitable speech API and operating-system execution arrangement for that use. [ML Kit GenAI overview, device support, quotas and background use](https://developers.google.com/ml-kit/genai).

On Windows, the current Phi Silica page documents a Limited Access Feature and excludes China. Its NPU path is available on Copilot+ PCs; the described GPU path requires an Insider build and experimental App SDK. The page also announces Aion Instruct's November 2026 Insider transition and a January 2027 retail replacement. As of this report's cutoff, the future retail date is a plan, and the November rollout should not be assumed present on every device. For the selected Surface, check the actual model, feature readiness and release channel. Preserve a working supported route while qualifying a replacement and its adapters. [Phi Silica documentation, updated 19 October 2026](https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica).

A custom NPU route adds graph conversion and calibration work. The documented QNN path requires supported operations, quantized inputs and fixed shapes. Exporting an ONNX file is only the start: the deployed graph must compile, place its intended work on the accelerator and preserve quality on real inputs. CPU fallback can be appropriate for a small unsupported operation, but a fallback across much of the graph can change power and latency substantially. The backend placement should therefore be part of the measured configuration, alongside the model artifact and driver. [QNN execution provider](https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html).

Updates are part of the operating cost. A custom model changes its tokenizer, template, stop conditions or output behavior as well as its weights. A system model can change without the app selecting a new download. Apple's 2025 adapter toolkit ties each adapter to a specific base-model version, so an adapter is an ongoing compatibility obligation. For either approach, retain version-aware prompts and task examples, qualify the update on supported device classes, and provide a practical rollback or feature-disable path where the platform permits one. This is particularly important when correctness means preserving a number, a source citation or a spoken command, rather than simply generating plausible prose. [Apple technical report, §7](https://arxiv.org/pdf/2507.13575v1), [Apple model availability and version checks](https://developer.apple.com/documentation/foundationmodels/detecting-available-apple-foundation-models).

## 8. Count accepted tasks, device ownership and integration work

An existing phone or PC can make local inference inexpensive at the margin. The full purchase price is not attributable to a feature that uses spare capacity on hardware the user already owns. Conversely, a required memory upgrade, dedicated endpoint or new cooling arrangement is incremental. Energy, battery use, distribution, engineering, qualification, support, correction and fallback remain costs even when no provider invoices a token.

A useful accounting model is:

`cost per accepted task = (annualized incremental hardware + annualized implementation + annual support + energy + distribution/network + remote calls + correction cost) / accepted tasks`.

The numerator and denominator must cover the same period and workload. A failed task that falls back to the cloud incurs both paths. A task returned with an unnoticed error should not enter the accepted denominator merely because the application displayed an answer. Evaluation should reflect the product's acceptance criteria and the actual distribution of requests. In speech, WER is useful but a wrong command or a missed medical name can matter more than an average word error; in documents, a correctly formatted but unsupported answer is still a failure.

### An existing-device application: when engineering dominates

Consider an explicitly hypothetical deployment with $120,000 of custom local engineering amortized over three years and $24,000 of annual maintenance, qualification and support: $64,000 per year. A cloud integration uses $15,000 amortized over three years plus $6,000 annually: $11,000 per year. Suppose a cloud task costs $0.01, 20% of local attempts require one cloud fallback, and a local attempt uses an incremental 5 W for twenty seconds. At $0.20/kWh, that energy costs about $0.0000056 per task. These are scenario inputs, not price quotations or observed acceptance rates.

| Incoming tasks per year | Custom local plus 20% fallback, per incoming task | Cloud integration, per incoming task | Local path per accepted task if acceptance is 92% | Cloud path per accepted task if acceptance is 96% |
|---|---:|---:|---:|---:|
| 10,000 | $6.4020 | $1.1100 | $6.9587 | $1.1563 |
| 100,000 | $0.6420 | $0.1200 | $0.6978 | $0.1250 |
| 1,000,000 | $0.0660 | $0.0210 | $0.0717 | $0.0219 |

The assumed client engineering cost dominates this range. At equal quality and the stated 20% fallback, the annual volume at which avoided API expense offsets the $53,000 fixed-cost difference is about 6.63 million incoming tasks. This is a calculation of the specified scenario, not a universal adoption threshold. A system API, an existing local runtime team or a feature already distributed with the app can reduce that fixed-cost difference sharply. A privacy or offline requirement can justify local implementation even when it does not minimize the monetary column.

Quality can matter more than electricity. An extra two percentage points of tasks requiring five minutes of correction at $30/hour adds $0.05 per incoming task. That exceeds the entire assumed cloud inference charge. Improving a retrieval stage or using a stronger model for a small hard subset may therefore be more valuable than further compressing an already cheap local attempt. Conversely, a specialized model that accurately handles frequent routine tasks can remove both network waits and API charges without increasing correction work.

Fallback rate matters increasingly at high volume. At one million incoming tasks, this scenario costs $0.0645 per incoming task at 5% fallback, $0.0660 at 20%, and $0.0690 at 50%, before any additional correction cost. If local work delays every difficult task before sending it remotely, include that user-time cost as well. A direct router for clearly hard requests can produce a better experience than universal local-first execution.

### A dedicated speech endpoint: utilization changes the denominator

For a separate edge box, assume an all-in installed hardware cost of $400, a three-year life, $60/year of support and replacement allowance, and 10 W whole-device power continuously at $0.20/kWh. Annualized cost is $133.33 hardware + $60 support + $17.52 energy = $210.85. At eight hours of useful audio per day, that is about $0.0722 per audio hour; at twenty-four hours it is $0.0241. These values exclude initial software development, network service, microphones not included in the assumed package, and human correction. They also require the chosen recognizer and pipeline to meet the task's quality requirement. The $400 assumption is deliberately an installed-system scenario rather than NVIDIA's historical $249 developer-kit price.

A continuously powered endpoint can be economical for frequent service because hardware and support are spread across many hours. For a few recordings per month, the same fixed costs have a much smaller denominator and a cloud service may be preferable. A shared existing PC presents a third situation: charge the incremental load and integration cost, while accounting for contention with its user's work. These ownership models should not be combined into one “edge cost.”

Network costs depend on representation. Mono 16 kHz, 16-bit PCM is 32 kB/s, or 115.2 MB/hour. An assumed 24 kbit/s compressed stream is 10.8 MB/hour before protocol overhead. Local transcription followed by selected text transfer can reduce bytes markedly, but a cloud speech API may charge for audio duration rather than bytes. Reduced transfer can improve availability and privacy without reducing the provider's billed unit by the same proportion. A system evaluation should record uplink use, retries and radio energy separately from recognition computation.

Model distribution creates a different traffic pattern: a multi-gigabyte download followed by many local uses, then another transfer when the artifact changes. Storage-constrained devices, metered connections and interrupted downloads can affect adoption. A shared system model can amortize distribution across apps, while a custom artifact gives control over version and support. Both approaches need a useful experience before a model is ready.

The matrix favors different implementations because the tasks differ. A phone document assistant and a twenty-four-hour speech appliance should not be forced through one model or API solely to simplify the architecture. Sharing retrieval formats, task definitions and validation logic is useful; execution and resource policies can remain specific to the workload.

Concrete decision rules follow from the combined evidence:

1. **For offline obligations, ship a complete local path.** Include model readiness, required preprocessing and a useful reduced-capability response. A cloud fallback cannot satisfy an offline requirement.
2. **For sensitive data, decide the boundary before routing.** Keep local indexing, recognition and source display available; escalate only the permitted content. Include logs, tools, backups and outputs in that boundary.
3. **For short transformations, prefer the smallest model that meets task quality.** Bound output and history, use an effective accelerator path, and optimize time to the usable result. Larger capacity should earn its additional wait and memory.
4. **For bursty hard tasks, use stronger remote inference when allowed.** A larger model can offset network delay and avoid a failed local attempt. Keep local retrieval or preprocessing when it reduces transfer without hiding decisive evidence.
5. **For continuous workloads, choose sustained service capacity.** Budget capture, preprocessing, model execution, postprocessing, queueing, cooling and operating-system permissions. A short clip faster than real time is a promising starting point, not the service itself.
6. **For scale economics, compare ownership models and accepted outcomes.** Existing hardware, dedicated appliances and a custom multi-device client have different fixed costs. Include correction and fallback before selecting a cheaper numerical representation.

The resulting product can give local models substantial responsibility without assigning them every task. Local retrieval, compact generation and nearby speech recognition create useful functionality on their own. Cloud and hybrid paths then address the cases where additional capability, context or availability justifies their data movement and expense.
