# On-Device Models: Hardware Constraints, Task Fit, and Edge–Cloud Design

Evidence cutoff: 9 November 2026. Author: Codex research producer `/root/ttc_research`. This is substantive author analysis; independent review is separate.

## 1. Choose a task envelope before choosing an accelerator

On-device inference is appropriate when a useful task can be completed with the memory, response time, operating duration and data access that a supported device can reliably provide. Its strongest uses have a bounded input, a short or structured output and information already present on the device: rewriting a message, extracting fields from a document, finding a passage, or transcribing nearby speech. A cloud model remains attractive for difficult synthesis, uncertain knowledge and sporadic requests whose quality requirement exceeds a small local model. Hybrid execution works when the local stage can reduce the information or work sent remotely without losing what determines the answer.

This is a joint quality and systems decision. A fast answer with an omitted contractual exception fails document assistance. An accurate transcription that arrives after a long utterance ends fails live captions. A small model that runs while a developer keeps an app open may fail the intended background experience. The right unit of comparison is a completed, acceptable task under its actual operating conditions.

Four representative configurations anchor this report. Samsung's Galaxy S24 Ultra has a Snapdragon 8 Gen 3 for Galaxy and a 12 GB memory configuration. The PC throughput evidence uses an M4 Pro with 16 GPU cores, 24 GB unified memory and 273 GB/s specified bandwidth; the paper does not identify its enclosure or OS build. A Surface Laptop 7th Edition with Snapdragon X Elite, 32 GB LPDDR5x and a 45-TOPS Hexagon NPU illustrates Windows integration. An actively cooled Jetson Orin Nano 8 GB illustrates a dedicated endpoint with sustained speech work. These devices are not placed on a common speed leaderboard. Their evidence answers different deployment questions. [Samsung S24 specifications](https://news.samsung.com/us/enter-new-era-of-mobile-ai-samsung-galaxy-s24-series/), [BaseRT, version 1](https://arxiv.org/html/2607.00501v1), [Surface specifications](https://learn.microsoft.com/en-us/surface/tech-specs/surface-laptop-snapdragon-tech-specs), [Jetson Super announcement](https://developer.nvidia.com/blog/nvidia-jetson-orin-nano-developer-kit-gets-a-super-boost/).

The report distinguishes documented capability, author or vendor measurement, independent research measurement, and calculated scenario. Published rates retain their model, runtime, precision and phase. The memory reservations, duty cycles, network speeds and financial assumptions below are explicit design scenarios. No new model inference benchmark was run for this report.

## 2. Memory is a working set, not a download size

A deployment needs enough usable memory for weights, quantization metadata, activations and temporary buffers, attention state, retrieval assets, the application and simultaneous system work. Storage answers whether a package can be downloaded. Installed RAM answers how much physical memory exists. The app's available budget answers whether its next request can finish. GPU residency and OS memory pressure can impose a tighter limit than either headline number.

For a dense model with P parameters and an ideal b-bit representation, raw weight storage is P × b / 8 bytes. Real formats include scales, zero points, alignment and tensors retained at higher precision. A runtime may duplicate or transform weights during loading; memory-mapped files and accelerator allocations also complicate process-memory readings. An operating system can reclaim cached pages, but repeated page faults into a large weight set can make a technically successful load unusably slow. Unified memory removes some explicit CPU-to-GPU copies; it does not give the model exclusive use of that memory or bandwidth.

Qwen2.5-3B-Instruct supplies a concrete architecture for calculation. Its official model card specifies 3.09 billion parameters and a 32,768-token context for this model, despite a broader family-level description of longer contexts. Raw weights occupy 5.756 GiB at 16 bits, 2.878 GiB at 8 bits, or 1.439 GiB at 4 bits. These are ideal byte counts, not measured resident footprints or proof that a particular quantized artifact preserves quality. [Qwen model card](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct/blob/main/README.md).

For an ordinary full-attention decoder, an uncompressed KV cache requires:

`KV bytes = 2 × layers × KV heads × head dimension × bytes per element × cached tokens × batch size`.

The factor two represents keys and values. Qwen's configuration has 36 layers, 16 query heads, two KV heads and a hidden dimension of 2,048, giving a head dimension of 128. With two-byte KV elements and one sequence, each cached token needs 36,864 bytes, or 36 KiB. The cache therefore occupies 144 MiB at 4,096 tokens, 288 MiB at 8,192 and 1,152 MiB at 32,768. The configuration disables sliding-window attention, so the presence of a `sliding_window` field is not a reason to cap this calculation. Input, retained history, tool results and generated output all consume the context budget. [Official Qwen configuration](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct/blob/main/config.json).

Grouped-query attention reduces the number of stored KV heads relative to query heads. KV quantization reduces bytes per stored element, with metadata and kernel costs, and requires its own quality evaluation. A sliding window bounds attention state only when the architecture and runtime actually implement that policy. Shared caches can reduce the number of independently stored layers. Apple's 2025 architecture, for example, shares the second block's KV state with the last layer of the first block, reducing KV memory by 37.5% relative to its stated unshared design. None of these changes implies that every model with the same parameter count has the same cache size. [Apple 2025 technical report, §§2 and 6](https://arxiv.org/pdf/2507.13575v1).

The following worksheet deliberately separates a memory calculation from a device measurement. Assume the S24 application can safely allocate a **4 GiB task budget after other device usage**. This is a proposed admission limit, not a documented Android entitlement. Reserve 1.8 GiB for a 4-bit Qwen artifact and its weight overhead, 0.6 GiB for working buffers, 0.25 GiB for a resident embedding model, 0.35 GiB for application/text assets, and 0.5 GiB for headroom. Ten thousand 384-dimensional FP16 vectors need 7.68 MB; allowing another 50% for an illustrative index structure produces 11.52 MB, or 10.99 MiB. Actual text, document files and metadata must be budgeted separately within the app reservation or on disk.

| Total cached tokens | BF16 KV | Planned phone working set, including 0.5 GiB headroom | Margin under 4 GiB |
|---|---:|---:|---:|
| 4,096 | 144 MiB | 3.651 GiB | 0.349 GiB |
| 8,192 | 288 MiB | 3.792 GiB | 0.208 GiB |
| 32,768 | 1,152 MiB | 4.636 GiB | Exceeds by 0.636 GiB |

The practical choice is a bounded 4K–8K request, with output space reserved before generation. A full 32K context is outside this example's allocation even though the model accepts that length. If the embedding model can be unloaded before generation, it returns 0.25 GiB; if retrieval and generation must overlap, it cannot. Raising precision also changes the decision: using an assumed 3.6 GiB 8-bit weight reservation adds 1.8 GiB. That version fits a separately assumed 10 GiB PC task budget at 5.592 GiB for 8K tokens or 6.436 GiB for 32K, leaving room for the rest of the desktop workload. Those calculations do not transfer the S24's Gemma measurements to Qwen or predict Qwen throughput.

This is how memory affects product behavior. Admission should consider the current available budget and the complete request, not only whether a model is installed. Under pressure, reduce retrieved material, release an idle model, choose a smaller supported artifact or queue the work. A privacy-required offline task should retain a source browser and extraction path when generation cannot fit. A silent cloud upload is not a memory-management strategy.

## 3. What makes inference fast, and what quality is traded away

Prefill processes the prompt and builds attention state. It can exploit parallel work across input tokens, so matrix throughput and efficient kernels matter. Decode generates tokens sequentially. At small batch sizes, repeatedly reading weights and attention state can dominate; reducing their bytes can help more than a larger nominal arithmetic rating. Launch overhead and CPU coordination matter especially for small models. Long contexts increase attention work and state traffic, so decode speed can deteriorate as a session grows.

CPU, GPU and NPU are different execution paths. A CPU has broad operation support and convenient integration. A GPU offers parallel matrix and attention kernels, but shares resources with display and other applications. An NPU can execute supported low-precision graphs efficiently, while unsupported operations, shape restrictions and transfer boundaries may undermine the expected benefit. ONNX Runtime's QNN HTP documentation requires quantized models and fixed rather than dynamic shapes for the documented path; it also provides an option to reject CPU fallback. A model that loads through an NPU-enabled library is not evidence that its whole critical path executes on the NPU. [ONNX Runtime QNN documentation](https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html).

Weight quantization primarily reduces weight storage and traffic. Activation quantization changes intermediate representation and arithmetic. KV quantization targets the state that grows with context. Distillation changes the model's learned function and capacity; it may preserve a narrow task better than broad reasoning. Pruning or sparse activation reduces useful work only if the runtime avoids the removed work. In a mixture-of-experts model, few active parameters per token can reduce computation, while many experts still require storage or costly paging. Gemma 3n's effective-parameter design likewise distinguishes total parameters from the portion kept active through parameter skipping and cached per-layer embeddings. Its E2B designation should not be used as a two-billion-parameter full-package memory estimate. [Gemma 3n overview](https://ai.google.dev/gemma/docs/gemma-3n).

Quantization quality depends on how the representation is obtained. AWQ uses activation statistics to scale important weight channels before quantization and couples the representation to packing, dequantization and fused kernels. Its central lesson is that numerical compression and implementation must be designed together. The reduction in bytes is an opportunity for acceleration, not a guarantee across backends. [AWQ, version 5, §§3–4](https://arxiv.org/html/2306.00978v5).

Meta's Llama 3.2 release gives a useful within-family example. For the 3B instruction model, its model-card MMLU result falls from 63.4 in BF16 to 60.5 for vanilla PTQ, versus 62.0 with SpinQuant and 62.4 with its QAT/LoRA method. On the separate Open-rewrite metric, the BF16 score is 40.1 and the QLoRA score is 40.7. These results support task-specific evaluation: a compression path that slightly improves one rewrite score can still lose general knowledge accuracy. Meta's scheme also retains different tensors and LoRA components at different precisions, so its package cannot be represented as uniformly four-bit. [Llama 3.2 model card, quantization and instruction-tuned evaluation tables](https://github.com/meta-llama/llama-models/blob/main/models/llama3_2/MODEL_CARD.md).

Apple's July 2025 technical report illustrates a more aggressive system-level trade. It combines two-bit decoder weights, four-bit embeddings, eight-bit KV state and recovery adapters. Table 3 reports on-device MMLU moving from 67.8 to 64.4 and IFEval from 85.1 to 82.3 after the stated optimization bundle. The relevant judgment is that a compact, integrated model can be useful for supported text tasks while retaining a measurable quality cost. These July report values are not silently substituted for later Apple model revisions. [Apple technical report, §6 and Table 3](https://arxiv.org/pdf/2507.13575v1).

### Phase evidence from a phone and a PC

The fixed LiteRT-LM README commit of 21 July 2025 reports 1,024 prefill tokens and 256 decode tokens, with a 4,096-token configured context for the following S24 Ultra rows. The artifacts use four-bit per-channel weights. This is vendor runtime evidence; the table does not supply an OS build, thermal history, repeated-run confidence interval or task-quality result. Its phase comparison is nevertheless informative. [Pinned LiteRT-LM benchmark table](https://github.com/google-ai-edge/LiteRT-LM/blob/eaa380eee74b677f9f305eb2a92ae0fcc14ffc39/README.md).

| S24 Ultra model and backend | Prefill tokens/s | Decode tokens/s | Calculated 1,024-token prefill | Calculated phase sum with 256 output tokens |
|---|---:|---:|---:|---:|
| Gemma 3n E2B, CPU | 110.5 | 16.1 | 9.27 s | 25.17 s |
| Gemma 3n E2B, GPU | 816.4 | 15.6 | 1.25 s | 17.66 s |
| Gemma 3 1B, GPU | 1,876.5 | 44.57 | 0.55 s | 6.29 s |

Switching E2B to the GPU dramatically reduces prompt processing while decode remains similar and is slightly slower in the reported row. For a 128-token reply, the same rate calculation gives 9.46 seconds on the GPU; projecting to 512 output tokens gives 34.07 seconds. The latter extrapolates beyond the table's 256-token decode run. These phase sums omit loading, tokenization, queueing, first-token bookkeeping and rendering; they are planning calculations, not observed end-to-end latency. The smaller Gemma 3 1B may be the better choice for short transformations if it meets the task's quality bar. Increasing model capacity is worthwhile only when its improved answer quality compensates for longer waits and greater memory use.

BaseRT's 2026 paper offers a separate PC comparison. On its M4 Pro configuration, Llama 3.2 3B Q4 decodes 128 tokens at 117.3 tokens/s, versus 102.4 for llama.cpp b9630 and 112.1 for MLX 0.31.2. At a 2,048-token prompt, BaseRT prefill is 835 tokens/s and llama.cpp is 864. Summing the separate BaseRT rates gives a 2.45-second prefill and 1.09-second 128-token decode. This 3.54-second phase sum is not a measured combined request; the benchmark phases and cache lengths need not coincide. The evidence supports fast short local tasks on this PC class, and shows that a runtime can win decode while losing prefill. It does not establish universal runtime leadership: MLX is faster on the paper's Gemma 4 26B-A4B Q4 decode row, 69.3 versus 62.2 tokens/s. [BaseRT, §4 and Tables 1–3](https://arxiv.org/html/2607.00501v1).

### Sustained operation changes the feasible task

MELT provides independent evidence about the gap between a successful mobile run and a stable experience. With Zephyr 3B four-bit on an iPhone 14 Pro, its 50-prompt continuous experiment, repeated three times, shows degradation from the start and further changes around prompts 20 and 32. Its Jetson AGX comparison is smoother at a 50 W setting. The study also reports app termination, unresponsiveness and device restarts under some configurations. These older devices and runtimes establish mechanisms to account for, rather than a temperature or slowdown forecast for the S24. [MELT, version 4, §§5.2–5.3](https://arxiv.org/html/2403.12844v4).

A passively cooled phone should therefore favor short, cancelable bursts and explicit limits on concurrent models. A desktop or actively cooled edge box can serve longer duty cycles if measured at the intended ambient temperature and cooling configuration. A useful sustained criterion is that the latency distribution, memory use and queue depth remain acceptable for the duration of the workload, while the rest of the device remains responsive. Peak TOPS, a first warm response, and a fan's presence each describe only part of that criterion.
