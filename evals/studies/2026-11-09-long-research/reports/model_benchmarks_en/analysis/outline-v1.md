# Comparing benchmarks for decisions about deployed systems

Evidence cutoff: 2026-11-09. Author: /root, continuing the preserved Astra plan after explicit quota exhaustion. Original task: evals/cases/model_benchmarks_en.json. This is the report plan, not a completed review.

The report will explain how benchmark evidence changes two model-selection decisions: grounded customer support and a repository-level coding agent. Its argument is that a score becomes useful when the evaluated object, measurement and workload are connected. The comparison will retain cases where a better test changes a ranking, where a prompt changes the result, and where an apparently improved benchmark later needs correction.

1. **Four objects and one selection problem.** Distinguish dataset, framework, harness and leaderboard; identify the evaluated model/system, unit and result conditions. Explain how repeated use of one dataset in several suites can create false breadth.
2. **HELM's changing measurement scope.** Reconstruct Classic's seven metric families, Lite's sampling and removed measurements, and Capabilities v1.0.0's five scenarios, zero-shot adaptation, judges and rescaled mean. Link the adapter and framework configuration to the actual measurement. Preserve the June 2026 maintenance notice and public result availability.
3. **Complementary coverage.** Matrix for MMLU/MMLU-Pro, HumanEval/EvalPlus, SWE-bench and revised Pro, tau/tau2, and preference evaluations. Explain construction, language/domain distribution, sample, scorer, aggregation and target capability. Use HELMET and LiveCodeBench for targeted long-context/refresh contrasts if their originals support the needed point.
4. **Worked changes in interpretation.** MMLU-Pro Table 3's prompt comparison; EvalPlus greedy rank reversal; SWE 500-task Verified versus original/Pro populations and September 2026 Pro V2 changes; tau pass@k versus pass^k and macro-domain weighting; AlpacaEval length intervention and stable ordering under different judges; HELM mean win rate versus a mean of component scores. Preserve actual denominators and do not create significance from rounded scores.
5. **What can be reproduced.** Versioned table of data, code, prompts, generation settings, tools, context, scorer, judge, retained output and endpoint availability. Procedure reconstruction, rescoring and new inference are different operations. Explain environment, cache and mutable endpoint consequences without running new benchmarks.
6. **Where score errors arise.** Separate demonstrated exposure, runtime access, adaptive public-test selection, contamination suspicion and flawed scoring. Incorporate both the 2026 OpenAI audit and the later Scale V2 change; distinguish selected audit subsets from random samples. Explain uncertainty, shared-task pairing and clustered issues. Arena critiques must be attributed and contrasted with the platform response where accessible.
7. **Grounded customer support.** Separate information answering from authorized transactions. Explain which measurements support a shortlist and which missing observations change it: grounding, policy versions, conflicting sources, clarification, failed tool recovery, multilingual requests and severe wrong actions. Model selection follows the actual service requirement; successful-resolution cost and response deadlines enter only as deployment constraints, not substitutes for correctness.
8. **Repository agents.** Connect function tests, issue repair, environment/tool policies and maintainability to developer workflow. Discuss fresh/private repository evidence and the METR 2025 randomized study with its 2026 follow-up's selection problem. Explain why model performance, autonomous patch success and assisted developer productivity answer different decisions.
9. **Synthesis and exhibits.** A coverage matrix, versioned reproducibility comparison, worked numeric interpretations and two conditional recommendations form one report. No universal model winner or synthetic benchmark score. Calculations will be explicit transformations of published values or clearly labelled author scenarios; no new model-run claim.
