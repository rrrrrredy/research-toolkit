# Model benchmarks that help a deployment decision

*Evidence through 9 November 2026. Historical results retain their original versions and conditions.*

A model-selection team should use benchmarks to explain a shortlist: which capabilities a candidate has demonstrated, which failures matter for the proposed service, and which unresolved comparison would change the choice. The strongest overall leaderboard entry is a useful starting point when little else is known. Once the workload is defined, the component results and execution conditions become more informative than the overall position.

Consider two teams choosing from the same models. A customer-support team needs grounded answers, appropriate clarification and correct handling of account actions. A repository-agent team needs the ability to inspect an unfamiliar codebase, make a coherent change and preserve existing behavior. Both benefit from reasoning and instruction following. Their decisive failures differ. A support answer can be fluent and factually plausible while applying an expired refund policy. A patch can solve the visible example while breaking an untested integration. A general preference result helps neither team identify these errors on its own; a suitable combination of knowledge, executable-task, interaction and output-quality evidence can.

The comparison below uses HELM as an entry point, then MMLU-Pro, EvalPlus, SWE-bench, the tau family and preference evaluations as complementary measurements. It examines published experiments rather than running a new leaderboard. The aim is to make model-selection reasoning concrete: a stronger test can reverse a ranking, a prompt can change what capability is elicited, and a benchmark revision can change the population being measured.

## What is being compared?

Four objects are often given the same name, although they perform different jobs.

| Object | What it supplies | Example | What a selection team needs from it |
|---|---|---|---|
| Dataset | Instances, source material, labels or reference outcomes | MMLU-Pro questions; SWE-bench issue instances | The sampled population, revision, exclusions and intended answer conditions |
| Evaluation framework | A reusable way to configure tasks, models and metrics | HELM; lm-evaluation-harness | Comparable adaptation, inspectable scoring and recoverable run configuration |
| Execution harness | The environment in which answers or actions are produced and assessed | A coding-agent scaffold plus repository sandbox and patch evaluator | Actual tools, permissions, dependencies, limits and recovery behavior |
| Leaderboard | A published aggregation of results | HELM Capabilities; Arena; SWE-bench submission tables | The meaning of each row, common comparison conditions and uncertainty |

A project may contain all four. Their coexistence does not make a leaderboard row a property of a model alone. A repository result measures a model operating through an agent implementation with a particular environment and task set. A multiple-choice result may measure generated answer letters or likelihood-ranked alternatives. A preference result measures judgments over a chosen prompt population and comparison set.

This distinction also prevents double-counting. MMLU-Pro appearing in its own table and inside HELM is not two independent demonstrations of broad competence. The latter may add an informative prompting contrast, but it still relies on overlapping task material. Several coding leaderboards can similarly reuse HumanEval or SWE-bench under different wrappers. A selection report gains breadth by adding distinct failure modes and operating conditions, not by counting more links to the same questions.

A useful result identity therefore includes the dataset revision and sample; model checkpoint or API date; prompt and demonstrations; decoding and reasoning configuration; available tools; context handling; environment and harness revision; scoring or judge configuration; aggregation; and run date. This information explains why scores differ. It need not become a new bureaucratic form: well-preserved run configurations and outputs already carry much of it.

## HELM: one framework, changing measurement objectives

The original HELM study made a valuable change to model comparison: it measured several properties on shared scenarios rather than treating accuracy as the entire result. Its 2023 TMLR version reports 30 models, 16 core scenarios and seven general metric families, with targeted evaluations bringing the total to 42 scenarios. Accuracy, calibration, robustness, fairness, bias, toxicity and inference efficiency are distinct measurements. The taxonomy explicitly separates properties measurable through black-box model access from properties requiring knowledge of the wider system or social context. For example, a perturbation-based fairness metric is a defined probe, while deployment accessibility depends on who uses the service and how it is delivered. [HELM, TMLR version, §§2–4](https://arxiv.org/pdf/2211.09110v2).

That design makes a trade-off visible. A model can be accurate on the unmodified questions but sensitive to wording changes. Another can discriminate well between options while assigning overconfident probabilities to wrong answers. For a support assistant, the first result motivates examining paraphrased requests; the second matters if confidence controls escalation. Neither issue is resolved by choosing the larger accuracy value. The benefit comes from connecting a measured difference to a service decision.

HELM Lite, announced in December 2023, made a different choice. It reduced the number of in-context example seeds from three to one and removed perturbation-based robustness and fairness, calibration, perplexity and an expensive retrieval scenario. It also changed coverage, including five of MMLU's 57 subjects and selected legal and translation tasks. Instances were capped at 1,000 per scenario, with generally five demonstrations reduced when necessary to fit the context. This made the suite easier to run across contemporary assistant APIs, but its output describes that revised coverage. The name HELM alone no longer specifies the measurements. [HELM Lite v1.0.0 announcement](https://crfm.stanford.edu/2023/12/19/helm-lite.html).

HELM Capabilities v1.0.0, announced in March 2025, changed the recipe again. It combines MMLU-Pro, GPQA, IFEval, WildBench and Omni-MATH. MMLU-Pro, WildBench and Omni-MATH are sampled to at most 1,000 instances; GPQA and IFEval use their smaller sets. It elicits chain-of-thought for the multiple-choice reasoning tasks, uses official rule-based instruction checks for IFEval, and employs model judges for open responses. WildBench scores on a 1–10 scale are mapped to 0–1, then averaged with the other scenario scores. The resulting mean differs from Classic and Lite's mean win rate. [HELM Capabilities, evaluation setup and metrics](https://crfm.stanford.edu/2025/03/20/helm-capabilities.html).

This is a substantive aggregation decision. Mean win rate describes how often a model beats the other included models across scenarios; changing the comparison set can change it. A mean of component scores avoids that dependence, but gives equal numerical weight to measurements with different meanings. A 0.1 change in a rescaled checklist score is not automatically equivalent in service value to a ten-point change in answer accuracy. The aggregate becomes useful when its weights approximately match the selection question, or when it is accompanied by the component profile.

The Capabilities announcement reports Gemini 2.0 Flash at 0.679 and Claude 3.7 Sonnet at 0.674. The 0.005 difference is a difference in that five-component mean. It is not a statement that the former resolves 0.5% more support requests. A team mainly concerned with reliable account actions should first ask how either model handles stateful policies, which this aggregate does not directly exercise. A team producing mathematical explanations can place more weight on the relevant reasoning components, while retaining instruction compliance and presentation quality as separate needs.

The implementation helps explain what a framework actually standardizes. HELM's joint multiple-choice adapter constructs the displayed choices and expected answer labels, while model and generation parameters come from the run configuration. A separately scored likelihood task is a different operation from asking the model to generate a letter. In lm-evaluation-harness, task configuration similarly specifies dataset and few-shot splits, prompt templates, generation or likelihood output types, filtering and aggregation. Its documented self-consistency example obtains first-answer and majority-vote measurements from the same saved generations. A reported improvement may therefore come from inference sampling or answer extraction even when the underlying checkpoint is unchanged. [HELM joint-choice adapter](https://github.com/stanford-crfm/helm/blob/main/src/helm/benchmark/adaptation/adapters/multiple_choice_joint_adapter.py); [lm-evaluation-harness task configuration](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/task_guide.md).

HELM entered maintenance mode on 1 June 2026. Existing leaderboards and results remain available, while new leaderboard evaluations are no longer maintained as before. Historical output remains valuable for studying controlled comparisons and measurement design. For a current procurement decision, the team must combine that evidence with results for the endpoints it can actually deploy. The framework's availability and the currency of its published model rows are separate facts. [HELM maintenance notice](https://crfm-helm.readthedocs.io/en/latest/maintenance_mode/).

## Complementary coverage, rather than interchangeable percentages

| Family and version used here | Construction, population and evaluation unit | Main measurement | What it adds to selection |
|---|---|---|---|
| HELM Classic, TMLR 2023 | Selected NLP scenarios; prompt instance and model response | Scenario accuracy plus six additional metric families where applicable | A profile of defined capabilities and failure sensitivities |
| HELM Capabilities v1.0.0, 2025 | Five selected reasoning, instruction and open-response scenarios | Accuracy/checklist judgments and a rescaled mean | A compact contemporary capability profile, with inspectable adaptation |
| MMLU-Pro, paper v6, 2024 | 12,032 predominantly English academic questions in 14 domains; up to ten choices | Extracted-answer accuracy; original paper mainly five-shot CoT | Knowledge and problem-solving discrimination under a specified response recipe |
| HumanEval and EvalPlus v3, 2023 | 164 Python function specifications; generated programs | Functional correctness under original and expanded tests; greedy or sampled pass rates | Whether apparently successful code survives broader input coverage |
| SWE-bench Verified, 2024; Pro V2, September 2026 | Repository issues and patches; different curated task populations | Fraction passing the designated repair and regression tests | Multi-file navigation, implementation and executable task completion |
| tau-bench v1, 2024 | Synthetic retail and airline policies, databases and model-simulated conversations | Final-state task success and repeated-run consistency | Policy-constrained actions across a conversation |
| tau2 paper v1, 2025; code v2.0.0, October 2026 | Adds a telecom environment where the simulated user acts too; later release changes tasks and scoring | State/action/communication success under the named release | Coordination and communication as part of tool-mediated service |
| Chatbot Arena paper v1, 2024 | Live, self-selected prompts and anonymized human pairwise votes across many languages | Estimated relative preference | Open-ended usefulness and presentation preferences in that audience |
| Length-controlled AlpacaEval paper v2, 2025 | 805 English instructions, candidate/reference outputs and automated comparisons | Reference-dependent win rate adjusted for output length | A controlled probe of preference and a concrete test of style-related ranking effects |

The rows answer different questions. Their breadth also differs. English academic questions do not supply multilingual customer-service coverage merely because a model is multilingual. Python function tests do not cover a TypeScript service's deployment or a Go repository's build behavior. Arena's language diversity adds naturally occurring interaction, but the mixture is determined by participants rather than by a buyer's ticket distribution. Selecting a complementary set means choosing useful contrasts and then examining the relevant subgroup, not averaging all the percentages in this table.

Safety follows the same logic. HELM's toxicity and bias probes measure their specified phenomena. A support assistant's authority to refund an order, disclose personal records or modify an account introduces different requirements. A high reasoning or preference score is useful capability evidence; the action's correctness is established by the relevant policy and state-based task evidence. This directs attention to consequential failure mechanisms without discarding the measurements that already help.

## What changes a result, and what changes its interpretation?

### The prompt can change the capability being elicited

MMLU-Pro illustrates why a checkpoint name is insufficient to interpret a reasoning result. Table 3 of the authors' v6 paper compares chain-of-thought and direct answering. GPT-4o scores 72.6% versus 53.5% on MMLU-Pro, a 19.1 percentage-point difference. On the original MMLU comparison in that table, its corresponding difference is 88.7% versus 87.2%, or 1.5 points. Llama-3-8B's direction changes across the two datasets: chain-of-thought is 3.9 points lower on MMLU and 3.9 points higher on MMLU-Pro. The value of eliciting intermediate reasoning depends on the model and the questions. [MMLU-Pro v6, Table 3](https://arxiv.org/pdf/2406.01574v6).

The practical conclusion is stronger than “prompts matter.” If the deployed assistant is allowed to reason through a difficult request, direct-answer measurements may omit a useful capability. If the service requires a constrained single response, a result obtained with many demonstrations and extensive generated reasoning describes a different operating condition. Choose the recipe that matches the proposed service, then compare candidates under it. The paper's main table uses five-shot CoT except for the two named Gemini models, which use zero-shot. HELM Capabilities uses its own zero-shot CoT adaptation on a sampled MMLU-Pro set. Treating these rows as one homogeneous experiment would erase both the intervention and the sample change.

Scoring is part of that intervention. The MMLU-Pro paper describes two answer-extraction patterns followed, if extraction fails, by a random choice. HELM's announcement describes broader extraction handling after observing outputs with valid answers in unexpected formats. These are observable evaluator choices. To investigate a score difference, inspect how many responses were extracted successfully and how fallback outcomes were counted. A model that knows the answer but violates the requested format has an instruction-following problem; an evaluator that misses a permitted equivalent format has a parsing problem. They imply different changes to a deployed system.

### Better test coverage can reverse a coding ranking

EvalPlus evaluates the same generated function implementations against a more demanding test set. Its HumanEval+ construction expands input coverage, adds contracts where appropriate and corrects faulty reference implementations. In the paper's Table 3, the greedy-decoding rows show the following results:

| Model label in EvalPlus v3 | Original HumanEval | HumanEval+ | Change, percentage points |
|---|---:|---:|---:|
| ChatGPT | 73.2% | 63.4% | −9.8 |
| Phind-CodeLlama 34B | 71.3% | 67.1% | −4.2 |
| WizardCoder-CodeLlama 34B | 73.2% | 64.6% | −8.6 |
| GPT-4 | 88.4% | 76.2% | −12.2 |

On the original tests, Phind trails ChatGPT by 1.9 points. On the expanded tests, it leads by 3.7 points. WizardCoder moves from a tie to a 1.2-point lead. These comparisons retain greedy decoding; the paper's sampled pass@1, pass@10 and pass@100 columns use separately specified temperatures and should not be substituted for them. The values above come from the original table, not a newly executed experiment. [EvalPlus v3, §3 and Table 3](https://arxiv.org/pdf/2305.01210v3).

The mechanism is concrete. Several models produce implementations that satisfy the original examples but differ on boundary cases and more demanding inputs. Expanded tests discriminate among those implementations. The revised ranking changes a function-generation shortlist because it adds evidence about correctness under a broader input distribution. It does not establish superiority for repository navigation, architecture or user communication; those require the complementary measurements in the coverage matrix.

This example also shows why passing tests must be interpreted through their contents. More tests help when they add meaningful coverage or correct an oracle. Repeating redundant examples adds little. EvalPlus's reduced test suite preserves much of the observed discrimination with fewer tests in its studied setting. Its useful lesson is to examine which wrong implementations the tests distinguish, rather than equate the number of assertions with quality.

### Repository benchmarks change when the task population or verifier changes

SWE-bench asks an agent to produce a patch for an issue in a real repository. The evaluator checks tests that should change from failing to passing and tests that should remain passing. This connects the score to executable behavior at a defined repository state. It also makes the issue statement, hidden tests and environment consequential: a reasonable implementation can fail a test that requires an unmentioned interface, while incomplete code can pass an insufficient test.

The 2024 Verified release curated 500 tasks through expert review of the original pool. A higher result on that subset can arise from removing ambiguous or defective tasks, not from an improved model. In February 2026, OpenAI audited 138 Verified tasks that o3 did not consistently solve across repeated attempts and reported material issues in 59.4% of that selected subset. It also presented cases of models reproducing gold patches or distinctive problem text. These are two different findings: task-design defects and evidence of prior exposure. The 59.4% figure describes a difficult, selected subset, not a random estimate of defects in all 500 tasks. [Verified release](https://openai.com/index/introducing-swe-bench-verified/); [February 2026 analysis](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/).

The subsequent Pro story prevents a simplistic response of replacing one trusted name with another. OpenAI's July 2026 investigation of the 731-task Pro public split reported 200 tasks flagged as broken by its deeper pipeline and 249 identified through the human annotation campaign. The human work examined an initially flagged subset; the figures describe that audit procedure. The reported problems included over-specific tests, omitted requirements and insufficient coverage. These findings direct attention to inspectable task-level evidence rather than justify treating every failure as an evaluator error. [July 2026 Pro audit](https://openai.com/index/separating-signal-from-noise-coding-evaluations/).

Scale's September 2026 Pro V2 update changes both the dataset and execution protocol. Its release describes 642 tasks across 11 repositories after removing 89 invalid tasks, instruction corrections on 69 retained tasks, restricted agent-phase network access, fresh-image regrading and dependency repairs. The same page retains older 731-task results below the update. Those older scores are historical context, not V2 outcomes. A longitudinal comparison must identify which task set and protocol generated each row. [SWE-Bench Pro V2 update, 22 September 2026](https://labs.scale.com/leaderboard/swe_bench_pro_public_v2).

The V2 protocol also exposes a difference between two practical goals. In production, a coding assistant may legitimately search public documentation or upstream changes. In an evaluation of its ability to solve a withheld issue, retrieving the exact fixing commit changes the challenge. Tool permissions should follow the question being measured. Likewise, clean-image regrading asks whether the submitted patch works without hidden state left in the development environment. That is directly useful to a team deciding whether an autonomous patch can be moved into its ordinary CI pipeline.

### Consistency across attempts differs from finding one successful attempt

The original tau-bench evaluates simulated retail and airline conversations through their final database states. Its main setup uses model-controlled function calling, up to 30 agent actions, temperature zero for the agent and temperature one for the user simulator, with at least three trials per task. Table 2 reports GPT-4o at 61.2% for retail and 35.2% for airline, giving a 48.2% equal-domain average. [tau-bench v1, §§4–5](https://arxiv.org/html/2406.12045v1).

The two domains contain 115 and 50 tasks. Weighting the published rounded rates by task count instead would yield approximately 53.32%. Nothing about the model changed; the weighting changed. Equal-domain weighting gives the smaller airline set the same influence as retail. Task weighting gives each retained task equal influence. A support organization can choose a workload mixture meaningful to its own operations, but should state that mixture rather than inherit an aggregate accidentally.

The distinction between pass@k and pass^k matters even more. Pass@k asks whether at least one of k sampled attempts succeeds. Pass^k asks whether all k attempts succeed. In an illustrative homogeneous scenario with independent 60% success per attempt, pass@4 is 97.44%, while pass^4 is 12.96%. These are author calculations illustrating definitions, not estimates from the tau trajectories. Real tasks vary in difficulty, and repeated attempts may share failure modes, so the powers of an overall mean are not replacements for task-level estimation.

A coding workflow that can run several candidates through a reliable verifier may benefit from pass@k. A customer making a single request benefits from first-attempt correctness and repeatable policy handling. Restarting a financial action four times also introduces different risks from sampling four independent function implementations. The choice of metric should reflect the actual opportunity to detect failure and retry safely.

The later tau2 environment adds tools for the simulated user, making communication and coordination part of the task. Its original telecom study finds performance differences between an agent acting alone and one guiding a user through actions. This is particularly relevant to technical support: having a correct diagnosis and successfully helping someone carry it out are separate abilities. The paper also examines simulator errors, making the simulated user's reliability part of interpreting agent failures. [tau2-bench v1, §§3–5](https://arxiv.org/html/2506.07982v1).

By October 2026, the public v2.0.0 release changes English tasks, communication judging, assertion judges, identifier lookup and simulator prompts. Its changelog explicitly separates 1.x and 2.0 scores. Switching the communication scorer to substring matching does not reconstruct all the earlier inputs. This is a strong reason to record the release and manifest, especially when evaluating multilingual or voice configurations; “tau2 score” by itself leaves too much unspecified. [tau2-bench v2.0.0 changelog](https://github.com/sierra-research/tau2-bench/blob/v2.0.0/CHANGELOG.md).

### Preference can be useful while remaining sensitive to presentation

Arena's original paper describes anonymized human pairwise voting over live prompts and statistical ranking from those comparisons. It broadens the observed behavior beyond fixed exam questions. Length-controlled AlpacaEval asks a narrower and useful question: how much does an automated preference estimate change when a model is prompted to be more concise or verbose?

In the paper's verbosity intervention, gpt-4-1106-preview's raw win rate ranges from 22.9% to 64.3%. Length adjustment reduces that range to 41.9%–51.6%. The model has not become a different checkpoint between these prompts; the measured preference is sensitive to presentation. This is material if a team is comparing models whose default answer lengths differ. It is equally material if the task requires a detailed explanation: useful completeness should not be removed merely to resemble a short reference answer. [Length-controlled AlpacaEval v2, §4.1](https://arxiv.org/html/2404.04475v2).

The same paper supplies an instructive counterexample to blanket distrust of model judges. In its small comparison using GPT-4, Claude and Mistral judges, win rates change but the ordering of the five evaluated models remains stable. Its length-adjusted ranking correlates more strongly with the contemporaneous Arena ranking, 0.98 rather than 0.94, over the reported comparison set. The associated bootstrap comparison has p=0.07 against unadjusted AlpacaEval, so the difference should not be described as crossing a conventional 0.05 threshold. Stable ordering in one comparison and meaningful verbosity sensitivity in another can both be true. [Same paper, §§4.2 and 5, Table 2](https://arxiv.org/html/2404.04475v2).

For procurement, preference evidence is best used to compare the experience of already plausible answers: clarity, completeness, interaction style and usefulness. Grounding and action correctness can then be examined on the service's actual material. This avoids two unproductive extremes: choosing a system entirely from an appealing response, or discarding presentation quality even though it affects whether people can use the response.

## Reproducibility is a sequence of concrete operations

Public artifacts let a team do several different things. A complete configuration explains a procedure. Saved outputs and an executable scorer permit rescoring. A usable checkpoint or endpoint permits new inference under reconstructed conditions. An independent execution that actually produces a comparable result supplies replication evidence. These operations answer progressively different questions; a repository link alone does not tell us which have occurred.

The cited original papers and release descriptions were retrieved for this report. No historical inference service was called and no benchmark environment was installed, so live endpoint usability and a runnable historical dependency set remain specific open parts of replication. [HELM implementation and results](https://crfm.stanford.edu/2025/03/20/helm-capabilities.html); [MMLU-Pro v6](https://arxiv.org/abs/2406.01574); [EvalPlus v3, §§4.1 and A](https://arxiv.org/pdf/2305.01210v3); [tau-bench v1, §5](https://arxiv.org/html/2406.12045v1).

Current implementation can also diverge from a paper. The MMLU-Pro repository now documents optional retrying of wrong answers in a convenience API command. That operation should be recorded as an additional inference/feedback policy rather than assumed to be the paper's first-answer accuracy. LiveCodeBench documents dated releases and defaults to a moving latest release. Specifying `release_v6`, which covers 1,055 problems through April 2025 in the documented table, defines a different population from leaving a moving default unspecified. A dated release window is useful for separating older and newer problems, while the model's actual training or retrieval access still determines what it has encountered. [MMLU-Pro current README](https://github.com/TIGER-AI-Lab/MMLU-Pro); [LiveCodeBench release documentation](https://github.com/LiveCodeBench/LiveCodeBench).

Environment and cache behavior deserve equal attention when they can change a result. SWE-bench's evaluation guide describes caching by run and instance identifiers: reusing those identifiers can reuse an earlier result even after a patch changes. A new patch therefore needs a distinct evaluation identity under that implementation. Repository dependencies, container architecture and external downloads likewise affect whether tests execute. These are concrete explanations for disagreement between runs; they should be distinguished from a model failing the requested repair. [SWE-bench evaluation guide, result caching and outputs](https://www.swebench.com/SWE-bench/guides/evaluation/).

The useful response is to retain the artifacts that make a disputed outcome inspectable: the actual answer or patch, the relevant original task, the run configuration and the scorer's result. This supports a focused regrade when the evaluator changes. It also avoids rerunning an expensive model merely to answer a question already settled by a saved output.

## Exposure, scoring defects and uncertainty need different interpretations

Benchmark exposure is not one mechanism. A model may have encountered questions or solutions during training. An agent may retrieve the fixing commit during evaluation. A developer may repeatedly adapt a prompt to a public task set. A provider may select the best of many tested variants for publication. Each can improve a published result, but each calls for different evidence and a different comparison.

Verbatim reproduction of a distinctive gold patch supplies more direct evidence of exposure than a high score. Runtime retrieval is observable in the trajectory. Repeated tuning can be established from the development procedure. In contrast, the fact that a dataset is public creates an opportunity for exposure without identifying what a particular model learned. A held-out split is valuable when it was actually withheld from candidate construction and selection. Private data changes access, but its relevance, labeling quality and sampling still matter to the deployment question.

Statistical contamination tests are informative when their assumptions fit the available interface. The exchangeability-based work examines whether a model assigns anomalously high probability to a dataset's canonical ordering compared with shuffled orderings. It supplies a hypothesis test under stated assumptions and requires likelihood access. A negative result from that test concerns the detectable ordering signal; it is not a complete inventory of everything seen during training. A product exposing only free-form generations may not support the same test. [Oren et al., contamination test, v2, §§2–4](https://arxiv.org/html/2310.17623v2).

The Arena debate illustrates why numerical claims should retain their origin. *The Leaderboard Illusion* audits provider testing and publication patterns and models effects of selective reporting. Arena's response disputes parts of the analysis, distinguishes simulations from measured effects and proposes provisional labeling with fresh post-release votes in specified circumstances. It also points out that a cited Arena-Hard result uses a static, model-judged set, not live human Arena votes. The practical implication is to inspect the row's vote window, release status and evaluation population. Neither side's broad characterization substitutes for those facts. [The Leaderboard Illusion v2](https://arxiv.org/html/2504.20879v2); [Arena's response, updated June 2025](https://arena.ai/blog/our-response).

Finite-sample uncertainty is another distinct issue. As an author illustration, 80% success on 500 independent, equally distributed binary tasks has a simple binomial standard error of about 1.79 percentage points. That approximation says nothing about the actual uncertainty of a particular leaderboard without its observations. Repository tasks may cluster by codebase; conversations may share policy templates; several attempts on the same task are not new independent tasks. For two models evaluated on the same instances, their pattern of joint successes and failures is needed for a paired comparison. Rounded aggregate percentages alone cannot recover it.

A small numerical lead can still matter when the additional successes occur in the most important workload. Conversely, a statistically clear average lead can be a poor choice if it comes from easy categories while the candidate fails the required action class. Uncertainty analysis and task relevance work together: the former describes what the observations resolve, while the latter determines what the resolution is worth.

## Decision I: a grounded customer-support assistant

The first choice is the intended responsibility. An assistant that explains a return policy is different from one authorized to issue a refund. Both need to find the current policy and apply it to the customer's circumstances. The latter must also verify identity, collect missing information, use the correct account and action parameters, and leave the system in the intended state.

For an informational assistant, HELM's reasoning and instruction components can screen for basic competence. Preference evaluations help identify clear and usable responses. Long-context and retrieval-focused evidence is closer to the essential problem: selecting the relevant policy, retaining its conditions and distinguishing an unsupported answer from a supported one. HELMET's study of 59 long-context models finds that synthetic needle retrieval is a weak substitute for its diverse downstream tasks, and recommends its RAG tasks as a useful development signal. The lesson for this service is to evaluate use of the retrieved evidence, not merely the ability to locate a recognizable string in a long context. [HELMET v3, abstract and analysis](https://arxiv.org/html/2410.02694v3).

The retrieval system and generator should be diagnosable separately. If the correct refund exception never reaches the model, replacing the model based on a reasoning leaderboard may leave the failure unchanged. If the exception is present but the answer omits it, the comparison concerns evidence use and instruction following. If the answer is accurate but impossible for the customer to act on, the missing capability is explanation or interaction. A complete service evaluation follows the result through these stages, while preserving the exact documents and policy version that justified the answer.

For a transaction-taking assistant, tau-style evidence becomes more relevant. It exercises multi-turn collection of information, policy constraints, tool arguments and final state. The original study's example of collecting all exchange items before a once-only action resembles a real class of operational failure. A model that performs well on exam reasoning but acts before the request is complete is a poor choice for that workflow. Tau2 adds a useful contrast for technical support, where the customer performs actions the agent cannot directly execute.

The resulting shortlist should be conditional on the service's responsibility:

| Service requirement | Most useful public evidence | Observation that changes the selection |
|---|---|---|
| Answer from a controlled knowledge base | Grounded/long-context tasks, instruction checks and inspectable answers | The candidate preserves the relevant exception and source date under conflicting or incomplete retrieval |
| Carry out account transactions | Policy/state-based agent tasks and recovery trajectories | Correct action parameters and final state, including denied or partially completed requests |
| Guide a customer through troubleshooting | Dual-control interaction evidence and clear explanations | The customer can carry out the instruction, and the assistant updates the diagnosis from the observed result |
| Serve multiple languages | Evidence in the actual languages and localized policies | Meaning, entity identifiers and policy conditions survive the language change |
| Handle unusual or high-consequence requests | Relevant unresolved cases and escalation behavior | It asks for needed information or transfers the case instead of inventing an authorized action |

A conditional recommendation follows. For a knowledge-only service, favor the candidate that most reliably uses the supplied material and gives a complete, actionable explanation under the intended retrieval setup, even if another model has a marginally higher overall score. For a service taking account actions, require appropriate action and policy evidence before using presentation preferences to choose among candidates. A model can also be assigned a narrower responsibility: an excellent explainer can prepare an answer while a constrained transaction system executes authorized changes.

Successful-resolution cost can then be compared on accepted outcomes. The relevant numerator includes the model, retrieval, tools, retries and human work needed to resolve the service request; the denominator is verified resolution, with reopened contacts treated consistently. If a service has a real response deadline, measure the deployed route against it. These economic and operational constraints help choose among systems meeting the quality requirements. They should not turn a cheap but incorrect refund, or a fast answer based on an obsolete policy, into a successful outcome.

## Decision II: a repository-level coding agent

A repository agent needs more than function synthesis, but function-level evidence remains useful. The EvalPlus rank reversal identifies a real difference in how generated code handles less obvious inputs. SWE-style tasks add navigation, multi-file changes and execution in an existing project. Clean-image grading tests whether the artifact is sufficient outside the agent's altered working environment. Together they support a more specific shortlist than either a coding preference ranking or a single exam result.

The intended workflow determines what comes next. In a human-assisted editor, the developer may supply context, reject poor suggestions and combine partial outputs. In an autonomous issue-to-patch workflow, the agent must obtain that context and return a coherent change itself. These systems can use the same model and produce different outcomes. The selection unit should be the configuration being purchased or deployed: model, agent, tools, access and integration.

A convincing local comparison can use representative work already in the team's queue: changes in the relevant languages and build systems, tasks requiring unfamiliar modules, regressions involving several components, and ambiguous issues that need clarification. Acceptance should follow the actual request and maintained behavior. Passing hidden tests whose requirements conflict with the issue would measure guesswork; passing an under-specified test while omitting a requested feature would measure insufficient coverage. Saved patches, failing traces and review changes show which mechanism occurred.

The best public row is therefore not automatically the best repository agent for the team. A candidate with slightly lower aggregate resolution can be preferable if it handles the required repository class, respects change boundaries and produces maintainable patches with fewer substantive corrections. Another candidate may justify a more capable model because it consistently resolves the difficult cross-component cases. The decision should identify those cases rather than use “more intelligent” as the explanation.

User-outcome evidence supplies a separate perspective. METR's 2025 randomized study assigned 246 tasks from 16 experienced open-source developers to AI-allowed or AI-disallowed conditions. Under the tools and working conditions studied, AI access increased completion time by 19%, while participants believed it had sped them up. This is evidence about assisted work on familiar mature repositories, not an autonomous patch benchmark. It establishes that capable tools and perceived usefulness can coexist with additional work in a particular workflow. [METR study v2](https://arxiv.org/html/2507.09089v2).

METR's February 2026 follow-up explains why simply extending that estimate is also inappropriate: participation and task selection changed as developers became reluctant to work without AI, and concurrent agent use complicated task-time measurement. The later observations do not identify one stable productivity multiplier for all current tools. For a deployment decision, use the study to ask where integration and correction work falls, then examine the current workflow. [METR follow-up](https://metr.org/blog/2026-02-24-uplift-update/).

This comparison produces a practical recommendation. Use executable repository evidence to shortlist autonomous patching systems. Use inspection of the submitted change and its actual acceptance conditions to select among that shortlist. If the product is an assistant embedded in a developer's work, include the developer's completion and correction process in the decision. A high benchmark score and a useful human-assistance result are complementary evidence when both correspond to the deployed configuration; neither should be substituted for the other.

## A benchmark portfolio should explain the choice

The useful portfolio has a reason for each component. Academic reasoning helps identify problem-solving capability. Expanded function tests probe implementation correctness. Repository tasks exercise sustained changes in an environment. Interaction tasks exercise policy and communication over time. Preference observations help distinguish answers people can use. Long-context tasks examine whether evidence remains usable as material grows.

For customer support, the decisive connection is between policy evidence, conversation and authorized outcome. For repository agents, it is between the issue, the change and maintained behavior. Those connections determine which public measurements deserve weight and which local observation would alter the recommendation.

This leads to three clear choices. Retain a benchmark when it supplies distinct, relevant evidence. Change its weight when the deployment responsibility differs from its population. Regrade or replace it when the task or scorer is materially defective, preserving the earlier result as historical evidence. The purpose is a defensible selection with known reasons, not a larger collection of impressive-looking scores.
