# 国内外 Personal Agent 研究：长期任务如何跨越记忆、授权与执行边界

资料截止：2026年11月9日。面向规划个人 Agent 产品、系统架构与商业路线的产品负责人和技术决策者。

## 一、真正需要持续的是任务，而不只是对话

个人 Agent 的价值取决于一件具体的事：用户隔了一天回来改变要求时，系统能否找到昨天尚未完成的工作，理解哪些条件已变，使用现在仍有效的权限，并确认外部世界最终发生了什么。记住用户喜欢靠窗，只解决了旅行安排的一小部分；它还要知道这次同行者需要靠过道，上一张机票是否出票，以及用户昨天允许的付款金额是否仍适用于今天的改签。

因此，本报告将 Personal Agent 定义为持续服务个人目标、能够利用跨会话状态并在一定授权范围内采取行动的系统。一次性聊天可以提供建议，固定脚本可以按时发送提醒，企业流程平台可以严格执行已定义的审批。Personal Agent 的独特用途在于处理这些流程之间的信息缺失、意图变化和例外情况。它也可以只承担其中一段：持续整理票据并生成可靠草稿，已经可能比能够点击更多网站却无法核对结果的系统更有价值。

当前公开证据支持三个判断。第一，长期记忆、持续执行和外部交易并没有自然合并成一个完备功能；它们经常由不同模块、账户或环境承担。第二，跨会话能力的瓶颈正在从“能否找到历史文本”转向“历史信息是否已更新、当前授权是否覆盖动作、回执是否证明完成”。第三，商业上较容易成立的是高频、有稳定信息来源、错误可以发现和修正的任务。对低频但后果重大的事务，自主程度提高可能同时增加核对成本和损失风险。

本报告采用两条任务链比较产品：跨会话旅行与日程，以及持续费用/报销管理。任务链中的步骤是分析情境，未在列举的消费产品上亲自运行。事实依据分别来自当前产品文档、注明日期的发布材料、公开代码、研究论文，以及能够定位到版本和操作的第三方体验。

## 二、不同路线已经解决了什么

把产品放在同一张功能表里，最容易丢掉版本和运行条件。2025年的发布演示、2026年的现行文档、受邀测试和本地开源框架，不能直接按同一种“已上线能力”比较。

|路线与代表|可核实的能力和证据日期|对长期任务有影响的使用条件|
|---|---|---|
|云端通用工作：ChatGPT Work|11月9日访问的当前文档描述项目上下文、云端续接、定时和事件任务；旧 ChatGPT agent 帮助页顶部已经宣布不可用|Work按付费计划、地区和工作区权限开放；云浏览器排除Free/Go，网站本身也可限制自动访问。旧Agent的40/400次额度不适用于当前比较|
|个人数据与任务结合：Gemini|当前 Tasks 文档提供浏览器、连接应用及日程动作；2026年1月 Personal Intelligence 发布说明跨 Gmail、Photos 等来源个性化|Tasks要求个人Google账户、AI Pro或Ultra以及Keep Activity；不能按同条件外推工作/学校账户。1月美国公测条件只描述首发，后续地区扩展不能由那篇发布稿推断|
|持续项目与自动化：Manus|当前 Projects、Automations、Browser Operator 文档分别说明上下文复用、触发、浏览器执行|Projects页称所有订阅层级可用；具体自动化源和高级触发受账户/连接条件限制。本地Operator推荐Chrome/Edge，运行桌面必须在线；积分取决于任务资源|
|中国服务生态：千问|2026年1月15日公告将购物、出行等生态动作公测与Task Assistant邀请测试分别说明|生态内服务接入有现实价值，但公告未披露每类任务的持久状态、排队取消或回执核验协议。不能把邀请测试覆盖到所有普通用户|
|设备入口：豆包手机助手|中兴3月公告是M153技术预览版；9月17日媒体实际操作的是消费者版NaviX Ultra|第三方App许可、手机型号和规则生效阶段影响可操作范围。预览演示、消费者版首日观察与11月状态需要分开|
|系统上下文：Siri AI|Apple 2026年9月14日发布英语beta、个人上下文、屏幕理解和系统动作、对话跨设备同步|需要支持Apple Intelligence的设备和语言；发布时iOS/iPadOS/watchOS的欧盟可用性受限，中国未开放新功能。未来语言计划不计作已验证交付|
|可检查的执行框架：Open-AutoGLM、OpenClaw|公开动作处理代码、文件记忆与网关文档展示实现选择|代码和文档快照证明机制存在，不代表所有部署使用同配置，也不代表生产级长期可靠性已经测定|

来源：[ChatGPT Work](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex)、[旧Agent页面](https://help.openai.com/en/articles/11752874-chatgpt-agent)、[Gemini Tasks](https://support.google.com/gemini/answer/17094507?co=GENIE.Platform%3DAndroid&hl=en)、[Manus Projects](https://manus.im/docs/features/projects)、[千问发布](https://www.alibabagroup.com/en-US/document-1948497434959151104)、[中兴预览版发布](https://www.zte.com.cn/china/about/news/20260303C3.html)、[Apple发布](https://www.apple.com/newsroom/2026/09/siri-ai-a-profoundly-more-capable-and-personal-assistant-is-here/)。

这些路线的差异首先来自任务执行条件。云端产品容易在用户关机后继续查资料和等待触发，个人生态产品更容易找到同一账户中的邮件和日历，设备助手更容易取得屏幕与本地内容。跨平台GUI能到达更多界面，却要承担登录、验证码、页面变化和应用规则的成本。接口连接覆盖面较窄，但动作参数、返回状态和权限范围通常更容易表达。

对中国用户而言，能操作实际使用的交通、支付和生活服务，可能比在海外网站完成复杂演示更重要；对海外Google生态用户，邮件和日历的连贯访问能减少重复输入。产品策略应由目标用户的真实服务组合决定，不宜先把“通用Agent”作为独立目标，再要求用户迁移全部生活工具来适配。

## 三、旅行与日程：同一个目标要经历多次授权变化

设一位用户计划从上海出发参加下月的会议。第一天只给出预算和日期，第二天补充目的地当地时间九点必须到场，第三天改为携同行动不便的家人，并表示可以增加一定费用。最初的“经济舱、靠窗”已经不足以指导后续执行：时区影响到达日，同行人影响座位和接驳，增加预算不一定包含不可退酒店或改签手续费。

一个能持续处理这项工作的系统，需要把“准备”和“承诺”分开。候选航班只是可能方案，填写表单仍可撤销；订单提交但没有回执时，外部状态未知；出票、扣款和日历更新又是三个不同结果。把聊天窗口中的“已完成”当成最终状态，会使重复付款、旧行程提醒和漏改酒店成为同一错误的不同表现。

|任务环节|需要保留的状态|产品路线可以承担的部分|决定是否继续的核验|
|---|---|---|---|
|建立目标|出发地、当地时间、预算、同行者、来源|项目/会话记录承接目标；个人上下文补充历史信息|历史偏好是否仍适用于本次旅行|
|补充与调整|新约束覆盖哪些旧条件、已排除的方案|模型重新规划，文件/连接源提供依据|旧任务是否真的采用新版本资料|
|查询与选择|报价时间、币种、行李、退改条款、可售状态|云浏览器、生态服务接口、设备App actions|候选必须重新确认库存和总价|
|填写与提交|乘机人、动作范围、单次金额、授权时效|已接入工具或允许的GUI执行|允许访问网站不等于允许买下任意方案|
|核对结果|订单号、票号、扣款、日历版本、失败项|读取邮件/订单页/日历并交叉核对|未收到回执时先查询，不立即重复提交|
|后续变化|航变、改签请求、退款进度、关联酒店|定时或事件触发后继续处理|新的差价、退改损失或同行者变化可能需要新决定|

ChatGPT现行云浏览器文档明确区分网站访问许可和重大动作确认；远程浏览器有独立登录会话，能够后台运行，也可能因网站限制需要人工接管。这支持“查找、准备、在允许范围内执行”的判断；它没有承诺每个供应商都能完成出票、退票和退款。把一次预订演示扩成所有旅行事务托管，没有证据基础。[云浏览器文档](https://help.openai.com/en/articles/20001280-using-cloud-browser-in-chatgpt)

Manus则提供了一个容易忽略的跨会话细节。Projects文档的配置表区分：指令更新在当前任务下一条消息时生效，文件更新只影响之后创建的新任务。用户把公司差旅标准换成新版，并不代表已经运行的旧任务会采用新文件。产品应向执行器传递明确的资料版本，并在继续前识别受影响的动作；只更新项目知识库的界面提示不足以解决这一问题。[Manus配置更新](https://manus.im/docs/features/projects)

设备助手能够利用正在看的屏幕，但第三方应用是否允许操作是另一道实际边界。《每日经济新闻》在2026年9月16日操作消费者版豆包手机时，观察到能够打开微信、淘宝等应用，却无法执行相关应用内任务；同次体验中，检索指定抖音账号约用26秒，购物支付等关键环节仍需确认。这个单次、指定版本且处于规则公示期的观察，证明“打开App”“完成检索”“完成交易”的区别，不能用26秒估算长期任务平均耗时，也不能据此判断11月所有应用仍被限制。[可定位的媒体体验](https://m.nbd.com.cn/articles/2026-09-17/4584694.html)

在这条链上，当前较合理的产品承诺是提供持续行程工作区：聚合候选与订单、发现冲突、准备改签方案、将需要决定的费用和条件集中呈现。若承诺自动承担全程，则必须进一步解决第三方受理状态、重试和补偿。所谓“多一步确认”只有在给用户提供了准确总价、操作对象和后果时才有用；让用户重复批准模糊的“继续处理”并不会提高控制力。

## 四、持续个人事务与报销：价值来自关联，而非把文件堆在一起

报销比旅行更适合观察高频价值。每个月的材料形式相似，但内容会变：同一酒店费用可能有预授权、正式支付、发票和退款；一张票据可能同时出现在邮箱附件与手机相册；外币交易日期、实际结算汇率和财务制度的换算规则又不相同。

Agent首先应建立交易关联，而不是把每张识别到金额的图片累加。原始订单、支付流水、发票和退款属于不同证据。两封邮件可以指向同一笔交易，一笔支付也可能拆成多个可报销项目。若用户跨会话指出某项属于私人消费，系统需要修改分类和报销草稿，不能改写原始支付事实。制度更新则要保留适用日期：旧出差按当时标准处理，并不自动跟随当前最高额度。

|阶段|需要解决的变化|适合Agent承担的工作|外部确认或人工交接|
|---|---|---|---|
|材料摄取|附件补到、重复截图、邮件撤回|读取获准来源、关联原件、标记缺项|限定邮箱/文件范围，保留原件出处|
|费用归一|退款、币种、税费与多人分摊|计算草稿、查找重复、解释差异|以真实支付与制度核对，而非仅凭摘要|
|用户纠正|私人消费、项目归属、旧偏好|修改任务事实和相关派生结果|说明哪些已经提交，哪些仍可改|
|提交|企业身份、审批顺序、收款账户|在正式接入且获准时填写或提交|取得财务系统受理号，不能以文件生成代替|
|退回与到账|补证、拒绝、部分支付|按新信息更新并提醒，查询状态|重复触发不应重复提交；到账需支付凭证|
|撤权与遗忘|关闭邮箱连接、取消自动任务|停止新摄取，处理取消，删除允许删除的个人副本|企业已受理记录有独立保留规则，不能承诺一并擦除|

Manus的项目与自动化适合承接“每月一组同类材料”的持续工作；Gemini的个人账户连接有利于从邮件和日历关联活动；Work可以将连接应用与浏览器组合使用。它们在公共文档中展示的是构成这条链的能力。财务系统角色、组织审批、支付账户与正式提交回执仍需逐一接通，消费产品拥有邮箱权限并不能替代企业授权。

任务的终点应由用户的真实需要决定。个人记账可能在核对后的清单和提醒处就结束，企业报销则要持续到受理、退回或付款。前一种场景不必为了“闭环”强行接入付款；后一种场景也不能以生成表格就宣称完成。对资料不多、拒绝常驻邮箱权限的用户，手动上传后生成草稿可能已经是更好的方案。

主动执行增加的是及时性，也增加了重复与过期问题。定时任务适合月末检查，事件触发适合新票据或退回通知，轮询适合没有事件接口的退款状态。它们都应在读取到新状态后判断是否需要行动：同一退款通知重复投递不应生成两笔退款，同一缺件状态连续出现也不需要每天重交。只有当用户的授权仍覆盖接下来的动作、资料足够并且外部状态可确认时，触发才应转成写入。

## 五、记忆如何转成动作，又如何接受纠正和遗忘

“长记忆”容易被理解成保存更多对话。对持续任务而言，更关键的是让记忆保留来源、时间、适用范围和失效关系。一个经过压缩的摘要如果丢掉“这次旅行”或“直到月底”的限定，检索越成功，执行错误反而可能越稳定。

```text
用户当前要求 ────────┐
历史偏好、原件与连接源 ├→ 识别来源/时间/适用范围 → 当前任务状态
外部订单与支付回执 ───┘                         │
                                               ↓
                                 形成候选动作与影响范围
                                               │
当前身份与授权 → 权限/动作条件核对 ──────────────┤
                                               ↓
                                     外部执行 → 读取回执
                                               │
                          更新任务事实、通知用户、安排后续

纠正：定位原事实 → 标记旧版本失效 → 更新受影响的草稿/排队任务
遗忘：定位来源与派生项 → 删除或停止使用 → 处理索引/副本传播
```

这里至少有六类对象。原始证据包括票据和邮件；任务状态记录现在进行到哪一步；长期偏好提供默认选择；承诺记录用户已经批准的具体范围；回执证明外部状态；凭证引用指向可用身份而不把密码塞进记忆。混在同一段文本中会使“以前这么做过”“我更喜欢这样”和“现在允许这样做”失去区别。

冲突处理也不能只遵循“最新文本优先”。最新网页可能是错误信息，旧发票仍是某笔历史支出的有效凭证。较合理的顺序是先识别对象和时间，再看证据权威与用户当前指令：用户可以修改此次偏好，银行决定已支付金额，供应商决定订单受理状态。对不同对象，应由不同来源定真，而不是让一个流畅摘要覆盖全部事实。

Google在Personal Intelligence发布说明中承认过度个性化和时间、关系变化的理解问题。例如频繁出现某类活动并不必然等于用户喜欢它。这个局限说明被观察的行为与用户表达的偏好需要分开；基于连接源的推断应允许用户纠正，并保留推断来源。[Google发布说明](https://blog.google/innovation-and-ai/products/gemini-app/personal-intelligence/)

公开实现也展示了可行的分层。OpenClaw当前记忆文档把稳定用户信息、持久非个人档案事实与日常工作记录分别组织，要求偏好变化时替代旧的有效项，而非保留两条矛盾指令。这种可读文件便于检查和迁移，但仍有检索索引、启动预算、写入来源和派生摘要的问题；文件在用户磁盘上并不自动等于所有推理和处理都在本地。[OpenClaw记忆](https://docs.openclaw.ai/concepts/memory)

遗忘尤其需要沿数据流处理。ChatGPT当前文档区分“不再提及”、删除保存的记忆、删除聊天或文件以及断开连接；删除聊天不一定删除独立记忆，关闭个性化也不删除原始聊天，更新传播需要时间。因此用户的“忘记这件事”应被解释为具体操作范围：是不再用于推荐，删除个人资料副本，还是断开未来读取源。已提交给航空公司或企业财务的记录属于另一系统，不能由删除聊天推断已删除。[Memory管理说明](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)

对于报销，一份正确的当前草稿可能仍由旧索引检索到错误分类。对于旅行，一项已经取消的约束可能仍留在等待确认的表单中。纠正成功的可观察结果应当是受影响的下游状态改变，而不只是Agent回答“我记住了”。

## 六、授权撤回以后，系统究竟应该停止什么

身份认证回答“这是哪个账户”，数据权限回答“可读哪些内容”，网站访问许可回答“能否进入该站点”，业务授权回答“可否采取这项动作”。它们相互关联，却不能互相替代。一个已经登录的浏览器有付款能力，不说明用户允许本次付款；一个收到账单的邮箱也不赋予任何外部邮件发送权。

逐项确认适合金额大、对象变化或不可逆的动作，但频繁确认会把用户变成执行器。范围授权适合重复、低风险、边界明确的任务，例如“每月读取这个文件夹，生成费用草稿；不要提交”，或“发现航变后更新候选方案并通知我”。范围应包含对象、金额/动作上限、时效和停止条件，而不只是长期有效的“替我处理”。

|撤权发生时的状态|应当发生的变化|不能据此宣称的结果|
|---|---|---|
|触发器尚未触发|停止新的检查或启动，标明自动化已停|已有任务已取消|
|任务已经排队|取消队列项或使执行前授权核对失败|单纯断开界面就保证队列被清空|
|正在读取/填写|终止执行并保存必要进度；释放或撤销会话|所有已取出的资料自动消失|
|请求已发出、回执未知|停止进一步写入，查询外部状态并请求必要交接|请求超时就是失败，可以安全重试|
|交易已确认|依据商家条件办理取消、退款或其他补偿|撤销令牌能够回滚已出票订单|
|已进入第三方审批|通知责任系统并尝试撤回；明确不可撤回部分|删除本地草稿就撤回外部提交|

Gemini文档给出了具体例子：停止Chrome侧栏中的网页浏览之后，任务仍可能使用远程浏览器或其他工具；完全取消需要在Gemini任务中停止。反过来，用户拒绝特定动作，文档描述的是停止该动作而非换路执行。两种“停止”对应不同边界，产品界面应让用户知道到底停止了浏览器、整个任务还是未来调度。[Gemini Tasks停止说明](https://support.google.com/gemini/answer/17094507?co=GENIE.Platform%3DAndroid&hl=en)

协议层只能解决部分问题。RFC7009描述令牌撤销，并承认传播可能有短窗口；撤销refresh token与access token的关联行为还取决于服务器支持和策略。MCP授权规范约束令牌接收者和透传，能够减少凭证被用到错误服务，但不负责判断差旅差价是否获得当前用户同意。业务动作仍需独立的授权和状态核验。[RFC7009](https://www.rfc-editor.org/info/rfc7009/)、[MCP授权规范2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

公开代码有助于进一步分清承诺。Open-AutoGLM的动作处理文件在Tap动作包含message时调用确认回调，默认要求用户在控制台确认，拒绝会结束该动作；登录或验证码可交给人工接管。但这个文件没有独立证明所有敏感点击都一定被识别并带上message。确认入口的存在与敏感行为识别完备，是两个不同命题。Note和Call_API在这个快照中还存在占位处理，不能从动作名称推断长期记忆与业务接口已经实现。[动作处理代码快照](https://raw.githubusercontent.com/zai-org/Open-AutoGLM/refs/heads/main/phone_agent/actions/handler.py)

失败恢复最需要保留的是可恢复的事实，而非一长串内部叙述。用户接管时应看到操作对象、最后得到的回执、仍不确定的状态和建议下一步。对“提交后超时”，读取订单优先于再次提交；对权限失效，应重新授权或交接，不能把权限错误当成临时网络错误无限重试。对于不能补偿的动作，等待用户作出最后决定常常是产品能力的一部分。

## 七、可靠性证据与架构选择

公开基准说明了不同薄弱点，但不提供当前消费产品的统一排行榜。LongMemEval v2以500个问题覆盖信息提取、多会话、时间、知识更新和无答案时拒答；其标准长历史设置检验记忆检索与使用。tau-bench v1使用模拟用户、领域API与政策，以数据库终态判断任务，并用pass^k观察多次一致完成。AgentDojo v3包含97个用户任务和629个安全用例，在不可信工具返回中加入攻击目标，同时检查任务效用与安全结果。[LongMemEval](https://arxiv.org/html/2410.10813v2)、[tau-bench](https://arxiv.org/html/2406.12045v1)、[AgentDojo](https://arxiv.org/pdf/2406.13352v3)

记忆问答正确不等于交易成功，数据库终态正确也不必然捕捉每一次授权越界，抵抗注入则不能靠全部拒绝任务获得有用服务。部署决策因此需要几种结果并列呈现：在多少个可执行任务中完成了多少，跨多少次会话和多少天，外部结果如何核验，有多少次用户介入，撤权后还有没有动作，平均耗时中是否包含用户等待和返工。一次成功演示既没有稳定分母，也常常避开凭证过期、变更和取消，适合证明可能性，不适合估算长期服务水平。

这不意味着每个用户都要运行大型测试。低频整理可以直接从结果核对开始；持续事务则要关注真实使用中出现的失败方式和可恢复性。对产品团队，最值得改善的指标常常是“每次有效完成需要用户花多少时间”，因为它同时约束任务成功、核对负担和接管质量。

|架构选择|主要收益|主要成本如何影响任务|
|---|---|---|
|端侧/本地记忆|接近屏幕和本地文件，便于用户检查与删除|设备离线、同步冲突、更新维护；本地保存不代表模型调用不出端|
|云端状态与执行|跨设备、后台触发、统一任务状态|独立凭证与网站访问、持续用量、远程数据处理条件|
|专用接口|结构化参数、较明确权限和回执，较易做重复请求控制|接入和版本维护成本，组织权限可能比技术接通更难|
|GUI操作|覆盖缺少API的既有服务，复用熟悉界面|页面变化、验证码、隐私屏幕、风控与动作语义不确定|
|单一生态|身份和服务衔接较顺畅，已有订单数据丰富|覆盖偏向本生态，跨供应商比较和迁移可能受限|
|跨平台/自托管|更广的工具选择、数据组织与流程控制|连接器维护、凭证隔离和故障响应由用户或服务商承担|

OpenClaw文档尤其明确，一个网关通常面向单一可信操作者或相互信任的团队，不能直接当成敌对多租户隔离。将个人自托管配置包装成面向陌生用户的服务，会改变原有信任边界和运维责任。[OpenClaw安全边界](https://docs.openclaw.ai/gateway/security)

连接器覆盖有乘法效应，也有维护负担。旅行需要邮件、日历、订单和支付至少几类系统同时可用；任何一环权限变化都可能中断链条。因此应围绕目标用户最常见的完整链选择连接器，先保证少数高频链的回执与恢复，再扩展服务。只统计连接器数量，很难反映用户真正能交付多少任务。

## 八、商业路线必须与净任务价值相连

订阅模式适合高频任务复用固定成本，但长任务的推理、浏览、轮询和返工不会因为月费固定而消失。Manus当前计划页说明积分随任务复杂度和资源变化，并提供用量历史；现有页面不足以给出统一的“处理一份报销多少钱”。产品如果不能让用户看到典型任务的消耗和失败后的成本，就很难判断持续委托是否值得。[Manus积分说明](https://manus.im/docs/introduction/plans)

交易佣金能让用户减少直接付费，却把平台收入与完成交易连接起来。推荐顺序、可接入商家和取消购买的建议，可能与用户省钱目标发生张力。广告模式也可能补贴免费服务，但需要在推荐中区分商业呈现和按用户目标排序。这里不能假设某一厂商当前都采取同一模式：ChatGPT商家页现已明确转向商品发现和商家自有网站/App结账，并说明该页所述站外成交不收费用、当前购物覆盖美国。2025年的独立Instant Checkout安排不应直接当作当前商业结构。[当前商家说明](https://chatgpt.com/merchants/)

设备生态通过硬件、账户留存和服务使用回收成本，优势是入口和上下文近；若外部App操作受限，新增价值可能集中在系统搜索、通知和少数合作动作，用户是否愿意为此换机就成为关键。平台入口模式则可能通过电商、内容和支付使用间接获益。其优势是完成生态内交易所需的身份和供给已经存在，局限是任务的可选方案可能围绕现有供给展开。

迁移成本也不限于导出聊天文本。用户需要带走偏好来源、当前任务状态、待办承诺、订单关联和已经纠正的错误，同时在新系统重新建立合法授权。保存越多私有格式的状态，迁移越困难；公开文件便于搬迁，但索引、连接器和外部身份仍不会随文件自动转移。产品若希望靠可信长期关系留存，应让用户看懂已经保存了什么及其用途，而不是把不可迁移当成唯一留存手段。

下面用明确假设计算任务经济性。每月净价值等于节省人工时间的价值，减去任务说明、核对、失败返工、固定费用、按次费用和外部损失。假设时间价值为每小时60元，月固定费用100元；这不是任何产品的现价或实测表现。

|假设场景|任务量与耗时假设|净节省时间|费用后净价值|
|---|---|---:|---:|
|票据草稿、核对较轻|每月20次；人工20分钟；说明2、核对4；失败15%，每次返工15；每次费用1元|235分钟|115元|
|同类任务、核对较重|每月20次；核对10分钟；失败30%、返工20；其余同上|40分钟|负80元|
|低频旅行整理|每月2次；人工90分钟；说明10、核对20；失败20%、返工30；每次费用5元|108分钟|负2元|
|旅行整理加入损失敏感性|前项基础上每月期望外部损失40元|108分钟|负42元|

计算由本报告附带脚本实际执行。第一种票据情境覆盖固定费用的分界约为每月9.3次，即离散任务至少10次。如果用户已为其他任务购买订阅，应只计新增或合理分摊的费用；如果节省时间不能转成现金，净价值更适合解释为愿付价格参考。延迟完成、隐私偏好和关键任务的尾部损失也不宜完全压缩成一个均值。

算例说明，降低核对与返工负担往往比增加自主动作数量更有商业意义。一个只生成可靠票据草稿的系统，可以在较小权限下反复产生收益；一个偶尔自动订票但每次都要重查全部条件的系统，未必值得单独订阅。重复任务越多，固定费用越易摊薄，但错误也会重复积累，因此可纠正、可停止和可恢复直接影响留存与服务成本。

## 九、面向产品与使用者的选择

对资料密集、重复频率高、结果容易核对的个人事务，当前方案适合从“读取指定来源、组织原件、计算和生成草稿、提示变化”开始。用户可以授予持续读取范围，保留提交与支付决定。跨会话记忆应优先保存已确认的规则和当前任务事实，减少每次重述成本。

对旅行和日程，较合理的授权是允许搜索、比较、准备和监测，让系统在报价、退改条件或对象变化时交付一个具体决定。写日历可以在明确范围内自动化，但出票、付款和可能损失费用的取消，需要与真实供应商回执连接。若相关网站持续阻止自动访问、身份无法可靠续接，人工完成最后一段比反复换路更有效。

对企业报销，首先选择组织已有权限模型支持的接入。个人Agent可以减少材料整理与解释负担，正式提交、审批和支付仍应遵守企业系统的角色和状态。没有连接正式财务系统时，应把承诺限定在可核对的报销草稿，不能让产品名称掩盖未完成的环节。

对要求全自动资金操作、不可逆承诺或长期无人监管的人群，现有公开资料尚不足以支持把这些代表产品当成稳定的全权代理。改变这一判断所需的证据很具体：按版本和地区记录的连续任务成功率、包含中途改意与撤权的轨迹、队列与在途取消语义、外部回执和失败补偿，以及用户实际核对时间。这些证据缺口不妨碍已经可用的整理、准备和监测价值，但会决定产品可以承诺到哪一步。

个人Agent的长期竞争力，最终表现为用户能放心交付多少具体工作，以及交付后减少了多少重复劳动。记忆、授权和执行需要围绕同一任务状态协作；能够明确等待、准确交接和确认外部完成，是持续服务的一部分。
