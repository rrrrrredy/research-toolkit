# 八家模型公司的研发管线：从训练数据到可交付的 Agent

## 核心要点

模型研发的共同骨架是数据、训练、评测与部署，但决定竞争方式的是这些环节如何互相反馈。DeepSeek 把算法和集群效率一起设计；Kimi 把工具、任务和执行环境做成后训练的数据生产系统；MiniMax 让长推理的计算成本进入模型设计；Google 将多模态训练与跨数据中心基础设施结合。OpenAI 将代码任务训练与容器交付连接，Anthropic 则披露了迭代评测如何进入发布决策；字节以复杂应用需求组织能力评价，腾讯将多产品反馈接入后训练改进。

本文据此提出一个组织判断：长期平台负责可复用的训练、数据和评测能力，模型节点项目组负责整合与取舍。这是对公开技术接口的分析，不是八家公司均采用同一张组织图的事实声明。数据与标注贯穿训练和线上反馈；预训练、中训、后训练的交接应绑定 checkpoint、数据及评测版本；Agent 交付应同时绑定模型、环境与配置；真正可积累的资产是能复现、验证和回滚的任务与系统。

研究截至2026年10月13日，以八家公司的代表性发布节点比较研发方式，不按不同时间的榜单给公司排名。字节与腾讯的组织判断分别限于吴永辉、姚顺雨加入之后。

## 管线总览

管线首先把能力目标变成可收集的数据和可执行的任务：预训练需要覆盖、去重和配比；监督微调需要问题、示范与筛选；强化学习还需要可反复运行的环境和可靠反馈。数据团队的交付物因此不只是文本文件，还包括任务定义、样本出处、过滤规则和质量记录。模型团队决定学习目标与训练配方，基础设施团队把配方变成稳定运行的作业；评测将能力变化和产品失败送回前两者。

从公开材料可以识别这些职能之间的依赖，不能据此宣布它们在公司内一定是独立部门。一个实用的交接设计是：数据交付带版本的样本及其质量说明；训练交付 checkpoint、配方和异常记录；评测交付固定输入、环境、结果与失败案例；产品交付可运行配置及线上反馈。这样出现退化时，能区分数据、权重和执行环境变化。这是本文的工程建议，不是对未公开内部流程的补写。

## 八家公司对比

| 公司与节点 | 公开管线特征 | 组织与交付上的含义 |
|---|---|---|
| OpenAI：codex-1，2025年5月16日 | 从 o3 延伸到真实代码任务的强化学习与容器执行 | 模型行为要与仓库、工具及补丁验收配套 |
| Anthropic：Claude 4，2025年5月22日 | 人与模型反馈、迭代评测、明确发布决策程序 | 训练、评测与发布责任可分别识别 |
| Google DeepMind：Gemini 2.5 Pro/Flash，2025年6月17日正式版 | 多模态数据、TPUv5p 跨中心训练、工具使用后训练 | 共享基础设施支撑多个模型与能力方向 |
| DeepSeek：V3，2024年12月26日 | MoE、FP8 与通信调度共同优化 | 系统效率直接约束模型设计和训练配方 |
| Moonshot：Kimi K2，2025年7月11日 | 工具规格、任务、轨迹生成与可验证反馈 | 数据生产逐步变成环境与反馈系统 |
| MiniMax：M1，2025年6月16日官网发布 | 持续预训练、长推理 SFT、CISPO 强化学习 | 架构与训练系统共同承担长推理成本 |
| 字节 Seed：Seed2.0，2026年2月14日 | 真实复杂任务评测与在线使用需求相连 | 基础研究与应用职能之间需要具体反馈接口 |
| 腾讯：Hy3，2026年7月6日 | 基建重构后，将多产品反馈用于后训练迭代 | 模型、Infra、数据平台与产品形成可见协作面 |

OpenAI 的 codex-1 原始系统卡把训练对象说得很具体：多种环境中的真实软件工程任务，目标包括代码风格、PR 偏好和迭代测试。发布时的产品把每个任务放进独立容器，交付补丁和可核查日志。这里能确认的是模型、环境和产物的接口；系统卡没有披露完整预训练配方，也没有给出数据部门的汇报线。[系统卡](sources.md#s01)、[发布说明](sources.md#s09)

Anthropic 的 Claude 4 系统卡同时披露了多样化预训练、人类反馈与 Constitutional AI，以及训练中多个快照的评测。发布判断由 Responsible Scaling Officer、CEO、董事会和 Long-Term Benefit Trust 参与监督，最终发布需确认相应措施已经就位。它为“谁对发布负责”提供了比作者名单更直接的证据。当前 RL Data Platform 招聘又呈现出研究者、标注者与数据工程之间的工作接口，但不能倒推该岗位在2025年已经完全相同。[系统卡](sources.md#s02)、[招聘](sources.md#s10)

Google 的 Gemini 2.5 报告把模型与平台能力放在同一条证据链上：预训练涵盖文本、代码、图像、音频、视频，后训练包含指令、偏好和工具使用数据；TPUv5p 与 Pathways 支持跨数据中心运行和局部故障后的弹性恢复。这里的组织含义是多模态数据、训练系统和能力评测必须共同迭代，不能把成绩只归因于某一支算法小组。报告署名证明贡献参与，不等于逐人的管理关系。[原论文](sources.md#s03)

DeepSeek-V3 的区别是把训练效率的细节公开到架构和系统层：MLA、MoE、FP8 与 DualPipe 相互配合；预训练后继续做上下文扩展和后训练。论文分别列出研究工程、数据标注等贡献，但不足以恢复正式组织图。其成本数字也不能当成公司全部研发成本；报告明确未纳入此前研究与消融实验。这更支持“算法与系统共同优化”的判断，而不是未经核实的低成本组织神话。[原论文](sources.md#s04)

Kimi K2 公开了较完整的数据生产链：工具规格来自真实工具与合成工具；再生成任务及交互轨迹，按任务判据筛选；软件工程任务补充真实沙箱执行。后训练同时使用可验证反馈和针对开放任务的模型评价。由此可识别的协作对象是任务、环境、判据和轨迹，不是笼统的“多买标注”。论文没有公开谁拥有最终产品发布权。[原论文](sources.md#s05)

MiniMax-M1 从 MiniMax-Text-01 继续预训练，再用长推理示范启动 SFT，随后扩展强化学习。混合注意力与 CISPO 分别处理长轨迹计算和训练更新效率；软件工程沙箱把代码执行反馈接入训练。这条路线说明后训练成本不能脱离模型架构讨论。论文给出的三周、512张 H800 是该轮强化学习配置，不是从零研发整个模型的投入。[原论文](sources.md#s06)

字节部分以吴永辉加入后的 Seed2.0 为节点。2025年2月21日第一财经的直接采访将吴永辉的基础研究职责与朱文佳的模型应用职责区分开，称两人当时都向梁汝波汇报；报道同时指出部分团队转汇报传闻未获回应。因此本文不把传闻写成已确认架构。Seed2.0 模型卡将科学、编程、上下文学习和实际任务作为评测维度，并讨论经授权的应用数据与开发者轨迹如何揭示需求。这支持研究与应用需要持续沟通，不能证明2026年的全部汇报线仍与2025年相同。[模型卡](sources.md#s07)、[组织报道](sources.md#s11)

腾讯部分从2025年12月17日调整之后开始。财新报道新设 AI Infra、AI Data、数据计算平台等部门，并明确姚顺雨两类职务的汇报对象。2026年7月 Hy3 官方发布说明则给出基建重构、4月预览、产品反馈、正式模型的连续节点；原始模型说明记录了多产品反馈后的数据及后训练改进。两者共同支持“基础设施与模型研发同步调整，再接应用反馈”的判断，不能证明这次组织变化单独造成了全部能力提升。[组织报道](sources.md#s12)、[技术说明](sources.md#s08)、[发布说明](sources.md#s13)

## 数据与标注

数据工作的差异首先体现在要交付什么。预训练关心语料覆盖和有效训练信号；后训练增加示范、偏好、任务判据和执行结果；上线以后，问题复现又会形成下一轮样本。DeepSeek 的数据构建与后训练章节、Kimi 的任务生成和筛选链、Anthropic 对偏好选择和对抗测试的说明，显示这些工作持续发生在不同阶段，而非训练前一次性交给“标注外包”。

具体组织上，应让提出能力需求的人说明要改变什么行为，让数据工程保存样本版本与筛选条件，让领域判断者处理标准不清或反馈冲突的问题。机器可以批量生成和初筛，人的工作也可以集中于任务定义及疑难判断；二者如何组合，应由任务反馈是否可信决定。上述分工是基于公开管线提出的建议，各公司未公开的人员规模与采购比例不能补成统一数字。

Agent 数据还多了一层状态：同一段动作文本放在不同代码版本、工具权限或文件状态下，结果可能不同。因此有效样本应保留任务起点、动作、观察、终态和判断依据。已有开发题与用户题都可以用于这样的真实测试；采用构造材料并不否定任务和测试的真实性。需要记录的是样本实际用途与重复运行，而不是另设“必须来自外部人员”的门槛。

## 训练、Infra与评测

预训练与后训练之间的 checkpoint 是交接点，却不是全部交付物。缺少分词、数据版本、评测配置或精度信息时，同一权重也可能得到不同结果。DeepSeek、Google 和 MiniMax 的原文说明了为什么优化器、数值精度、通信与容错都属于能力实现条件。建议把这些配置与 checkpoint 一起版本化，再以固定任务做变更前后核验；出现问题先定位并修复，再对受影响部分复验。

评测也有不同职责：训练中的评测帮助选方向，发布前评测检查交付是否满足要求，产品反馈发现遗漏场景。Anthropic 的发布程序说明评测结论如何进入决策；Kimi 的任务判据说明反馈如何进入学习。两者都不意味着分数越高就可以忽略任务定义。对比 Agent 时应固定或明确工具、预算、任务子集和运行次数；否则模型变化与系统变化混在一起，难以解释结果。

公开信息对正式决策权的披露不均衡。Anthropic 有明确发布程序；字节、腾讯有特定时点的职责报道；其余节点更多能确认技术贡献与交付接口。跨公司可借鉴的是让模型负责人协调能力与成本、平台负责人保障可运行性、评测负责人说明缺陷及依据，再由已授权的产品或发布负责人作决定。不能将这套建议写成八家公司已经证实的统一制度。

## Harness与Coding Agent

Harness 决定模型能看到什么、能执行什么以及如何接收反馈。OpenAI 的容器与测试日志、Kimi 和 MiniMax 的执行沙箱都表明，训练数据正在从问答扩展到有状态的任务轨迹。Claude 4 发布说明还交代了 SWE-bench 使用的工具和高计算量下的候选筛选方式；这些配置改变时，评测结果的含义也会改变。[评测配置](sources.md#s14)

交付 Coding Agent 因此需要一起验证模型、工具解析器、运行环境和项目测试。Hy3 技术说明提供不同推理框架的部署配置，海外科技报道核对了正式发布及产品接入；DeepSeek 社区的精度格式讨论则提示实际使用者会遇到权重与推理实现的匹配问题。社区提问只作为待验证的兼容性线索，不能充当内部训练或组织关系的证明。[海外报道](sources.md#s15)、[社区讨论](sources.md#s16)

这种变化要求平台把失败变成可复用任务：保留失败起点及配置，区分模型、工具与环境的责任，再对修订版本做针对性复验。重复运行可以确认缺陷是否修好，新增任务可检查修复是否过度贴合；二者需要分别记录。产品回传如果只有好坏评分而没有可复现的状态，训练团队就难以利用；只有日志而没有终态验收，也无法确认问题是否解决。能保存环境、回滚版本并重放失败的系统，才会在下一轮研发中持续降低成本。

## 不确定性

公开论文、系统卡和模型说明足以比较这些节点的技术选择，却没有披露八家公司完整的人事、预算和内部验收阈值。本文对这类事项保留未知，并把工程建议标为建议。招聘反映采集时的职责需求，媒体汇报线反映报道时点，社区讨论反映个别使用者反馈；都不外推为公司的完整现状。腾讯采用可取得的官方原始技术说明，未把未取得的 Hy3 论文写成已读材料。不同节点的实验配置也不同，本文不据此宣称任何公司普遍领先。
