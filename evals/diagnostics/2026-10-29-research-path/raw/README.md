# Research Toolkit v1.5.0 本地交付记录

基于 `be56dcc8a6c9189c35cca2fd03d3f07f3cd24fec` 完成的工作区改动。版本元数据为 1.5.0，未提交、推送、打标签或发布；没有部署网站。原有研究报告、评测案例和历史结果未修改。

## 行为变化

- 规范按任务与上下文、证据与分析、成稿与修订、审阅与交付分工；删除重复定义和无条件的局部结构要求，保留原有方法与示范。方法加载从依赖章节编号改为具名内容边界。`guide/status` 可选 `methods` 按问题取用方法，省略时沿用阶段默认指导。
- `current_work` 同时返回未完成要求与仍适用的要求，已满足的要求继续可见；已豁免、超出范围和接受限制的决定分别保留。`status.work` 按执行者明确选择的要求、主张、来源和文件组织输入，包括支持与反证原文、主稿引用和文件版本。与评审共用任务要求、来源原文的读取逻辑。
- 现有 `save` 支持 `draft.kind=analysis`，可选 `based_on` 保存输入版本、`host_task` 保存宿主实际任务引用。从原有活动日志恢复成果，不新增成果台账。输入变化列出具体文件，不自动判定结论失效。局部成果完成不会自动成为主稿或整项交付。
- 主 Agent 负责统稿，子 Agent 可以完成调查、计算、比较、解释和局部论证。短成果直接返回，需续接或较长成果保存文件；宿主承担启动、消息、等待、取消与恢复。工具没有新增 Agent 调度器。
- 审阅后端不可用继续显示为未就绪，但不阻止资料收集。任务规范、来源、评审与交付的既有检查仍在相关操作上执行。
- 公共文件读写与方法加载从工作流入口拆出；现有导入名称、工具名称和旧任务完成契约保留。新参数均可选。中英文、插件内容和本地网站页面已同步；MCP 工具仍为 9 个。

主要实现：`scripts/task_context.py`、`scripts/research_records.py`、`scripts/research_workflow.py`、`scripts/research_mcp.py`、`scripts/research_guidance.py`、`scripts/task_storage.py`。完整请求示例在仓库 `docs/usage-modes.zh-CN.md` 的“研究委派与成果交接”。

## 一次贯通接口核对

运行脚本：`verify_path.py`。这是合成冷却改造任务的接口核对；分析文字与自检内容预先提供，没有调用研究模型，没有执行宿主子 Agent。宿主引用明确使用合成值。

12 次 CLI 操作的子进程墙钟合计 **9.625 秒**；不代表研究耗时或用户节省时间。

观察到：

1. 已满足但持续适用的约束保留在工作输入中。
2. 选定主张的支持来源和反证来源原文一并返回，缺失文件被明确拒绝。
3. 按选择返回比较与委派方法。
4. 分支分析、输入版本和宿主引用可保存并恢复，未改变主稿。
5. 用户要求更新后，返回具体变化文件；整合步骤可读取先前分析。
6. 完整报告沿现有评审输入、提交意见和完成检查走到交付。

原始证据：`calls/` 保存逐次请求与返回，`execution.json` 保存命令和各次耗时，`result.json` 保存汇总；`tasks/handoff/` 保留来源、要求、分析稿、整合稿和评审交付记录。

可重复执行方式（仅供后续需要时使用，本轮不再运行）：把 `verify_path.py` 复制到本目录的同级新目录，例如 `output/research-v1.5.0-reproduce/`，使用本项目 Python 环境执行该副本。脚本会创建独立的任务和调用记录；遇到已存在的任务会退出，避免覆盖首次结果。

- 插件构建与一致性、版本元数据、DSH 配置校验、本地网站构建与页面检查完成。

- 既有记录检查暴露了新恢复逻辑对损坏活动日志的处理问题：已修为保留原日志并提示，而不是让 `status` 失败；对应失败项通过。

没有增加研究模型对照或重跑旧研究案例。必要检查完成后停止。

## 尚未运行的部分

本轮没有调用实际宿主的多 Agent 会话，也未测量研究质量、返工量或用户耗时收益。没有运行远端 CI 或进行线上部署。新增工作上下文在 CLI 贯通核对中已实际使用；MCP 的新参数复用同一函数，本轮插件 MCP 集成覆盖的是现有调用路径。

宿主协作的最小人工核查（供后续实际使用，不作为本轮新增流程）：

1. 在支持子 Agent 的宿主中，对一项已有任务调用 `status`，选择需要的 `work` 与 `methods`，通过原生委派工具发送返回内容，保留真实任务引用。
2. 子 Agent 保存一份分析成果，使用返回的 `inputs` 填写 `based_on`。更新一项相关要求后，主 Agent 重新取上下文并通过宿主的消息或恢复功能通知该子任务。
3. 主 Agent 读取实际分析文件并整合到主稿，然后沿任务原有评审和交付方式完成。

预期：执行者可读取原始输入，更新后的要求可见，保存的分析能被续接和统稿使用，局部成果不会替代主稿完成状态。注意宿主任务引用必须真实，不同宿主的可续接会话与一次性执行器应使用各自已有操作；输入哈希变化只提示文件变化。
