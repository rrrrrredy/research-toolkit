# Sources and reading notes

Primary English documentation read on 5 November 2026. These notes identify the passages used and their limits. Current undated documentation establishes the behavior described when accessed; it does not establish a feature's earlier release date. The report's workflow is hypothetical and its cost model is proposed, without measured results.

| Source | Relevant location and use | Limit |
| --- | --- | --- |
| [IETF, RFC 9110: HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html#name-202-accepted) | §15.3.3 distinguishes accepted processing from completion; neighboring 200/201/204 definitions clarify successful operation responses. | HTTP semantics do not define a complete business workflow. |
| [Stripe, Idempotent requests](https://docs.stripe.com/api/idempotent_requests) | The paragraphs on API v1 describe saved responses, parameter matching, key retention and when execution begins. | Specific to the stated namespace and conditions. |
| [Stripe, API v2 overview](https://docs.stripe.com/api-v2-overview#idempotency) | “Idempotency” and “Idempotency differences” describe replay scope and updated responses; the namespace table covers list consistency. | A v2 replay rule cannot be assumed for v1 or another provider. |
| [Stripe, Advanced error handling](https://docs.stripe.com/error-low-level) | “Network errors,” “Server errors,” “POST requests” and “Sending idempotency keys” explain uncertain outcomes, reconciliation and persistent keys. | Error recovery may still leave an operation unresolved. |
| [Playwright, Locators](https://playwright.dev/docs/locators) | “Locating elements” and “Locate by CSS or XPath” compare user-facing locator contracts with structural selectors. | Locator guidance does not promise stability in a third-party application's business flow. |
| [Playwright, Auto-waiting](https://playwright.dev/docs/actionability) | Introduction, forcing actions and assertions define the conditions checked for interactions. | Clickability and a chosen assertion are not automatically the desired business result. |
| [Playwright, Authentication](https://playwright.dev/docs/auth) | Introduction and core concepts explain isolated contexts and sensitive saved browser state. | Session separation does not define the application's account permissions. |
| [OpenAI, Computer use](https://developers.openai.com/api/docs/guides/tools-computer-use) | SDK, direct API, code execution, computer-tool and safety sections explain driver responsibilities and action generation versus execution. | Integration capabilities and guidance; no cross-route reliability measurement. |

| [GitHub, REST API best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api) | Polling, pacing, rate limits, conditional reads and repeated errors establish integration obligations. | Provider-specific advice does not establish comparative cost. |
| [OpenAI, Computer-use integration recipes](https://developers.openai.com/api/docs/guides/tools-computer-use-integration#handle-user-confirmation-and-consent) | Confirmation/consent guidance distinguishes action-time confirmation, initial permission and human takeover. | Applies to the documented integration; do not generalize every detail to other providers. |
| [OWASP, LLM Prompt Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) | Indirect injection, structured prompts, agent-specific defenses and execution controls distinguish content from authority. | Security guidance, without a measured failure rate for the proposed workflow. |
