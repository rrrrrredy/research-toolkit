Skill 不是越多越强：Agent 真正的风险，往往发生在“选择工具”那一刻

Skills 试验田：原链接

很多人讨论 Agent 时，习惯把注意力放在单个 Skill 上：这个 Skill 的提示词写得够不够清楚，输入契约明不明确，输出结构稳不稳，失败处理是否完整，评测集是否足够全面。这些问题当然重要，但如果系统真的开始进入多人协作、长期维护和持续扩张的阶段，你很快就会发现，真正让 Agent 变得不稳定的，往往不是某一个 Skill 太弱，而是系统里同时存在了太多边界接近、能力重叠、名字不同但本质相似的 Skill。

很多问题其实并不是出在执行阶段，而是出在执行之前。不是 Skill 本身不会做，而是 Agent 先选错了那个应该被调用的工具**。单个 Skill 的设计问题，解决的是“它会不会做”；多个 Skill 共存时的问题，解决的则是“这件事究竟该不该由它来做”。**这两件事表面相近，实则是两个层次完全不同的问题。

之前一篇文章里讲“误触发、越权、漂移”时，其实已经把事情的前半段讲清楚了：一个 Skill 被调起之后，可能根本不该被触发，可能做到了不该它做的层级，也可能从事实层慢慢滑向判断层，最后把事情做偏。真正值得补上的，是它的后半段：为什么这些问题会在多 Skill 系统里更容易发生。答案往往不是模型突然不聪明了，而是 Skill 一多，系统面对的就不再是简单执行，而是复杂路由。

一、单 Skill 优化解决不了多 Skills 路由问题

单 Skill 设计的目标相对明确。给定一类任务，我们希望这个 Skill 能够稳定识别、正确执行、按预期收口。在这种设置下，评测也比较直观：给正样本看是否触发，给边界样本看是否误触发，给异常样本看是否能正确拒绝。很多 Skills 的设计，做到这里就觉得系统已经比较成熟了。

但真实环境不是这样。真实环境里，系统里往往同时在线着很多个 Skills，而且它们并不是彼此毫无关系的模块，而是有很强的邻接性。用户的输入也并不会像评测集那样干净，它常常是混合的、模糊的、半成品的，里面同时带着研究意图、整理意图、写作意图、判断意图，甚至还夹着一段代码或几条个人草稿。在这种情况下，系统首先要做的不是执行，而是判断：到底应该调用哪一个 Skill，或者是否应该先降级到更低风险的处理层。

这就是为什么很多系统会出现一种很奇怪的现象：离线评测看起来都很好，线上实际使用却总觉得“不太稳”。根本原因不是 Skill 本身写得差，而是很多评测默认了一个前提——这个 Skill 面对的是一个相对孤立的判断环境。可线上不是孤立环境，线上是竞争环境。真正的难点不是“它能不能被触发”，而是“在一堆相似 Skill 同时存在时，它为什么会被选中”。

二、Skill 一多，系统增加的不只是能力，还有歧义

很多人在给自己的龙虾配置 Skill 时会天然觉得：Skill 越多，系统能覆盖的场景就越多，能力也就越强。这个判断只说对了一半。Skill 变多，表面上确实意味着能力覆盖面扩大了，但与此同时，系统的歧义也在上升。新增一个 Skill，不只是新增一个功能模块，也是在给路由器新增一个竞争候选。新增两个边界相近的 Skill，不只是多了两个工具，而是多了很多组潜在混淆关系。

这类问题在真实业务里特别常见，因为 Skill 往往是按业务命名而不是按能力边界来拆的。还是以之前文章里的案例来看，系统里很容易出现“AI 月度行研”“Agent 行研”“通用行研”“AI 代码分析”“行业信息整理”“管理摘要生成”这类名字。它们单看都合理，每一个名字都能讲出自己的应用场景，开发者也都能说出它存在的价值。**但问题在于，用户输入从来不是按技能树切好的。**用户更常见的说法是：“这里有这个月的一些 AI 材料，加上一版我的草稿，先帮我搞一版。”“这些链接先整理一下，最好顺手给我总结几个变化。”“这里有几篇文章和一个 demo repo，你帮我看看值不值得重点跟。”

这种输入天然带混合信号。它既像研究，又像整理；既像轻量写作，又可能包含代码理解；既可能是要底稿，也可能是在试探方向判断。如果几个 Skill 的区别主要停留在名称上，而不是体现在输入对象、输出层级、权限边界和失败处理上，那么 Agent 面对的就不是一个清晰的选择题，而是一组互相争抢解释权的模糊候选。

三、最危险的不是没触发，而是“触发得像是对的”

很多人更容易警惕那种一眼就能看出来的错误，比如答非所问、结构混乱、胡说八道、逻辑断裂。但在 Agent 系统里，真正麻烦的往往不是这种显错，而是一种更隐蔽的错：它选错了 Skill，但产出看起来还挺像那么回事。标题是对的，结构是对的，措辞也很专业，甚至比很多人手工写出来还顺。可问题是，它从系统层面已经偏了。

举个很典型的例子。用户说：“先把这 20 个链接整理一下，分类就行。”这其实是一个非常典型的低层任务，目标应该是去重、分类、挂主题、补标签，最多附一个轻量摘要。但只要系统里有一个描述比较宽的“行业研究 Skill”，它就很容易把“整理一下”理解成“整理之后顺手分析一下”，再进一步写成趋势总结甚至月度观察。表面看系统很主动，实际上却是在把用户的“收材料”任务升级成“做判断”的任务。这类情况，在之前提到的误触发样本里已经说得很清楚：如果用户只是让系统整理链接，不应该直接调用月度分析类 Skill，更不该自动越到趋势层。

再举一个例子。用户说：“帮我写一封邮件，概述一下这个月 AI 行业几个值得看的变化。”真正的交付物是邮件，不是月报；真正的需求是轻量概述，不是研究输出。但由于输入里同时出现了“这个月”“AI 行业”“变化”这些强研究信号，系统很容易直接调用“月度 AI 行业分析”一类 Skill，最后给出一份很认真、很完整、也很长的分析稿。它不是不会写邮件，而是从一开始就把任务类型判断错了。我把这类情况归为误触发，因为问题不是输出质量，而是路由方向。

更危险的是越权和漂移。比如你本来只是想让系统先把几份会议纪要和零散草稿整理成几个讨论方向，方便下周开会。一个边界感强的 Skill，应该做到材料归类、观察提炼、分歧点整理和待决策项列举就停住。但一个边界感弱的 Skill，尤其是在多 Skill 竞争环境下被送到了“研究”甚至“判断”模式里之后，很容易再往前迈一步，开始替你判断“最应该重押哪个方向”“资源优先投向哪里”“哪个赛道最值得下注”。这不是更聪明，而是越权。这篇文章里给出的 guardrails——先事实、后观察，观察与建议分层，高风险请求停在分析输入层，本身就在提醒一点：系统最危险的时候，往往不是没答案，而是太容易主动补出不该补的那一步。

漂移则更隐蔽。比如用户只给了几条材料：两家公司做了类似的 Agent 交互，一篇采访里提到类似方向，再加上一页带明显主观色彩的判断草稿。一个控制得好的 Skill，最多只能写“这是值得关注的早期信号，暂时不足以证明主流化”。但一旦系统已经被路由到“趋势分析”模式，又缺少足够强的漂移约束，它就很容易把这些弱信号写成确定趋势，把个别观点包装成行业共识。我把这种情况归为漂移样本，这类错最容易在形式正确的外壳下被忽略。

四、很多所谓的新 Skill，本质上只是旧能力换了一个名字

**为什么 Skill 库会越来越乱？一个很重要的原因是，很人并不是按“能力边界”拆 Skill，而是按“业务名称”拆 Skill。**于是系统里会不断长出“AI 月度行研”“海外 AI 观察”“Agent 行研”“AI 周趋势洞察”“行业材料整理”这类名字。它们看起来越来越专业，越来越贴近场景，但很多时候底层动作其实高度相似：读材料、做归类、提炼主题、写摘要、补观察、列待跟进问题。

如果输入对象差不多，输出模板差不多，权限边界也差不多，只是主题范围或时间窗口不同，那么它很可能不是一个真正的新 Skill，而只是一个旧能力的新壳子。这样的 Skill 越多，系统越不稳定。因为它并没有增加多少新的能力，却增加了大量新的冲突关系。Agent 更难选，开发者也更难维护。开发者不知道已有 Skill 之间到底差在哪，不知道新 Skill 是该复用现有能力还是继续新建，也不知道最近邻 Skill 是谁、边界该如何书写。最后最容易发生的事情不是体系越来越清晰，而是重复造轮子越来越快。

从工程角度看，这其实是一个典型的“命名优先于抽象”的问题。团队先有了业务标签，再围绕标签建模块，却没有先把能力单元抽象稳定。结果就是，系统表面上看起来功能越来越丰富，底层却越来越像一堆相互重叠的壳。

五、为什么很多评测看起来没问题，系统却还是不稳

很多 Skill 评测做得并不差，有正常样本、有边界样本、有异常样本，甚至还有失败模式设计。上文提到的“月度 AI 行业分析”这个 Skill 的设计不只是写了 Skill 本体，还补了 guardrails、failure modes，以及正常样本、边界样本、误触发样本、越权样本、漂移样本。这种写法已经不只是在测“会不会触发”，而是在测“触发之后会不会越层、会不会失真”。 但即便如此，还差一步。这一步恰恰是多 Skill 系统最关键的一步：竞争路由评测。也就是，不只是看这个 Skill 单独是否应当命中，而是看在多个相似 Skill 同时存在时，系统为什么选了它，而不是旁边那个。

真正该补的评测，至少有几类。第一类是相邻 Skill 混淆评测，比如把“AI 月度行研”和“通用行研”放在一起，看同一输入下系统如何取舍；第二类是多候选优先级评测，也就是同一任务同时满足多个触发条件时，系统是优先走低层、窄权限、低风险路径，还是直接进入高层分析或判断路径；第三类是错路由损失评测，不只是问“选错了没”，还要问“错到最近邻 Skill 之后，代价有多大”；第四类是降级与停机评测，在意图不清、材料不足、信息冲突时，系统能否主动降级，或者停在低权限层，而不是继续硬做；第五类是组合环境回归评测，也就是每新增一个 Skill，不只是测它自己，而是要看它是否破坏了周边 Skill 的边界稳定性。

这是很多人最容易忽略的地方。单 Skill 评测通过，不等于系统级可用。一个 Skill 很强，也不等于整套 Skill 体系很稳。因为真正的系统问题，不发生在孤立模块里，而发生在模块之间。

六、真正需要治理的，不只是 Skill 本身，而是 Skill 目录

如果把 Skill 看成一把把刀，那系统真正需要的不是“拥有更多刀”，而是“知道什么场景该先拿哪把刀，什么时候宁可先别拿刀”。所以当 Skill 系统发展到一定阶段，治理对象就不能再只是单个 Skill 的文案、prompt 和评测，而必须升级成整个 Skill 目录。

一个成熟的 Skill 目录，至少应该回答四个问题：第一，这个 Skill 属于哪一层，是低层的信息处理，还是中层的分析归纳，还是高层的建议与判断支持；第二，它和最近邻 Skill 的区别是什么，这种区别不是名称差异，而是输入对象、输出层级、权限边界和失败模式的差异；第三，它的默认降级路径是什么，意图不清时去哪，材料不足时去哪，信息冲突时去哪，高风险请求又该停在哪；第四，它会和谁抢活，也就是设计时就要明确最容易混淆的两三个邻居，因为很多路由问题本质上不是孤立问题，而是邻接问题。

只有把这些问题前置，Skill 体系才有可能从“功能堆砌”变成“能力地图”。否则，系统就会一直停留在一个危险状态：每个 Skill 自己都写得还行，但放在一起时谁都不够稳。

七、一个更稳的设计原则：先做“少而硬”，再做“多而细”

我的感受是，Agent 系统早期最该追求的不是 Skill 数量，而是 Skill 的硬度。所谓“少而硬”，不是简单压缩数量，而是保证每个 Skill 都满足几件事：边界清晰，输入契约明确，输出层级稳定，权限可控，失败模式清楚，最近邻关系可解释，放进真实目录里也不容易和旁边的 Skill 抢活。只有当这些基础问题都稳定后，系统才值得继续往“多而细”走。否则，Skill 加得越快，歧义就积得越快；目录看起来越丰富，路由就越容易漂；开发者以为自己在搭积木，最后其实是在堆迷宫。

这也是为什么新增一个 Skill 之前，最好先问几个问题：它解决的是一个新问题，还是旧问题换了个壳；它和最近的两个现有 Skill，差异到底体现在哪；如果路由错到旁边那个 Skill，损失有多大；它能不能通过参数化现有 Skill 来解决，而不是继续新增一个名字。只有这些问题都答得清楚，新增 Skill 才是在增强系统，而不是在制造新冲突。

八、成熟的 Agent，不是 Skill 越来越多，而是越来越不容易选错

很多人会把 Agent 的成熟理解成“会做越来越多的事”。这当然没错，但只说对了一半。真正成熟的系统，不只是会做更多事，更关键的是它在模糊输入面前有没有边界感。它会不会在意图不清时先降级，会不会在多个相似 Skill 里优先选低风险路径，会不会在证据不足时保留不确定性，会不会在高风险请求前停住，而不是装作自己已经理解了一切。**单个 Skill 的上限，决定了系统能做什么；多个 Skills 之间能否被稳定地区分，决定了系统会不会把事做歪。**所以对 Agent 来说，真正的能力，不只是“会做”，而是“在一堆看起来都能做的工具里，依然不轻易选错”。

  • 需要补充竞争路由评测，包括相邻Skill混淆评测、多候选优先级评测、错路由损失评测、降级与停机评测、组合环境回归评测五类
