一个 Skill 是怎么“看起来很强”却“用起来不稳”的

一、最常见的 10 种 Skill 伪工程

Skill 这个东西，很容易给人一种错觉：只要写得足够长、足够细、足够像“专家说明书”，就等于有工程感了。但真正做多了之后，你会发现，很多 Skill 看上去工程味十足，实际上只是 Prompt 变长了。它没有变成能力，没有变成接口，更没有变成一个能被复用、维护和验证的小系统。我把这类情况叫做“伪工程”。所谓“伪工程”，不是说它完全没用，而是它只在演示时显得很专业，一进真实场景就开始失灵。下面这十种，是我最常见到的。

第一种，名字很大，边界没有。 最典型的写法就是“行业研究助手”“战略分析专家”“高质量报告生成器”。名字一个比一个大，描述一个比一个强，但你真问它：到底是整理信息，还是输出判断，还是生成汇报稿？答不上来。名字越大，边界越空；边界越空，误触发越多。

第二种，description 像宣传文案。
很多 description 写得像产品首页：“你是一名经验丰富的研究顾问，擅长洞察行业趋势，能够输出高质量分析。”这对路由几乎没有帮助。系统需要的不是赞美词，而是规则：什么时候用、什么时候不用、最低输入是什么、输出固定成什么。

第三种，不写 when not to use。
只写适用场景，不写不适用场景，是 Skill 滥用的起点。比如“研究报告合稿 Skill”如果不写“不得直接替代最终战略结论”，它就很容易一路越权写到最后。

第四种，输入靠猜。 你让它“帮我整理下这个方向的研究”，却没告诉它时间范围、材料边界、目标读者、输出层级。结果今天给你一版摘要，明天给你一版评论，后天直接给出建议。不是它随机，是你根本没定义接口。

第五种，输出不固定。 同一个 Skill，有时写成目录，有时写成长文，有时写成表格，有时夹带建议。输出不固定，看似灵活，实则不可接入流程。因为别人永远不知道下一次它会交出什么。

第六种，所有步骤都丢给模型。
收集、清洗、去重、分类、归纳、成稿，全交给模型一次完成。这当然省事，但也是最不稳的写法。越是机械、重复、规则明确的步骤，越应该剥给工具和脚本，而不是让模型一边理解一边干杂活。

第七种，不设计失败路径。
很多 Skill 只设计“理想输入下怎么成功”，从不设计“材料不足怎么办、信息冲突怎么办、任务意图不清怎么办”。结果一遇到脏输入，系统就硬写。它不是坏，是你没给它停下来的权利。

第八种，默认权限过宽。
明明只是个信息整理 Skill，却顺手给了它写正式文稿、替换原文、甚至直接发送的能力。权限一宽，风险就不是线性增长，而是指数增长。

第九种，不做反例测试。 只拿最好看的三组样本去试，当然会成功。真正暴露问题的，从来都是那些“不该触发”“应该追问”“应该停机”的样本。没有反例测试，Skill 看起来永远很强。

第十种，demo 成功一次就宣布上线。 这是最常见也最危险的伪工程。一次成功，只能证明它在一个样本上跑通了，不能证明它变成了能力。能力要看复用、看稳定、看异常、看边界，不是看第一次是不是惊艳。

怎么从伪工程走向真工程：

  • 缩边界：把大 Skill 拆成小能力，不要试图一把梭；
  • 固定接口：输入输出写清楚，不要让系统猜你想要什么；
  • 设计异常：材料不够、信息冲突、意图不清，都要有明确处理；
  • 做评测：不仅测会不会做，还要测会不会停、会不会拒绝、会不会追问；
  • 最小权限：默认先少给，再逐步加。

真正的工程感，从来不在字多，不在术语多，也不在语气像不像专家，而在于这个 Skill 是不是能进流程、扛异常、少越权、可复跑。别把“写得很像系统”误当成“真的成了系统”。

二、看起来很强的 Skill，为什么一进入生产环境就翻车

很多 Skill 在测试时都特别像天才。你喂给它三份干净材料、一段清楚需求、一套明确格式，它不仅能顺利完成，甚至还常常会给你一种“这已经可以替代人工了”的错觉。但真正把它放进生产之后，事情就常常不是这样了。它会漏掉关键观点，会混错版本，会把旧结论写进新报告，会把个别人意见写成共同判断，会在证据不够时硬凑出一个完整结论。这时候大家往往会说，模型不稳定。其实很多时候，问题不是模型“忽然不行了”，而是你让一个只在理想输入里被证明过的 Skill，直接去面对真实世界。

最典型的例子，是我反复提到的研究报告合稿。假设你先在小范围测试这个 Skill。你给它三份结构接近、口径一致、时间相近的研究材料，再加一句要求：“合并成一份统一主题的年度研究报告，按趋势、案例、判断、建议的结构输出。”在这种环境里，它很容易表现得很好。因为材料都很完整、观点冲突很少、版本关系很清楚、所给的任务也很明确。这种条件下，一个合稿 Skill 不仅能跑通，甚至还能写得漂亮。

但一旦进生产，环境立刻变了。你不再只有三份材料，而是八份，甚至十二份。里面有不同时间写的版本，有旧口径和新口径并存的章节，有别人临时补的备注，有半成稿，有重复片段，还有一些只写了例子、没写结论的碎片化素材。更麻烦的是，你自己给的任务也未必那么清楚。有时候你说“先合一下”，心里想的是“先出底稿”；有时候你说“做完整一点”，心里想的是“先接近成稿”。这些不确定，测试环境里是没有的，生产环境里却全都有。

于是 Skill 开始翻车。它可能把 1 月份的旧判断和 3 月份的新材料并列进同一章节，却没意识到结论已经变了；它可能把两份报告里略有差异的统计口径当成同一件事合并，结果把数字写乱；它可能为了让文章更顺，主动把一些冲突观点压平，制造出一种并不存在的“统一叙事”；它甚至可能在材料不足的地方，补上听起来很合理的过渡句和结论句，表面更完整，实际更危险。

这就是为什么很多 Skill 一上线就翻车：它不是不能做，而是只在“好样本”里学会了做。生产环境比测试多出来的，至少有四样东西。

**第一，脏输入。**真实材料不整齐、不完整、不一致，这是常态，不是例外。

**第二，冲突信息。**同一个结论在不同版本里可能相反，同一个事件在不同来源里可能口径不同。测试时你很少故意喂它这些东西，生产里却天天有。

**第三，模糊意图。**用户自己都未必把任务层级想清楚。到底要底稿、提纲、摘要还是终稿，这些在真实使用时经常是混着说的。

**第四，责任压力。**一旦输出真的要给老板看、要进入决策会、要接到正式文档流里，系统的每一个漂移都会被放大。

所以，真正的问题不是“为什么模型一上线就变差”，而是“为什么我们会拿一次漂亮 demo，当成它已经具备生产能力的证明”。要避免这种事，最重要的是放弃一步到位的幻想。

**第一，先做影子运行。**同一个任务，让 Skill 跟着跑，但不直接进入正式流程。你先看它在哪些环节会偏，再决定是否真的放出来用。

**第二，先做副驾驶，不做主驾驶。**让它先产出底稿、结构稿、辅助稿，而不是最终定稿。这样即使它偏了，也还有人工校正的余地。

**第三，评测要加入脏样本。**不要只测理想材料。要故意给它冲突版本、缺字段输入、边界不清的需求、混杂结构的素材。只有这样，你才会知道它在真实世界里是不是还站得住。

**第四，权限分阶段放开。**先只给整理权，再给成稿权；先只给内部草稿，再考虑正式流转。不要一开始就假设它配得上全部权限。

生产环境不会放大你的成功，它只会放大你的缺陷。一个真正稳定的 Skill，不是在最顺的样本里跑得多漂亮，而是在最脏的环境里，依然知道什么时候该做、什么时候该停、什么时候该把问题暴露出来。
