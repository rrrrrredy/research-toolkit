把 Skill 当 API 写，而不是当作文写

很多不稳定的 Skill 的写作方式：它看起来很认真，很完整，很有专家口吻，甚至会写上“请深度思考”“请全面分析”“请系统归纳”，但你一旦把它放进真实工作流里，结果往往并不稳定。同样一个任务，今天输出一份摘要，明天输出一篇评论；今天分三层结构，明天突然自由发挥；今天会标注证据来源，明天又把推测和事实混在一起。问题出在哪？很多时候不是模型忽然变笨了，而是这个 Skill 从头到尾就没有被当成一个接口来设计。

所谓的“把 Skill 当 API 写”，并不是让非技术用户去学编程，而是换一种更清醒的任务表达方式：不要把 Skill 当成一个“懂你心思的写作者”，而要把它当成一个“接受输入、返回结果、遇错停下、边界清楚的能力接口”。一旦换成这个视角，很多原本说不清的问题会突然变清楚。

举个工作场景的例子：要把 8 份已有报告合成 1 份统一主题的研究报告。这里面包含不同时间写的材料、不同作者的口径、重复的观点、互相冲突的数据、长短不一的章节结构，还可能夹杂一些已经过时的判断。如果你只是给系统一句话：“把这 8 个报告整合成一篇完整报告，要有深度、有洞察、有结构。” 这当然听起来很合理，但它对一个 Skill 来说，几乎等于没说。因为这里至少有六个关键信息没有被定义：

**第一，输入的优先级是什么。**如果八份文档观点冲突，是以后写的为准，还是以你指定的主报告为准？没有这个规则，系统就可能把旧版本的结论和新版本的判断硬拼在一起。

**第二，输出层级是什么。**你要的是“一版合稿底稿”，还是“可以直接给老板看的成稿”？前者可以保留冲突、暴露缺口；后者则需要更强的选择和收束。两者不是一个任务。

**第三，允许不允许保留不确定性。**如果一条趋势在文档 A 里被强调，在文档 B 里却被弱化，系统是应该替你拍板，还是应该把差异列出来，等你再判断？这决定了它是“代写结论”还是“辅助研究”。

**第四，输出结构是什么。**是按“趋势—证据—案例—行动建议”写，还是按“海外—国内—重点公司—后续观察”写？没有固定结构，结果就会漂。

**第五，证据要求是什么。**是不是每个判断都必须回到材料里能找到依据？能不能补充外部常识？能不能做跨文档推断？这些不说清楚，就很容易把“整合”做成“创作”。

**第六，异常怎么处理。**如果发现几份文档的统计口径不一致，是继续合并，还是先标红冲突点？如果有一份材料只有半成稿，是跳过，还是作为附录处理？这就是典型的接口问题，而不是文风问题。

所以，一个真正可交付的研究合稿 Skill，它需要：

  • 明确必需输入，例如主题、目标读者、主报告优先级、时间范围、输出格式；
  • 明确可选输入，例如章节框架、是否需要保留冲突观点、是否需要行动建议；
  • 明确默认值，例如若未指定目标读者，默认输出为内部研究底稿；
  • 明确异常处理，例如遇到冲突数据时不强行统一，而是并列展示并标注来源；
  • 明确固定输出，例如摘要、结构目录、合并后正文、冲突信息、待核实问题；
  • 明确禁止行为，例如不得把未经证实的补充信息写成正式结论。

这就是接口思维。

可能人会觉得，这样写是不是太“工程化”了，会不会失去灵活性。恰恰相反。知识工作的最大敌人，不是规则太多，而是大家总以为彼此理解了一样的东西，最后交付出来的却根本不是同一种结果。

再看另一个场景：周趋势洞察提炼。 这类任务尤其容易失控，因为它天然介于“信息整理”和“观点判断”之间。你把最近一周的公司动态、产品动作、技术趋势和市场声音整理给系统，系统很容易一脚踩进“总结 + 判断 + 建议”三合一模式。最后明明只是想先看本周发生了什么，它却直接写出“建议公司重点关注某方向”的句子。

如果用接口思维来写，这个问题就会简单很多。你可以把任务拆成三个层次：

  • 第一层，信息摘要：发生了什么；
  • 第二层，趋势提炼：这些事件可能说明什么；
  • 第三层，行动建议：对我们意味着什么。

这三层完全可以由三个不同的 Skill 完成，或者至少在同一个 Skill 中明确分段、分权、分风险。一旦不拆，系统就会默认“既然你让我总结，那我顺手替你判断一下”。这其实就是很多 Skill 看起来“聪明”，用起来却不稳的根本原因：它没有接口，只有意图；没有明确的输入输出，只有一段很会说话的说明书。

所以我越来越觉得，非技术用户尤其应该学会这种接口思维。因为它不是程序员专属，它本质上是在训练一种更清楚的工作表达方式：

  • 我要给你什么材料；
  • 我希望你产出什么；
  • 什么情况你可以自己处理；
  • 什么情况你必须停下来；
  • 哪些东西你可以整理；
  • 哪些东西你不能替我决定。

当这些问题都被提前定义好，一个 Skill 才会真正从“看起来很厉害”，变成“真的能交付”。

**作文式的 Skill，靠读者理解；接口式的 Skill，靠系统执行。**而真正能进工作流的，永远是后者。
