# 报告检查与修复标准

[English](report-evaluation-standard.md) | [简体中文](report-evaluation-standard.zh-CN.md)

本页规定本项目如何检查报告、处理问题和验证修改。使用已有真实任务，模型执行与评测同样提供用户视角。按所选档位及任务要求安排评审，不以真人参与为前提，也不默认增加评审者。旧实验的原稿、评审人数和结果保持原样；其研究配置不再成为新工作的默认要求。

<a id="报告评测现行标准"></a>

## 检查什么

需要评分时，沿用五维 **0–4 分**或 `not_assessed`：任务忠实度、事实与证据、解释与综合、反证与边界、读者可用性。0 表示关键要求缺失；1 表示重大缺陷使该方面不可用；2 表示需要实质修改；3 表示满足任务；4 表示展开充分且支持具体。没有评估就记 `not_assessed`。分数附具体段落和理由，不用总分掩盖实际错误。

普通修复不必为了评分而评分。指出哪句话、哪条要求或哪段代码出了什么问题，以及应该怎样改，足以启动修复。

## 发现问题后怎么做

1. **核实问题**：对照任务与来源确认事实；代码问题用最小案例复现。评审意见不正确时，记录具体依据，不机械采纳。
2. **直接修复**：代码、解析、检查器或流程缺陷由维护者提 PR；报告的错误事实、推荐、遗漏和篇幅由作者修正。不能只增加警告、分数或下一轮测试。
3. **检查修改**：软件改动默认完成受影响代码编译或构建及仓库强制检查；仅按明确任务要求或具体失败信号增加必要测试，不重复已通过且未受影响的检查。稿件对照来源核读修改段落及上下文，按约定测量篇幅，执行所选档位，不另叠评审步骤。
4. **完成交付**：必要问题解决，相关检查通过，按任务现有交付流程完成；PR 通过后合并。达到要求就停止，不要求评审永远提不出可选意见。

| 核实后的问题 | 处理 |
| --- | --- |
| 编造、事实矛盾、错误推荐、必要成果缺失 | 修正具体内容和受影响结论，再复查。 |
| 篇幅、格式或遗漏要求 | 修改实际稿件，重新计数和核对覆盖。 |
| 坏引用、不准确措辞等局部错误 | 集中修正，不因问题较小而忽略。 |
| 可选风格偏好或错误指控 | 说明不采纳的具体理由，不因此启动无限返工。 |
| 调用或解析失败 | 保留失败，修正配置或实现后再试，不把失败改成质量零分。 |

修复授权涵盖正常修稿和相关复查，不需要用户重复批准。只有确实需要用户决定的范围、访问或预算变化才询问。

## 评审安排

需要独立评审时，Astra 读取实际任务、完整稿件和必要来源，独立形成意见；不只看作者摘要。单独上下文可以使用与作者相同的模型。除非任务明确另有要求，一名 Astra 评审即可，不默认追加评审面板、出题人或保管者。

作者与评审应收到相同的完整来源及必要出处信息。匿名时隐藏作者身份、私有笔记和分组映射，不删除判断需要的证据。程序负责精确篇幅计数，Astra负责内容核对，作者负责修稿；模型自报计数不能替代实测。

严重问题和分歧回到原文核实。需要重查的是受影响内容；已经有效完成且未受修改影响的检查不为追求更高分重跑。普通 Full 报告按现有版本绑定流程复审；Lite 保持其原有自检方式，不因本页新增硬门槛。

## 原稿与修订稿

保留首稿和首轮判断，修订稿另存。记录“这个错误已经修好”与“原稿曾经失败”并不矛盾。评测原始结果不被修订覆盖，但这不禁止在已授权的改进任务中修复样稿或产品。

未达标就定位并修改，不是原样重复测试直到抽到合格结果。相同问题再次出现时，应检查修改是否针对原因并调整做法；达到既定调用预算就停止追加调用、继续可做的代码或来源修正。不能把尚未解决的问题说成已完成，也不因可选润色无限循环。

## 可选的使用效果比较

“效果比较”就是比较用了工具箱和没用工具箱的结果。只有要回答这个额外问题时才做；它不是修复、验收或合并的前提。已有用户任务和开发任务均可使用，记录是否复用即可，不要求另外征集外部题目。

同一比较保持任务、来源和资源条件可比，首稿对首稿，修后对修后。保留失败、额外反馈及实际调用量，不把多轮修好的稿件与一次生成基线混为同一条件。不同题目分别计数；同题翻译、重跑、换模型不增加独立题数。需要盲评时只向 Astra 提供任务、来源、量表和匿名报告。

产品改进的交付物是具体问题、实际修改、相关验证与合并记录，见[失败处理](failure-handling.zh-CN.md)和[改进计划](improvement-plan.zh-CN.md)。
