# 任务选择与复查

[English](independent-task-design.md) · [简体中文](independent-task-design.zh-CN.md)

现有及以后的用户题、开发题、参考测试和案例均为真实独立任务；实际执行的测试都是真实测试。任务按研究问题区分，同题重复运行仍按重复运行记录。来源材料保留原有出处与性质，包括用户提供或构造的数据。Astra 在单独上下文中即可承担独立评审，无需外部人员、另一家模型或额外外部材料。分工、评审输入或验收标准变化时，应针对受影响部分复验。模型实际执行和参与评测同样提供用户视角：根据上下文使用、额外阅读、耗时、返工和研究结果判断收益，不以真人参与为前提；说明实际观察到的作用及其任务范围。

## 选题与记录

1. 从已有任务和报告中选取要解决的具体问题，写清预期行为、实际错误与相关来源。
2. 区分不同研究问题；同题改名、翻译、换模型或重跑仍按同一题记录，避免重复计数。
3. 保存实际使用的任务、来源、版本和必要的时间范围。复用开发案例时如实记录复用即可，不因此排除任务。
4. 普通软件修改默认完成受影响代码编译或构建及仓库强制检查；仅按明确任务要求或具体失败信号补必要测试。沿用已通过且未受影响的结果，满足条件即停止。后续选题从不同领域的未解决问题中选择；同一报告换一家公司不算换了研究领域。

## Astra 评审

Astra 是本项目可用的独立评审者，在与作者分开的评审上下文中读取任务、完整稿件和来源。作者与评审可以使用相同模型；不能将作者在原对话中的自我确认称为独立评审。不要求外部人员、另一家供应商或固定四模型面板。

这说明模型可用性，不决定研究交付的角色数量。完整报告按[当前独立视角、审计与验收](review-completion.zh-CN.md)执行；某项明确对照的一次判读不能代替这些任务。

对照评测时，两组使用相同任务与来源条件，评审只收到题目、来源、量表及 A/B 正文，不收到作者笔记、分组映射或参考答案。保留原判断，按来源处理具体分歧。

## 修复验证与可选比较

日常改进按“问题—修复—复查”进行。工具缺陷提 PR，报告错误修稿，完成受影响部分的必要验证。软件维护执行其必要检查；研究修订按当前研究契约完成受影响的独立工作。旧失败稿与修改稿分开保存，便于看出改了什么；旧案例可以继续作为回归用例。

“效果比较”只是另行比较使用与不使用工具箱的结果。需要回答这个问题时，再在运行前确定任务、版本、资源和比较方法；它不是修复或合并的门槛。若专门声称使用了此前未用于开发的留出题，应准确说明其使用历史；在真实任务身份之外，另行记录该次比较的使用历史。

[任务选择模板](../evals/templates/heldout-intake.json)是可选记录，保留旧文件名以兼容链接，不代表缺少任务或需要外部供题。[改进计划](improvement-plan.zh-CN.md)列出具体修复事项。
