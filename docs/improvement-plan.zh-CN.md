## 执行顺序与验收

每批围绕一个可验证问题提交 PR，通过相关回归和完整 CI 后合并。表中“待推进”不代表已验证缺陷；需先复现。可以推进不依赖前项的文档和离线设计工作。实验只等待会影响其输入、执行或判断的前置修复，不要求全部维护工作结束。

| 批次 / 优先级 | 工作及交付物 | 验收条件 | 状态 |
| --- | --- | --- | --- |
| R1 / P0：执行可靠性 | CLI、MCP、Python 共用跨进程任务锁；保留异常编码的原始评审输出，正确区分启动失败与输出损坏。 | 两个进程不能同时改同一任务；不同任务可运行；崩溃后锁可释放；负面评审与超时证据保留；UTF-8 异常不丢原件。 | 本批实现 |
| R2 / P1：使用体验 | 工具升级时固定在途审查指令；改善缺参、错误行定位和按需指南；核对安装前提及双语入口。 | 老任务不因无关文档升级丢失复审能力；新用户按文档从模板完成修稿交付；错误说明具体下一步。 | 待推进 |

| E1 / P1：评测基础设施 | 显式配置提供商格式、模型别名和预算；保留原始返回及解析方法；区分截断、超时、格式失败、质量缺陷；配置冻结与调用上限。 | 围栏等格式差异可按预先声明规则处理，歧义或无效内容保留为失败；不因负面结果重跑；密钥不进入配置、命令参数或公开材料。 | 下一批 |

## 下一轮评测设计

先冻结协议，再锁定题目和调用配置，最后运行。暂定四家 API 作为作者模型，Codex 中请求 `gpt-6-astra` 作为开发阶段评审；实际可用模型和返回名称以接入结果为准。接入测试不计入报告质量结果。若 Astra 作为作者，单列模型层并由其他模型评审，不能使用已看过分组的开发对话代替盲评。

任务从五类需求开始设计：数值口径与单位核对、冲突证据下的选择、因果与相关区分、受约束方案比较、随时间变化的证据综合。每类采用新的题面与材料，避免只重写旧五题；中英文分层记录，翻译或同题换模型不增加独立任务族数量。合成材料用于协议及缺陷识别校准；真实研究另需可公开来源和明确时间边界。编写者已看过的材料公开标为开发暴露，不声称未知训练数据或真正外部留出集。

盲法采用预先固定的报告／notes 分离规则。两组均把执行和独立审阅状态放在 notes；评审包只含题目、来源、量表及 A/B 正文。不得看见结果后删句、改写报告或更换标签；残留工具、模型或流程线索单独登记并报告盲法局限。次序互换用于观察位置敏感性，不当成新增任务。评审先用长度匹配、含具体证据的有效／缺陷对照校准；不同模型的一致意见不等于事实。

第一阶段仅做各提供商一次短接入调用及一次独立 Astra 调用，最多五次生成、无自动付费重试；失败保留后再诊断。批量开发试验开始前，另存机器可读计划，列出模型、请求数、token／时间上限、重试规则、两组资源、评审面板、来源哈希与结果指标。正式效果研究遵循[当前标准](report-evaluation-standard.zh-CN.md)；单一 Astra 评审的开发试验是明确缩小范围的诊断，不能冒充四评审面板或普遍效果结论。

## 取舍与更新规则

暂不实施强制更多确认、用最小字数或“未读”等词判断研究真伪、强制维度加总等于整体偏好，也不未经引用检查迁移或删除资源。安装命令按支持的平台核对，不把所有 `python` 简单替换为 `python3`。包目录重组和大型素材迁移排在可靠性与方法改进之后。

每次合并更新本页的状态、PR 和验收证据。分别报告流程完成、机械合规、稿件质量和工具效果；不能把其中一项通过写成另一项通过。API 密钥仅在本地调用进程中使用，研究配置只保存环境变量名；公开前检查请求、响应、错误和来源中的敏感信息。
